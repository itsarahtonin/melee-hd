# The player

melee-hd's player presents the simulation: it draws the display pass's commands, mixes the audio driver's voices into sound, and reads the controllers into the simulation's input. The [architecture](architecture.md) draws the line: everything here is presentation, and nothing here feeds back into `melee-sim`.

## Crates

| Crate | What it does |
| --- | --- |
| `melee-render` | Turns a frame's `display::Draw` commands into a GX command stream (HSD's display code ported to issue GX SDK calls), and draws that stream with melee-gpu |
| `melee-gx` | The GPU's command stream and register state: runs a stream, handing each draw and EFB copy to a renderer (ported from ssbm-rs's `ssbm-gx`) |
| `melee-gpu` | Draws the stream with wgpu (ported from ssbm-rs's renderer, `ssbm-render`) |
| `melee-audio` | Mixes the voices the simulation keeps into samples, as the DSP's AX microcode does, and plays them |
| `melee-ax` | The DSP's AX microcode (ported from ssbm-rs's `ssbm-ax`) |
| `melee-slippi` | Slippi replays (`.slp`), what Slippi's EXI device answers playback's codes from them, and recordings written as `.slp` files |
| `melee-input` | The keyboard, standard gamepads and the GameCube controller adapter, as the simulation's pad input |
| `melee-player` | The `melee-hd` binary: a VS match in a window |
| `tools/render-check` | Compares melee-render's frames with ssbm-rs's renderer's |
| `tools/audio-check` | Compares melee-audio's mix of a replay with ssbm-rs's recording of its audio |

`melee-sim` depends on none of them.

**Decision: no ssbm-rs code runs in the player.** ssbm-rs is the test oracle. The player's crates are melee-hd's own, ported from ssbm-rs where it has the piece (the GX stream decoder, the renderer, the AX microcode, the replay reader), as `crates/gekko-fp` is: idiomatic melee-hd code to change, not frozen copies. ssbm-rs's crates stay dependencies of the check tools, which compare against it. `crates/melee-player/tests/runtime_deps.rs` fails if `cargo tree` finds any ssbm-rs crate among the player's normal and build dependencies, and `leaf-check`'s `slippi` test parses every benchmark replay and a sample of Slippi replays with both melee-slippi and ssbm-rs's `ssbm_slippi` and compares the results.

## Rendering

The display pass names the objects it draws (a joint's display object's shape, a camera, a light set, a particle link) and leaves their state as it was when the pass drew them. `melee-render` ports what HSD would have sent GX for each: the camera's viewport, scissor and projection (`HSD_CObjSetCurrent`), the lights' GX objects (`HSD_LObjSetupInit`, `HSD_LObjSetup`), the material's colors, textures, texture coordinates, TEV stages and pixel-engine mode (`HSD_MObjSetup`, HAL's TEV expression compiler, `HSD_SetupRenderModeWithCustomPE`), and each shape's matrices, vertex descriptions and display list (`HSD_PObjDisp`). Those go through a port of the GX SDK (`melee_render::gx`), which encodes the same command stream the console's SDK would, register write for register write.

**Decision: the GX command stream is the interface to the GPU.** The stream is what melee-gpu (ssbm-rs's renderer, `ssbm-render`, ported) draws, and its frames match Dolphin's software renderer within tolerance. Encoding the stream and running it through `melee-gx` costs little next to drawing, and buys two things: the renderer is the one whose output is already checked, and each frame can be compared with ssbm-rs's draw by draw (`melee-render-check`), with every register, transformed vertex and texture of each draw, not only as an image.

**Decision: per-draw state the pass changes is snapshotted.** Most objects keep the same state through a frame's pass, so the renderer reads them as the pass left them. A few change between draws, and the simulation records what the presentation needs at the moment of the draw (in `display::Display`, so drawing allocates nothing once warmed up):

- a camera can draw more than once a frame, moved in between (the magnifier's, once per bubble): `Draw::Camera` names a `CameraView` with the viewport, scissor, projection and view matrix;
- the magnifier erases each bubble in a color it blends from the stage's colors by where that player's fighter is (see **Magnifier bubbles** below): `Draw::MagnifierErase` names the player;
- the lights' GX slots are given by every `HSD_LObjSetupInit` (a light GObj's callback, a fighter's lights, a fighter's overlay light): `Draw::Lights` names a `LightSet` with the active table, the light masks and each light's specular slot and vector;
- materials read the GObj being drawn (`HSD_GObj_804D7814`: a fighter's color overlays and translucency, a stage object's or item's overlay): `Draw::Rendering` names it;
- the shadow textures shadowed materials take after their own (`tobj_shadows`) change joint by joint while a stage object that receives shadows draws (see **Stage shadows** below): `Draw::Shadows` names the list as a shadowed material sets up, whenever it differs from the last named;
- a highlight texture takes the first current infinite light's vector, and render callbacks change the current lights between draws: `Draw::Hilight` names the vector as a material with one sets up, whenever it differs from the last named (see **Highlights and specular lights** below);
- the toon texture's image (`tobj_toon->imagedesc`) is set by Poké Floats' render callback around each float's draw and cleared after it (`fn_802130D0`), so the frame's end holds none: `Draw::Toon` names it as a toon material sets up, whenever it differs from the last named (see **Poké Floats' toon texture** below);
- a fighter's render callback sets its draw flags (`x2223_b2`, `x2223_b3`, `x2228_b0`) before each tree it draws, and Mr. Game & Watch draws three in a pass: `Draw::FighterFlags` names them as a fighter's material sets up, whenever they differ from the last named (see **Fighters' trees and lights** below);
- a fighter's material that sets its light up without alpha sets its channels from those lights before it sets the light up again with alpha: `Draw::LightsAfterRenderMode` names the second set, which melee-render loads after the material's render mode (see **Fighters' trees and lights** below);
- a specular joint leaves its half vectors in the specular lights for what follows, whether or not any of its shapes draw in the pass: `Draw::SpecularInit` names the joint for every pass `HSD_JObjDispSub` draws it in;
- a particle's app-SRT takes the view of the camera drawing it, once per display frame, so the frame's last view is the last camera's: `Draw::AppSrt` names the view matrix and screen scales whenever the pass brings them up to date (see **Particles in the reflection** below);
- a stage object's render callback puts HAL's state caches out of date before it draws (`grDisplay_801C5DB0`'s `HSD_StateInvalidate(-1)`): `Draw::Invalidate` names the reset (see **State cache resets** below).

These are additions to `melee-sim`'s output only; no simulated value depends on them.

**Stage shadows.** A stage object that receives shadows (`x10_flags.b5`) draws joint by joint (`grDisplay_801C5B90`): before each joint, the stage's check (`stage_info.on_check_shadow_render`; Yoshi's Story's, `grStory_801E36D8`, asks whether the fighter stands above the joint) switches each fighter's shadow on or off, which adds its texture to or takes it from the list shadowed materials take after their own (`lbShadow_8000EFEC`, `HSD_ShadowSetActive`, `tobj_shadows`). Each material's setup then gives its chain texture maps, matrices and coordinates afresh (`HSD_TObjSetup`'s `HSD_TObjAssignResources`), so the shadows' slots, and a material's own UV coordinates, which come after the shadows', depend on the chain being drawn. melee-render read both as the pass left them at the frame's end: the last joint's list for every shadowed draw, and each texture's resources from the pass's last setup of it. So stage draws took shadows the original's don't (Yoshi's Story's, Dream Land's and Fountain of Dreams' platforms, Pokémon Stadium's floor and its transformations' ground), with resources from other chains: on Yoshi's Story the left platform's texture shared its coordinates with a shadow's and its top came out white, and on Pokémon Stadium the floor's textures took other slots, so a 256 by 256 CMPR texture went missing from some of its draws and a white band crossed the Poké Ball (PSNR 15.2 dB at frame 600). The pass now names the list (`Draw::Shadows`), and melee-render assigns each chain's resources as it sets the chain up (`hsd::Assigned`), as the original does. The frames those differences reached are identical now (Yoshi's Story's 600 and 6000, Pokémon Stadium's 600, 2600 and 11000) or keep only a difference of their own (Dream Land's, Fountain of Dreams', Stadium's screen at 9000). Mutation checks, each made by reverting part of the fix locally: reverting both fails 12 checks (`fox_sheik_ys_600` at 33.4 dB, `fox_marth_ps_600` at 15.2 dB, `sheik_fox_fod_600`, and the sweep's Yoshi's Story 6000, Dream Land 6000, Pokémon Stadium 2600, 9000 and 11000, Fountain of Dreams' three frames and its scaled 6000); reading the frame's last shadow list again, with the resources assigned, fails 7 (`fox_sheik_ys_600` at 65.7 dB in its second frame, and six of the sweep's); keeping the shadow list but reading the resources the pass left fails 5 (`fox_marth_ps_600` at 15.2 dB again, and the sweep's Dream Land 6000 and Pokémon Stadium 2600, 9000 and 11000). The floor's white band was the resources; the platforms' extra shadows were the list.

**Magnifier bubbles.** The magnifier's camera erases each bubble before drawing its fighter (`ifMagnify_802FBBDC`), in a color it blends from four of the stage's nine colors (`GroundParam::xB8` through `xD8`, a three by three grid around the camera limits): which four depends on which half of the limits, or which side past them, the fighter's camera bone is in (`ifMagnify_GetCornerColors`, `ifMagnify_803F984C`), and the blend on how far into that half it is. melee-render took the average of the magnifier's own four colors (`ifMagnify`'s `x4` to `x10`, the grid's corners) for every bubble, so on Pokémon Stadium's fire stage Fox's bubble was dark where ssbm-rs's is gray. The display pass now names the player whose bubble it erases (`Draw::MagnifierErase`, an addition to the output only), and melee-render blends the color with the original's single-precision operations (`magnifier_erase_color`). Pokémon Stadium's frame 6000 is identical now (it was 22.1 and 39.3 dB), against a capture made with ssbm-rs's renderer running (see **Copies made before a log** under [Results](#checking-frames)). Mutation check: putting the average back fails `fox_marth_ps_6000_fire` (39.3 dB in both frames); Dream Land's 12000 still passes: there the average and the blend come to the same color, and its recorded difference was the capture's.

**Compiled TEV.** A material's TEV stages are the ones its compile made as it loaded, not ones made from its textures as drawn ([the engine notes](engine.md#the-object-state)): melee-render draws from the compile melee-sim keeps on the material (`MObj::tev`). Recompiling at each draw left Fountain of Dreams' water a stage short: the stage turns the reflection's texture into a shadow lightmap after it loads, so the original's water still blends the reflection in by a constant (0x4C) and then multiplies by it, where melee-render only multiplied, and the water came out about 8 levels greener and 5 bluer once the reflection showed. It isn't the reflection's RGB565 copy, the earlier suspect: melee-gpu drawing ssbm-rs's log makes gxplay's frames exactly, and the copy's texels at the water's draw are the same on both sides. `compare` hadn't shown the draw, as it printed only the first 20 differing events and the stars' point size register differed in every draw. The sweep's frames 2600, 6000 and 9000 went from 32.3/32.4, 33.3/33.8 and 32.0/32.1 dB to 59.4/65.1, 40.6/55.1 and 50.0/49.3 dB (with the point size below). The comparer checks each material's compiled stages and constants against the original's memory; the four benchmark matches and Fountain of Dreams' replay compare every tick with no difference with it. Mutation check: compiling at each draw again fails `sheik_fox_fod_600` (48.5 and 48.8 dB) and the sweep's Fountain of Dreams frames (32.4/32.6, 34.4/35.1, 32.1/32.2 dB) and its scaled 6000.

**Unset TEV components.** `HSD_TExpSetReg` sends the components of a TEV or konst register that none of its constants set as its uninitialized stack held them; melee-render sends 0 there and marks them unset in GX (`Gx::unset`). A draw whose active stages read a component marked unset is noted (`frame::UNSET_READ`), so a frame check expecting a frame drawn exactly fails on it ([the engine notes](engine.md#uninitialized-values)); `melee-render-check notes DISC REPLAY [TO]` builds a whole match's frames without drawing them and lists what melee-render noted, with how often and from which frame.

**Highlights and specular lights.** Sheik's needle reflects a highlight texture (`TEX_COORD_HILIGHT`), whose matrix `TObjSetupMtx` makes from the first current infinite light (`HSD_LObjGetCurrentByType`). melee-render looked that light up in the current lights as the pass left them at the frame's end, which in the four-player match hold no infinite light, so it loaded the no-light matrix and the needle's texture coordinates came out constant (195 components, a 3 by 10 pixel box below the stock icons, and 3 pixels in the second frame at 59.5 dB). The pass now names the light's vector as the material sets up (`Draw::Hilight`). On Dream Land a few vertices' specular colors differed, by up to 43 levels, in about 80 draws a frame: `HSD_JObjDispSub` makes each specular light's half vector toward every specular joint it visits (`HSD_LObjSetupSpecularInit`), even one whose shapes are all hidden in that pass, and the last joint's vectors stay in the lights for the draws after; melee-render made them only for joints that drew a shape, so after Sheik's hidden parts in the translucent pass the original's lights held other vectors than melee-render's (`Draw::SpecularInit` now). Dream Land's few differing pixels (90.5 and 64.6 dB) were its background's: its billboard (`JOBJ_RBILLBOARD`) took its scale from `PSVECMag`, where `HSD_MtxColMag` is `sqrtf` of the single-precision sum, so the diagonal differed in its last bit and the depth test turned on it. `SetupSharedVtxModelMtx` always loads the normal matrices as texture matrices (its joint flags share their values with `SETUP_NORMAL` and `SETUP_REFLECTION`), which melee-render now does too; no checked draw reads them, but the transform unit's memory is compared (see [Checking frames](#checking-frames)). `four_fd_600` and `fox_sheik_dl_600` are identical now, draw for draw. Mutation checks, each made by reverting one part locally: ignoring `Draw::Hilight` fails `four_fd_600` (the needle's texture matrix, and 59.5 dB in its second frame); naming half vectors only for joints that draw a shape fails `fox_sheik_dl_600` (the specular light in the transform unit's memory and the colors of 167 draws, though no pixel); `PSVECMag` for the billboard fails `fox_sheik_dl_600` (positions and the position matrix; 90.5 dB in its first frame); loading the shared-vertex setup's texture matrices only by `GetSetupFlags` fails `fox_sheik_dl_600` (the transform unit's memory, every draw after Dream Land's first skinned shape).

**State cache resets.** Every stage object's render callback puts HAL's state caches out of date before it draws, whether or not it draws anything (`grDisplay_801C5DB0`'s `HSD_StateInvalidate(-1)`), so the original sends the next draw's vertex description, pixel engine and channel state again; as the last register it writes is then an XF register, it sends no flush primitive (`__GXSendFlushPrim`) before the next display list. melee-render's caches still held the last stage draw's, so it sent less and ended on a BP register: an extra 8-vertex degenerate draw between Final Destination's and Dream Land's opaque and translucent background passes, which drew no pixel. The pass names the reset (`Draw::Invalidate`). The fighters' and items' resets (`ftDrawCommon`, `itDraw`) come only with their debug displays (hitboxes), which a match never turns on. Mutation check: ignoring `Draw::Invalidate` fails `four_fd_600` and `fox_sheik_dl_600` (the extra draw, in both frames).

**Particles in the reflection.** A particle with an app-SRT (attached to a joint) is drawn through its app-SRT's view matrix, which its first draw in a display frame makes from the current camera (`psDispSubAppSRT`), and each camera starts a display frame (`psDispParticles` in pass 0). Fountain of Dreams' reflection camera draws them first, mirrored, then the game camera; melee-render read every app-SRT's view as the pass left it, the game camera's, so the reflection's attached particles (about 25 draws a frame) were placed tens to thousands of pixels from ssbm-rs's, a ring of difference in the water at frame 6000 (40.6 dB). The pass names each view as it makes it (`Draw::AppSrt`). The sweep's Fountain of Dreams frames 2600, 6000 and 9000 are identical now. Mutation check: ignoring `Draw::AppSrt` fails `sheik_fox_fod_6000` (the particles' positions; 40.6 and 55.1 dB).

**Point size.** Fountain of Dreams' stars are points of size 18 (`grIzumi_801CCB90`'s `HSD_StateSetPointSize`, `Draw::PointSize`), which melee-render noted and skipped; it now sets the point size, and melee-gpu draws each point as a square that size, as ssbm-render does. The stars and the line and point register of every draw after them now match, and `sheik_fox_fod_600` is identical (it was 41.1 and 41.2 dB). Mutation check: skipping the point size again fails `sheik_fox_fod_600` (41.9 and 42.0 dB) and the sweep's three Fountain of Dreams frames and its scaled 6000.

**Poké Floats' toon texture.** The floats are toon-shaded: each float's materials take the toon texture (`tobj_toon`, a 32 by 32 RGB565 ramp in the executable, `grPu_803E7620`) first in their chain, looked up by the light, and the compile at their setup names it (`MObj::tev`). Their render callback sets the toon texture's image around each float's draw and clears it after (`fn_802130D0`), so melee-render, reading the toon texture as the pass left it at the frame's end, found no image and left it out of the chain (`material_chain`); nor could it have drawn it, since an image in the executable (`ImageRef::Static`) resolved only as a magnifier bubble's copy. The material's own texture took the toon's texture map, and the compiled stage that reads the toon sampled a map nothing in the draw loaded, whatever an earlier draw had left in the renderer's texture unit: black while the unit is empty (the match's first frames, and an F12 capture's fresh render, whose renderer starts empty), otherwise the last texture loaded there (at frame 900 of the oracle match, Yoshi's green). So the floats came out wrong from the match's first frame, and a capture's live and fresh renders disagreed. The allocator model had nothing to do with it: the frame checks run without it, and no simulated value changes. The pass now names the toon texture's image as a toon material sets up (`Draw::Toon`); melee-render builds the chain and finds the image from it, and reads an image descriptor in the executable's data, and its texels, from `main.dol` (`Space::dol_bytes`), noting one outside it. Poké Floats' frames 900 and 6000 are identical now. Mutation checks: reverting the fix fails `poke_floats_900` (PSNR 13.1 dB in both frames, 142 of 801 events differing) and `poke_floats_6000` (16.9 dB, 348 of 719); ignoring `Draw::Toon` alone fails `poke_floats_900` the same way, and resolving only the bubbles' images again fails it at 13.6 dB. No other stage sets the toon texture, and the magnifier's bubbles are the only other image the game names in its statics.

**Fighters' trees and lights.** Two pieces of a fighter's material setup (`ftMaterial_800BF2B8`) were read as the display pass left them at the frame's end, which the stage checks found (Onett's and Venom's frames; neither the oracle nor the earlier frames could see them, no earlier check having Mr. Game & Watch or a lit translucent fighter):

- A fighter's render callback (`ftDrawCommon_80080E18`) sets its draw flags before each tree it draws: in the camera's pass 1, a fighter with an outline model group (Mr. Game & Watch) draws the outline (`x2223_b2` set: its color as a tint stage, no depth update), itself (both clear) and its silhouette (`x2223_b2` and `x2223_b3`: no tint, color writes off, depth updated), and a later pass 0 clears `x2223_b3` again. melee-render read the frame's last flags (`x2223_b2` set, `x2223_b3` clear) for every tree, so Mr. Game & Watch's body drew as a second translucent gray outline instead of black, every frame he was on screen, in every match (Onett's frame 150: 128 draws a frame with an extra TEV stage, no depth update and the wrong blend, PSNR 27.4 dB). The pass now names the flags as his material sets up (`Draw::FighterFlags`), which also decides the shared-material swap (`x2228_b0`).
- A translucent fighter (or an outline) whose color overlay lights it sets its light up without alpha (`ftMaterial_800BF534`'s `ftCo_8009F75C(fp, false)`), sets its channels from those lights (`HSD_SetupRenderModeWithCustomPE`'s `HSD_SetupChannelMode`) and only then sets the light up again with alpha (`ftCo_8009F75C(fp, true)`). melee-sim named both light sets before the material, so melee-render's channels took the second set's masks and ambient: in Venom's frame 777, a lit fighter's draws took three lights for one in the color channel and lit alpha where the original's has it off (`XF 100E`, `1010`, and the ambient `100A`), 92 color components up to 255 levels apart, PSNR 67.1 and 72.2 dB; on Brinstar Depths from frame 3740 the second frame's 1,696 draws differed. The note melee-render made there ("a fighter's light overlay set up without alpha", over the whole oracle matches 404 times on Onett from frame 147, 8 on Venom from 774 and 780 on Brinstar Depths from 3740, and on no other stage's match) was this, and it changed pixels. The second set is now named after the render mode (`Draw::LightsAfterRenderMode`), and melee-sim's specular channel setup takes the first set, as the original's does.

melee-sim's own state doesn't change (the oracle's diffs of Onett, Venom and Brinstar Depths, `--fp hardware --heap`, compare every tick with no difference and no stale read, and `sync-test --rollback 7` passes on each). Mutation checks: reading the frame's last flags again fails `onett_150` (PSNR 27.4 and 27.4 dB) and `onett_2400` (29.0 and 29.4 dB); loading the second light set before the material fails `venom_777` (67.1 and 72.2 dB), `brinstar_depths_3743` (65.6 and 67.8 dB) and `onett_150` (identical images, 27 draws differing).

**Poké Floats' stars** twinkle in the original too: the sky's star layer (an I8 256 by 256 texture, among the frame's first stage draws) takes a TEV color that alternates frame by frame between (229, 203, 229) and (101, 75, 101), so a few stars show only every other frame. ssbm-rs's frames show them on and off the same way, and melee-hd's 90 frames from native frame 897 match ssbm-rs's star for star (frames 897 and 898 draw for draw, as `poke_floats_900` checks).

**Vertices behind the eye.** melee-gpu hands the GPU each vertex in clip space, made from its screen position snapped to the rasterizer's sixteenths of a pixel and multiplied back by w, so the GPU clips as the GameCube does. The snap rounded in integers (`iround`, as ssbm-render does), which saturate at 2^31 sixteenths, 134 million pixels; a vertex a hair behind the camera's plane lies farther out than that, so it moved in clip space, and the part of its triangle left in front of the camera could cover the screen at any depth. In ganon-captain-fd's tick 6279 a vertex of Final Destination's background lies 0.0004 behind the eye, at -5.5e8 and -7.6e8 pixels, and moved from (656.5, -1209.8) to (160, -194): the background's triangle covered the screen nearer than everything else, so the stage, the fighters, their shadows and the timer failed the depth test for the frame and only the background color and the HUD that doesn't test depth were left, at every scale, in every mode, every run. Other frames lost part of the scene the same way: drawn with the old snap against the new over whole matches, fox-fox-fd differs at 5 ticks (27 to 41 levels on average at 4427, 5493 and 5547), fox-marth-bf at 1 (and 4 by under a level), fox-marth-fd at 2, ics-peach-ps at 1 (Pokémon Stadium's background gone), and of five Slippi replays, Yoshi's Story's at 2 (its main platform gone) and Fountain of Dreams' at 1; fox-marth-ps and Dream Land's at none. melee-gpu now rounds in floats, which gives every position an `i32` holds bit for bit as before, and a vertex in the eye's plane (w = 0), which has no screen position, takes its direction. The frames checked against ssbm-rs's can't show it: ssbm-render rounds in integers too. Checks: `vertex_tests` (melee-gpu) puts tick 6279's vertex where its clip coordinates do and checks the float snap against the integer one; `tests/behind_the_eye.rs` (melee-render) draws tick 6279 with its 8 frames before and compares its brightness with tick 6278's (12.6 against 47.4 with the integer snap, 46.7 now). Mutation check: rounding in integers again fails both.

**Depth and early z.** The EFB's depth is 24-bit integers: the shader computes each pixel's from the depth the GPU rasterized (screen z through the viewport's z range and far z, truncated) and writes it, so every depth test compares what the GameCube's would. The rasterized depth itself can't stand in for it: the truncation isn't something interpolation reproduces, and comparing the floats would part from the integers wherever two depths share one. Writing depth from the shader keeps the GPU from testing depth before shading, though, so every hidden pixel would run the whole TEV shader. So the depth buffer (32-bit float) holds the integer z as (z + 1.5) / 2^24 below 2^23 - 1 and (z + 1) / 2^24 from there: exact and strictly increasing, so tests compare as the integers do, and never nearer than the rasterized depth it came from, with GXSetViewport's z range 0 to 1 (every viewport HSD sets), checked for every float depth from 0 to 1 with the multiply-add fused or not (`depth_tests`). Draws that test depth and write that depth (no z texture replaces or adds to it, or the z test comes before texturing) use pipelines whose fragment shader promises the GPU a depth no nearer than the rasterized one (`@early_depth_test(greater_equal)`, wgpu's `SHADER_EARLY_DEPTH_TEST`, Vulkan only), so it drops fragments that would fail the test before shading them; nothing else changes. Not with MSAA (each sample tests its own depth), nor on D3D12, nor with `MELEE_EARLY_Z=0`. Checked: the standard frames, and every frame of the six benchmark matches and a Fountain of Dreams replay at 1x, and their first 3,000 at 5x, hashed the same as main's (108,040 frames); a shader that broke the promise changed every frame, so the GPU does test early.

**Specialized shaders.** gx.wgsl's fragment shader reads every register it needs from the uniforms per pixel and loops over the TEV's stages, switching on each stage's inputs and indexing arrays by what the registers say; at 5x that work, per pixel, was nearly all of the GPU's time ([performance](performance.md#rendering-speed)). So each draw also has a shader specialized to its TEV configuration, after Dolphin's shader uids as melee-unlocked uses them (`melee_gpu::tev`). A draw's uid is its registers' configuration bits and its mode (draw or depth only): the stage count, each stage's texture order, inputs, operations, bias, scale, clamp and destinations, its indirect stage, its konstant selections, the swap tables it uses, the sampled maps' wrap modes, filters and diagonal lod, the indirect stages' maps, coordinates and scales, the alpha compare's functions and logic, the z texture's mode, fog's function, projection and range enable, the EFB format, dither, early z and destination alpha's enable. Everything else (colors, konstants, reference values, fog's constants, the indirect matrices, texture sizes and lod limits, lod bias) stays data in the uniforms. The shader for a uid is gx.wgsl itself with `bp` answering those bits as constants (a register that also holds data takes the rest from the uniforms) and the stage loop written out once per stage, so the GPU's compiler folds the branches, switches and array indexing away, and the texture coordinates and colors a configuration doesn't read with them. Every value it computes is the uber shader's from the same registers, by construction: the same code reading the same values. Floating point is the one place a compiler could still part them: with a register's branch folded away, a multiply before its merge could fuse with an add after it. Fog's depth was the one such place (a draw on Final Destination came out a level apart in a few pixels a frame), so gx.wgsl now subtracts fog's C behind an operation the compiler can't see through (`opaque`), which leaves the uber shader's output as it was.

A uid's pipeline is made on two threads of the renderer's own (wgpu's `Device` is shared across threads), those a frame's draws need first, and the uber shader draws until it's ready, so nothing changes meanwhile (`MELEE_TEV=sync` makes each as its first draw needs it, waiting, so every draw has its own: for checking; `MELEE_TEV=0` draws with the uber shader alone, as before; `MELEE_TEV_STATS=1` prints what they did when the renderer goes). The player keeps every specialized pipeline it asked for, each its pipeline key and uid, in `specialized-pipelines.bin` beside the other pipelines and makes them on those threads from the next run's start, through the driver's pipeline cache; the perf report says how many there were, how long they took and how many draw calls waited with the uber shader. Checked: random configurations with random data (`tev_tests`: 48 in the tests, 1,000 ignored), drawn with each shader, leave the EFB's color and depth bit for bit the same (without `opaque`, configuration 902 of the 1,000 came out a level apart); and every frame of the six benchmark matches and a Fountain of Dreams replay at 1x, and their first 3,000 at 5x, with every draw specialized hashed the same as with the uber shader alone, which hashed the same as main's (108,040 frames each).

### Checking frames

ssbm-rs records a run's GPU command stream as a Dolphin FIFO log, and its `gxplay` draws the log with ssbm-render:

```sh
GX_DFF=f600.dff GX_DFF_FRAMES=600,2 ssbm-run "$SSBM_DISC" --replay data/bench/fox-fox-fd.slp --fp hardware --port all --fields 640
gxplay f600.dff f600
```

`melee-render-check` plays the same replay natively, draws its frames through melee-render, and compares:

```sh
melee-render-check align "$SSBM_DISC" data/bench/fox-fox-fd.slp f600.dff 560 600      # which native frame the log starts at
melee-render-check compare "$SSBM_DISC" data/bench/fox-fox-fd.slp f600.dff f600 FRAME out/
```

`compare` lines the two streams up event by event and reports each draw whose raster or TEV registers (TEV stages and colors included), the transform unit's registers (channel colors and controls, viewport, projection, texture coordinate generation) and memory (its matrices and lights, read or not), sampled textures and palettes (by content: a palette's entries up to the highest one the image indexes), transformed vertices (screen positions, the colors of the channels in use, texture coordinates) or copies differ, exactly, with no tolerance, then compares the images with ssbm-rs's render tolerance: a PSNR of at least 38 dB, and at most 0.25% of the pixels off by more than 32 levels. It exits with failure when a frame is out of tolerance. The native match runs on the timeline the boot's audio setup starts (see [The boot](#audio)), so its scene loop renders on the same rounds as ssbm-rs's, and a log's frame N is native frame N - 3 from the first checked frame to the last (without the timeline, rounds that tick twice and render once came at other times, and the two drifted apart by 13 frames over a match). `compare` takes the native frame within 16 either way whose draws share the most exact vertices with the log's (`CHECK_SEARCH` changes the range). `CHECK_FP=slippi` plays a Slippi replay in Slippi Dolphin's float mode; `CHECK_EVENT=N` prints one event of each side in full; `CHECK_DIFFS=N` shows the first N differing events (20 by default, so a frame where a register differs in every draw shows only the first few and hides the rest: Fountain of Dreams' water's missing stage hid that way behind its stars' point size); `CHECK_DRAW_LIMIT=N` draws only the first N draws of melee-render's side, to find the draw where two images part (with `play`, of the log's); `CHECK_COMMANDS=1` keeps each event's preceding stream commands (BP, CP and XF writes, display list calls), which `CHECK_EVENT` prints and `CHECK_COMMANDS_OUT=DIR` writes for every event of both sides, a file a frame, to diff; `melee-render-check play LOG.dff OUT/` draws a log alone. A summary's box is in the EFB's coordinates, which start at the scissor offset (342), so a draw at y 700 is on screen at 358. The native match draws the eight frames before the first compared (`native::WARM_UP`), whose copies it may sample: the shadows and bubbles copy the frame before, but Pokémon Stadium's screen shows a copy of the screen showing the copy before, each smaller, and with only two frames drawn a few of its feed's pixels differed at frame 9000 (70.8 and 84.1 dB).

### Scaled frames

There's no reference above 1x, since ssbm-rs and Dolphin's software renderer draw at the console's size, so `melee-render-check scaled DISC REPLAY FRAME [OUT]` checks the scaled frames against melee-render's own frame at 1x, which `compare` checks against ssbm-rs's. It plays the replay once and draws native frame FRAME (and the two before it, whose copies it may sample) with six renderers of their own: the 640 by 480 frame copied to the XFB on the CPU, as `compare` draws it; the same copied on the GPU, as the player does; 2x and 3x at 640 by 480 (1280 by 960, 1920 by 1440); and at 3x the game's 73:60 (1752 wide) and 16:9 with the cameras widened (2560 wide). It compares the GPU copy with the CPU's (identical on every frame measured), 2x and 3x box-downsampled to 640 by 480 with the 1x GPU frame, and the 16:9 frame's middle 1752 columns with the 73:60 frame (at 3x both are whole pixels: widening keeps the pixels' size and adds 404 columns each side).

Pixel by pixel the scales differ a lot even when nothing is wrong: on frames ssbm-rs's check finds identical at 1x, 2x and 3x downsampled measure 27.6 to 34.3 dB, with 0.8% to 4.7% of the pixels off by 32, because edges are sampled nine times instead of once, textures at grazing angles take finer mip levels, the dither pattern scales, and copies to textures (shadows, the reflection, the bubbles) are drawn at the scale and averaged back. Those differences go both ways from pixel to pixel; a region drawn wrong doesn't. So the tolerance takes the mean difference of each block of 16 by 16 of the console's pixels, per channel, and allows at most 32 levels in the worst block, with a PSNR floor of 24 dB (`SCALED_BLOCK`, `SCALED_PSNR`). Measured on the 11 frames of every stage the standard set and the sweep check this way (and Fountain of Dreams' 6000 below), the worst blocks were 23.6 levels at 2x (Final Destination's edge and grid at a grazing angle), 13.3 at 3x and 11.7 for 16:9's middle against 73:60, and the PSNRs at least 27.7 dB (2x), 28.0 dB (3x) and 34.7 dB (16:9). One frame is beyond it for a known reason and recorded as it is: Fountain of Dreams' frame 6000, whose water shows the reflection, an 80 by 60 copy drawn at each scale and magnified over the water (worst block 49.2 levels at 2x and 32.4 at 3x; 40.3 and 28.6 before the water blended the reflection in as the original does, see **Compiled TEV**).

Mutation checks, each made by reverting a fix locally: reverting Fountain of Dreams' corner copies in melee-render (`fix(render): Send Fountain of Dreams' and Stadium's corner copies`) fails `sheik_fox_fod_600` (PSNR 29.6 dB against the recorded 40.9, and melee-render notes the erase color and reflection copy as not drawn exactly) and `scaled_fox_marth_ps_600` (worst block 48.6 levels for 16:9 against 73:60, at Stadium's screen), though Fountain of Dreams' scaled check passes, as that bug was the same at every scale; reverting melee-gpu's copy fix (`fix(gpu): Keep RGB565 copies on the GPU ...`) fails every scaled check, as the 73:60 EFB's readback rows aren't aligned.

The standard set checks Fountain of Dreams, Pokémon Stadium and Battlefield at frame 600 this way (`scaled_*` in `documented.rs`).

### The dashboard

`melee-render-check dashboard RESULTS_DIR OUT_DIR` writes a page of the checks' last results in `RESULTS_DIR` (`target/tmp/render-check-results` after the tests) to `OUT_DIR/index.html`, with the images beside it in `OUT_DIR/img/`: per stage, each check's frames, what they were compared with (ssbm-rs at 1x, or 1x for 2x, 3x and 16:9), PSNR, the shares off by 8 and 32, the worst block of a scaled check, and whether it passed, is a known difference (with the reason) or failed. Each comparison keeps three lossless PNGs at full size: the source (ssbm-rs's frame, or for a scaled check melee-render's own frame it's held against), melee-render's, and a third. Against ssbm-rs the third is their difference, `img/CHECK-FRAME-diff.png` (four times each pixel's largest channel difference, as ssbm-rs's ladder shows it; black when identical). For a scaled check it's a heatmap of what the check measures, `img/CHECK-FRAME-heat.png`: pixel by pixel a frame drawn at a higher resolution differs in detail the check means to tolerate (edges, finer mip levels, dither; in places it simply looks better), so a pixel difference mostly shows that. The dashboard draws the heatmap from the two recorded frames with the check's own block code (`block_means`): each block of 16 by 16 of the console's pixels is filled with its mean difference in its furthest channel, the quantity held against the 32-level limit, on inferno's dark-to-yellow ramp from 0 to 32 levels (near black for the few levels normal detail makes, orange and yellow nearing the limit) and cyan past it; the columns past the last whole block, which the check doesn't measure (24 at 3x 73:60), are transparent. The heatmap is the frames' size, so its blocks line up with the other two images, and the page and viewer show it over the source at 80% opacity, with a legend of the ramp and the limit; in the viewer the corner label names the block value under the pointer. An image several comparisons share (an identical frame's source and ours, a black difference or heatmap, a scaled check's 1x frame) is written once. Clicking an image opens a full-window viewer, as ssbm-rs's ladder had: 1, 2 and 3 (or its buttons) switch between the three, space flips the first two, and the view stays where it is, so differences stand out; the wheel or a pinch zooms at the pointer, Fit, 1:1, 2x and 4x set the size (pixels stay sharp from 1:1 up), dragging pans, a double click or double tap zooms in or fits, left and right step through the entries, and Escape closes. The page is published as a claude.ai artifact, so the folder keeps to 250 files and 60 MB: the images all go in when they fit, else the frames at the console's size first (each check's first frame before its others), then as many of the larger 3x 16:9 comparisons (about 4 MB each) as fit, those of checks not passing and then the standard set's first. On 2026-10-15 the standard set and the sweep (47 checks, 118 comparisons) made 175 files and 57.2 MB, six of the twelve 16:9 comparisons left without images (the heatmaps take 0.24 MB in all, where the scaled checks' pixel differences took 4.8 MB, room for one more 16:9 comparison); the PNGs are compressed with the png crate's strongest setting, the smaller of two filter choices, within a few percent of an optimizer's. `compare` and `scaled` write the measures and the images when `CHECK_RESULTS=DIR` is set (each check under `CHECK_ID`), and the tests write each check's status beside them; a check that ran earlier keeps its last result until it runs again.

### Resolution, aspect ratio and pipelines

**Resolution scaling.** melee-gpu is ssbm-render ported, with one addition: an EFB `scale` times the console's 480 lines tall, and as many pixels wide for the console's 640 as the frame is shown wide (`Renderer::with_device_efb`), so its pixels are square at the aspect ratio shown: 584 times the scale at the game's 73:60, 853⅓ (rounded to even) at 16:9, 640 at 4:3. Draws rasterize at the scaled size; EFB copies to textures (shadows, the magnifier's bubbles) average each block back to the console's size (a block's width is whole pixels from one console column's start to the next's), so the game's textures stay what it expects, and the copy to the XFB keeps the scaled size for the window, which only scales it uniformly. The dither pattern scales with it. `--scale N` sets it; by default it's the smallest whose 480 lines cover the window's height (3 for 1440p), and it follows the window as it's resized or made fullscreen. At scale 1 and 640 wide the output is ssbm-render's, which is what the frame checks compare: `melee-render-check` makes its renderer that way and draws the frames unwidened, so the aspect ratio doesn't reach the checks.

**Stage copies.** Fountain of Dreams renders its water's reflection through a camera onto the EFB's top left 80 by 60 pixels, in a white erase color (`Draw::EraseColor`), and copies that corner into the image the water shows with the copy's clear bit, which clears the corner's color and depth for the screen's pass (`grIzumi_801CCEA0`, `lb_800122C8`, `Draw::ReflectionCopy`); Pokémon Stadium's text screen does the same with 250 by 160 pixels, and its feeds copy the screen's frame without clearing (`Draw::ScreenCopy`). melee-render once sent none of these copies and erased those cameras as a magnifier bubble's (its corner colors, depth too), so at every scale, 1x included, the reflection's depth stayed in the corner and the screen's background lost to it there, a dark silhouette of the mirrored stage over the sky; Stadium's corner stayed black and its screen showed no text. It now sends each copy as `HSD_ImageDescCopyFromEFB` does, into images it keeps (`Dynamic::Reflection`, `Dynamic::Screen`) that the water's texture (the stage archive's descriptor, which the stage rewrites) and the screens' textures (`ImageRef::Screen`) sample. melee-gpu keeps RGB565 copies on the GPU like I4 and RGB5A3 ones, and masks copies' addresses to melee-render's 64 MB space, not 32 MB: masked to 32 MB, the copies it encoded on the CPU into those images landed on the loaded archives at 0x0180_0000 and changed their textures. `crates/melee-render/tests/corner_copies.rs` draws onto each corner and copies it, at 1x and at 3x at 73:60, and checks the corner comes out cleared. Against ssbm-rs's frames (`compare`, frame 600 of each), the reflection's draws and the water now match on Slippi replay Game_20260129T214216 (Sheik against Fox on Fountain of Dreams), whose frames then still differed in the stars' point size and the water's TEV, and the text screen's draws, copy and texture on fox-marth-ps, whose floor draws then still differed (see **Stage shadows**).

**MSAA.** `--msaa 4` draws with four samples a pixel: the draws go to a multisampled EFB (color and depth), resolved at the end of each pass into the EFB that copies to textures, readbacks and copies to the XFB read, so the game's textures and frames still come from one image. The TEV runs once a pixel, as before; triangles' edges are what it smooths. Off by default, where the output is unchanged. At 1440p it adds next to nothing to a frame (the GPU's work, inside presenting).

**Decision: frames are shown at the game's 73:60.** Melee's 640 by 480 picture isn't made for a 4:3 screen: on a GameCube and a CRT its 640 pixels fill less than the 4:3 width, and the game camera's perspective aspect is 1.2173333 (`lb_80013B14` widens descriptors' 1.18 to it; `DESC_ASPECT` in `game::camera`), about 0.913 of 4:3. Shown at a full 4:3, as the player first did, everything was about 9.5% too wide (4/3 ÷ 1.2173). The player shows the picture pillarboxed at 73:60 (`melee_render::frame::GAME_ASPECT`), the ratio Slippi Dolphin's "73:60" option uses (`Ratio /= (73.0f / 60.0f)` in Ishiiruka's `RenderBase.cpp`) and a whole-pixel 584 by 480 picture; the camera's 1.2173333 is 584.32 by 480, the same within 0.06% (a third of a console pixel across the screen). 73:60 is used rather than the camera's own number because it's the convention players know and compare against, and it gives the EFB a whole width (584 per scale) with square pixels. `--aspect 4:3` keeps the old look, the picture stretched to 4:3 as Dolphin's "Force 4:3" shows it.

**Decision: widescreen widens the drawn cameras, not the gameplay camera.** With `--widescreen` (16:9) or `--aspect W:H` wider than 73:60, each camera whose viewport covers the whole screen sees `aspect / (73/60)` times as wide at the same height (a perspective camera's aspect ratio, an orthographic or frustum camera's left and right about their center), and the frame is shown at that aspect ratio, so it has the target aspect with the proportions of the 73:60 picture: no stretch. The game camera, which the simulation runs and which decides who is off screen, stays as it is, so who is off screen is decided at 73:60, as Slippi's widescreen code keeps it (below); only the rendered view sees more of the stage. The HUD's orthographic cameras widen the same way, so the HUD keeps its shape and its place in the 73:60 middle, and the P1 to P4 tags, placed at the pixel their fighter is drawn at, stay over it. The background flash (a heavy hit's flash and the screen's fades and wipes, `lbbgflash.c`) isn't widened: its camera frames exactly its 640 by 480 quads, so widened it would leave the added sides untinted; unwidened, the quads stretch across the picture. The renderer knows the flash's camera by its owner, the camera GObj the flash records, not by its projection. Cameras that draw into textures (shadows, the magnifier's bubbles) are left alone. The render pass can't tell those apart by its offscreen flag, since the original leaves the frame in the shadows' offscreen pass, so the viewport decides.

**Measured.** A shield bubble is a sphere, so it should draw round. On the Battlefield Slippi replay Game_20260524T181118 at tick 6480 (Captain Falcon shielding, `--bench 6480 --scale 2 --shot`), measured in the saved frame, whose pixels are square as shown: the bubble is 140.4 pixels wide and 142.0 tall at 73:60 (1168 by 960, width over height 0.989) and the same at 16:9 (1706 by 960, 0.988), where before, at 4:3 (`--aspect 4:3`, the old look, 1280 by 960), it was 154.3 wide and 142.1 tall (1.086): 9.9% wider than at 73:60, against the 9.6% that 4/3 over 73/60 predicts. The old 16:9 showed that same 4:3 shape, widened and stretched alike. The edges are where the brightness falls halfway to the background; the lower rim lies over the lit floor, which moves that edge by a pixel or two with the threshold, so the absolute ratio is good to about 2% and the comparison between aspects, at the same threshold, to a fraction of a pixel.

**Decision: fighters in widescreen's added sides are drawn, as Slippi's widescreen code draws them.** The game draws a fighter only while its camera's view reaches it: a fighter whose camera box's bone is off the screen is marked off screen, and drawn only if the box's sphere, with a 15-unit margin, still reaches the screen (`ftLib_UpdateScreenVisibility`, [engine](engine.md#state-the-render-pass-writes)). So with the view widened, a fighter who flew into the added sides vanished there and only its magnifier bubble showed. Slippi's widescreen code (`Optional: Widescreen 16:9` in Slippi Dolphin's `GALE01r2.ini`) widens the game camera itself (`8036A4A8`), moves the off-screen test's left and right bounds in to 100 and 540 of the widened 640 (`80030C7C`, `80030C88`), the 73:60 view's edges within a pixel and a half, so the mark stays the game's, and draws every fighter so marked (`80086B24`, "Draw High Poly Models": the branch that returns "don't draw" made a nop), which GX clips past the screen's edge. melee-hd widens only the drawn view and keeps the game camera and the mark at 73:60 (above), so it needs only the last change, as a cosmetic toggle ([architecture](architecture.md#simulation-and-presentation)): `Cosmetic::draw_offscreen_fighters`, in the match's state, which the player turns on whenever its frames are widescreen (`Session::set_aspect`, as a match starts and when the aspect changes) and tools turn on as they need it (`melee-render-check`'s widescreen views, `melee-oracle sync-test --draw-offscreen-fighters`). Off, the match is the game's, exact against ssbm-rs; on, drawing a marked fighter writes what drawing writes, and its bubble still shows, as in Slippi. Extrapolate's prediction runs on a copy of the match, the toggle included, so it draws such a fighter too. melee-unlocked (GPL-3.0) does the same for its renderer-side widescreen (`apply_wide_fighter_draw`). Before, the player ran the display pass again on a copy of the state to keep the whole state identical at every aspect; Slippi's way is one instruction, proven online, and the test below shows that what it changes is display-only.

**Measured (2026-10-19).** `crates/melee-player/src/cosmetic_tests.rs` plays a match with the toggle off and on through the player's own tick and compares every tick: its sounds, rumble, events and mixed sound, and every difference in its state (`StateEq::state_diffs`). Over the six benchmark matches and five Slippi replays (Fox vs Sheik on Final Destination and Dream Land, Captain Falcon vs Sheik on Battlefield and Final Destination, Jigglypuff vs Sheik on Final Destination, the last five under the Slippi ruleset with its fixed-limit off-screen damage), the toggle drew a fighter more on 221 to 761 frames a match, and the output was the same every tick. The state differed only in the fighters' last-drawn model flags (`x2227_b7`, `x2228_b0`, from the first frame a marked fighter was drawn, ticks 1,167 to 4,670), joints' world matrices and dirty flags and texture matrices and flags (brought up to date by the traversal, from ticks 1,625 to 7,494), lights' shininess and a flag (a specular fighter material loads them, `HSD_SetupChannelMode`; all but the Fox ditto and the two Fox vs Sheik replays), and on the Jigglypuff replay, from tick 14,125 to its end, her hat's dynamic bones (their joints' rotations and dynamics links), which swing from the matrix the hat takes in the display pass ([engine](engine.md#state-the-render-pass-writes)). Never in anything gameplay reads: positions, velocities, action states, percents, hitboxes and hurtboxes, the random seed, items, the stage, the camera, the off-screen mark (`x221F_b0`, `x2188`), its count (`x1910`) or the magnifier; no particle spawned. The test keeps that list (`DISPLAY_ONLY`, and the hat's fields for a hat's joints only) and fails on any other difference; by default it plays Captain Falcon vs Ganondorf's benchmark match, and `COSMETIC_TEST_REPLAYS` plays others. Seen in `melee-render-check snap ... --aspect 16:9` and `--aspect 21:9`: Captain Falcon in the added right side at Captain Falcon vs Ganondorf's frame 4850 and in the left at 10150, and Fox in the right at Fox vs Marth on Battlefield's 5565, each beside his bubble, where before only the bubble (and Captain Falcon's P2 tag) showed.

**Decision: pipelines are kept by what they're made for, after Aurora's design.** The uber shader runs the TEV for every draw, so its pipelines differ only in blending, color and alpha writes, the depth test and whether the depth test may run early. The player records every pipeline key it has needed in `%LOCALAPPDATA%\melee-hd\pipelines.bin` (`$XDG_CACHE_HOME/melee-hd` elsewhere) and makes them all before the first frame of the next run, with the driver's own pipeline cache (wgpu's `PipelineCache`, where the backend has one) kept beside it. A frame never waits on a pipeline the player has made before. The pipelines with specialized shaders (see [Rendering](#rendering)) are kept the same way, with their TEV configurations, in `specialized-pipelines.bin`, and made on the renderer's shader threads instead, the uber shader drawing until each is ready.

### Slippi's name plates

**Decision: melee-hd's VS draws no name plates.** Slippi's playback draws each player's Slippi Online display name under the damage counters: an optional code of its playback set, on by default (`Optional: Show Player Names`, a `C2` code at `0x8016E9B4` after the VS scene's entry, `Playback/Show Player Names/InitInGame.asm`, which "shows players' Slippi Online display names as HUD elements when available"). It's a replay viewer's feature: the names come from an online replay's start, and the code makes a GObj of its own with a joint from a HUD archive and the names' text, objects the game doesn't have, so it isn't part of the Slippi ruleset a match plays (slippi-ssbm-asm keeps it under `Playback/`, not `Online/`), and a local VS has no display names to show. The oracle's traces leave it off (`SLIPPI_PLAYER_NAMES=0`); the one reference made with it on (Fox vs Sheik and Zelda's) stays as it is, its plates the only difference (35 or 36 draws, `Expect::Known`). Should melee-hd play replays back or play online with accounts (the netplay follow-on), the presentation can draw the plates from the replay's or the session's names without touching the simulation, as an overlay of its own.

## Audio

The simulation keeps the audio driver's voices, both copies of their parameter blocks, the sound banks' places in ARAM, the music stream and a DSP model that walks each voice through its samples (`docs/engine.md`). What it doesn't do is decode and mix the samples: that is `melee-audio`'s.

**The mix log** (`melee_sim::audio::mix`, `Audio::mix`) is the simulation's only addition, and it is presentation output: `None` unless the presentation turns it on, never read by simulated code, left alone by a rollback restore and empty in a clone. Each audio frame, right after `__AXSyncPBs`, where ssbm-rs's DSP stand-in runs the command list, it records a `MixFrame`: the DSP's 64 parameter blocks, each voice's sync flags, the voices whose depop the sync adds to the studio's sums (`__AXDepopVoice`, from a depop flag or a drop for the DSP's budget), the command list's mode and aux mixes as `__AXNextFrame` built it at the frame before, and the aux callbacks as `__AXProcessAux` finds them. Every write into ARAM is recorded as it completes (`AramWrite`, placed before the frame it precedes): a disc file's bytes from the device command queue (sound bank samples, music boxes), ARAM to ARAM (a bank's groups moved down), zeros, and each bank group again in whole when its load finishes. The presentation empties the log as it mixes; its vectors keep their storage, so recording allocates nothing once warmed up.

**The mixer** (`melee_audio::Mixer`) keeps a 16 MB ARAM image: the boot state's bank groups (each group's samples come from its `.ssm` file after the header: the file's first word plus 0x10, rounded up to 32 bytes), then the log's writes in order. Each frame it puts the frame's blocks, the studio (the depop sums faded as `__AXPrintStudio` does) and the command list in a small stand-in for main memory and runs the AX microcode (`melee_ax`, ported from ssbm-rs's `ssbm_ax`) over it. The words that depend on the samples' values (the ADPCM predictor and history, the resampler's last samples, the buses' last samples) come from the mixer's own last output for that voice unless the frame's sync flags say the CPU just wrote them (a new sound). The rest comes from the simulation, and the mixer counts any voice where the two disagree with no CPU write (`Stats::drift`; none so far). It then runs the aux effects, as the CPU's `__AXProcessAux` does, on the triple-buffered aux buses: the DSP sends a frame's aux mix, the CPU's effect processes it the next frame, and the DSP mixes the result back the frame after. Melee's boot sets up AXFX's standard reverb on aux A and its delay on aux B (`lbAudioAx_8002838C`), and a match uses both. Both are ported (`melee_audio::fx`): the reverb's float math follows the original's instructions through `gekko_fp`, and its comb filters' feedback comes from the game's own `powf`, as the original links it. The mixer makes them as that setup does (`AXFXReverbStdInit`, `AXFXDelayInit`, with the types the driver recorded), or, given a boot state's memory, takes their state, delay lines included, the depop sums, the surround buffer and the aux buffers from it. Each frame gives 160 stereo samples at 32 kHz, as the audio interface plays them.

**Output** (`melee_audio::Output`) plays them on the default device. The game loop pushes each tick's samples into a lock-free ring and never waits; the device's callback resamples them to the device's rate. On Windows the output talks to WASAPI directly (`output/wasapi.rs`): shared, it asks the audio engine for its smallest period (`IAudioClient3::InitializeSharedAudioStream`, 128 samples, 2.67 ms, on Sarah's PC; else the engine's current period if another program holds it, else the standard 10 ms) and keeps two periods queued on the device, from a thread in the multimedia scheduler's "Pro Audio" class; with `--audio-exclusive` it takes the device itself in WASAPI's exclusive mode at its smallest period, in a format the device plays natively (24-bit here), which saves the engine's mixing and its period: the lowest latency the device has, but no other program's sound plays while the match does, and if another program holds the device exclusively, or Windows' "allow applications to take exclusive control" is off, the output shares it instead. Elsewhere, and if WASAPI fails, it goes through cpal, shared, with buffers of about 5 ms where the device allows them.

**Decision: the audio queue is as short as stays glitch-free.** A tick pushes 16.7 ms of samples at once, so the ring rises and falls by that much between ticks, and a tick's first sample waits as long as the ring is full at its lowest, just before the push. The callback measures, each quarter second, the least slack it found (what the ring held beyond what the callback took) and nudges the rate by up to 0.5% so that slack comes to one more callback's samples plus a 2 ms margin: a tick that arrives a callback later still finds samples. Running dry anyway (an underrun, a gap) adds a millisecond to the margin, unless the dry spell lasted more than two ticks (a stall no margin covers: the first frame's pipelines, a dragged window), and a minute without one takes a millisecond back; a stall's catch-up beyond two ticks is dropped rather than played late for seconds. The game's ticks bring a little more than 32 kHz (the console's 59.94 frames a second come 60 times), so the slack settles a fraction of a millisecond above its target, on the safe side. The mix itself is untouched: it's the same samples, and the mix checks don't use the output. Before this, the ring aimed at 40 ms and sat at about 85 ms (the start's stall filled it, and a 0.5% nudge drains 40 ms in 8 s), behind cpal's 32 ms of device queue.

**The boot.** Voices need the boot's audio state: the sound bank, the banks every scene keeps, and the timeline the audio frames run on. melee-sim's match start runs the boot's audio setup (`game::boot`, [the engine notes](engine.md)), so a match from its settings or a replay plays sound from its first tick, with nothing from ssbm-rs. The player turns the mix log on before that setup runs (`Match::start_from`'s `boot`, which runs first), so the mixer sees the boot's own ARAM writes (the cleared silence, the banks' samples) and frames (silent ones, the effects running over them) and starts the effects new. A replay's start also plays the sound Slippi's playback scene does.

### Checking the mix

ssbm-rs records what its audio interface plays (`AUDIO_OUT`) and the boot state in the same run:

```sh
SLIPPI_PLAYER_NAMES=0 STATE_TRACE=audio-fox-fox-fd.trc STATE_TRACE_MEMORY=0..600 AUDIO_OUT=audio-fox-fox-fd.wav \
  ssbm-run "$SSBM_DISC" --replay data/bench/fox-fox-fd.slp --fp hardware --port all --fields 2400
melee-audio-check audio-fox-fox-fd.trc data/bench/fox-fox-fd.slp audio-fox-fox-fd.wav --fp hardware --ticks 2500
```

`melee-audio-check` plays the replay natively from the trace's boot state (`tools/audio-check/src/boot.rs` reuses `tools/oracle`'s trace reader and seeding), mixes it, and aligns the two streams: an exact match of 1024 samples if there is one, else cross-correlation. ssbm-rs's recording starts at power-on, and the native mix starts at the boot state, 4000 samples (25 frames) later. It then reports each window's SNR, largest difference and share of equal stereo samples, and the first sample that differs. On the Fox ditto on Final Destination (39.9 s compared) and Fox against Marth on Battlefield (59.9 s compared), the mix is sample-exact from the match's start to the recording's end, reverb and delay included: both effects processed sound in about 86% of the frames. The trace's game files that the fighters cache in ARAM (`PlFxAJ.dat`, `PlMsAJ.dat`) aren't sound and aren't in the device command queue's files, so the mixer skips them. On this machine mixing takes about 0.22 ms a tick.

With `--port` (and `-` for the trace) `melee-audio-check` doesn't read the trace: the match starts as the player starts one, from melee-sim's boot, and the mix covers the boot's frames too. Against the same recordings it is sample-exact from the native mix's first sample (the AX library's first frame, which lines up with the recording's sample 320) to the end: 40.0 s of the Fox ditto and 60.0 s of Fox against Marth.

`melee-audio-check --out MIX.wav` writes the native mix, and the check reports how often the music stream moved on to its next box and when it last did: a song that stopped stops moving.

**Decision: the player reads the disc at a drive's pace, unlike the replay checks.** The disc's speed is a match setting (`Settings::disc`, [the engine notes](engine.md)): at Slippi's fast disc speed, which ssbm-rs's traces and recordings of replays use and so every replay check keeps, about half of all songs stop 1.8 s in, in ssbm-rs's runs as in melee-sim's, because the stream's start and its addresses reach the DSP in one audio frame. ssbm-rs's window reads at a drive's pace, 3 MB/s on top of each read's latency (its `1fb4da3`), and the player does the same, for its own matches and replays alike; `--disc-speed fast` takes the fast speed. `melee-audio-check --disc-speed drive` checks that pace against ssbm-rs's runs with `DISC_RATE=3000000`:

```sh
SLIPPI_PLAYER_NAMES=0 DISC_RATE=3000000 STATE_TRACE=local/player/audio-drive-fox-marth-fd.trc STATE_TRACE_MEMORY=1 \
  AUDIO_OUT=local/player/audio-drive-fox-marth-fd.wav ssbm-run "$SSBM_DISC" --replay local/bench/fox-marth-fd.slp --fp hardware --port all --fields 4500
melee-audio-check - fox-marth-fd.slp audio-drive-fox-marth-fd.wav --port --fp hardware --disc-speed drive --ticks 4200 --out mix.wav
```

On Fox against Marth on Final Destination, whose song stops at the fast speed (the stream last moves in tick 109; the mix is sample-exact with ssbm-rs's fast recording for 66.7 s, song gone in both), the drive's mix is sample-exact with ssbm-rs's recording at that pace from the native mix's first sample to the recording's end, 75.0 s from melee-sim's boot (72.1 s from the trace's boot state), and the song plays throughout: the stream moves to a new box 42 times, the last in tick 4187, and the mix is about half again as loud in every 10 s of the match's first minute. Fox against Marth on Battlefield, whose song plays at either speed, is sample-exact for 75.0 s at a drive's pace too. A match from the player's own settings behaves the same: Fox against Marth on Final Destination lost its song at tick 109 at the fast speed for every seed tried, and keeps it at a drive's pace.

## Input

`melee_input::Inputs::read` returns the four ports' `PADStatus` just before each tick. GameCube controllers on a Wii U adapter (or a copy, such as Mayflash's in Wii U mode) take their own ports. The adapter is read raw over USB with nusb, as Dolphin's GCAdapter reads it, not through SDL, which rescales the axes; on Windows it needs the WinUSB driver (Zadig installs it). A thread keeps the latest report and sends rumble, and each read turns the report into what `PADRead` returns, with the origin calibration the console's SI and PAD library do (ported from ssbm-rs's player). Standard gamepads (gilrs) and then the keyboard take the first ports left. The keyboard: arrows for the stick, IJKL for the C-stick, X, Z, C and S for A, B, X and Y, D for Z, Q and W for L and R, Enter for start, and left shift to halve the stick. `--no-adapter` leaves the adapter alone.

## The player

```sh
melee-hd                                               # the launcher: pick the match in the window
melee-hd --p1 fox --p2 marth --stage bf [--stocks 4] [--minutes 8] [--widescreen | --aspect 21:9 | --aspect 4:3] [--scale N] [--msaa 4] [--size 1920x1440] [--fullscreen] [--disc-speed drive|fast]
melee-hd --replay data/bench/fox-fox-fd.slp            # a replay's match, its inputs played back
melee-hd --bench 1200 --size 2560x1440                 # headless, timing each frame
melee-hd --launcher-shot launcher.png [--size WxH]     # draws the launcher to a PNG, no window
melee-hd ... [--latency-log FILE.csv] [--latency-overlay] [--present mailbox|fifo|immediate] [--added-delay N] [--audio-exclusive] [--mute]
melee-hd ... [--no-record] [--replays DIR]               # each match saved as a Slippi replay, in DIR or replays beside the program (see Recording below)
melee-hd ... [--high-refresh off|interpolate|extrapolate]  # frames between ticks for faster displays
melee-hd ... [--tick-timing timer|auto|refresh|vrr] [--jit-margin MS]  # when ticks start (the fixed timer by default; just in time is experimental)
melee-hd ... --flicker-scan                            # captures a frame that drops out for one presented frame (see Flicker scan below)
melee-hd --bench 1800 --high-refresh interpolate|extrapolate [--frames-per-tick 4]
```

Characters and stages are what melee-sim has ported: its `game::roster` lists them (the characters by `CharacterKind`, the stages by `StKind`, with their command-line names), a new port adds its line there, and the command line, `--help` and the launcher all read that list; a stage is offered only once its audit finds nothing a match on it reaches unported ([Stages the player offers](#stages-the-player-offers)). `--help` prints the names. The match runs at 60 ticks a second.

**The launcher.** With no `--p1` to `--p4`, `--stage` or `--replay` (and no `--bench`), the window opens on a small form: a character or none for each port (at least two players), each human or a CPU at a level from 1 to 9 (of those [offered](#cpu-players-the-player-offers)), the stage (of those [offered](#stages-the-player-offers)), stocks (0 for a timed match) and minutes (0 for no time limit), the items (the frequency and the item switch, of the kinds [offered](#items-the-player-offers)), the aspect ratio (the game's 73:60, 16:9, 16:10 or 21:9 widened, or 4:3 stretched), a fullscreen box, the present mode and the added delay (see [Latency](#latency)), High refresh (see [High refresh rates](#high-refresh-rates)), Tick timing and Timing margin (see [Just-in-time ticks](#just-in-time-ticks)), and Save replays with the Replays folder (see [Recording](#recording)). Start (or Enter) plays the match in the same window; Escape in the match, or the match's end, comes back to the form, and Escape on the form quits. The other options (`--stocks`, `--minutes`, `--widescreen`, `--aspect`, `--scale`, `--msaa`, `--fullscreen` and the rest) still apply. The form opens with the choices of the last match started from it, which the settings folder keeps (`last-match.txt`, see [Playing it](#playing-it)); `--stocks`, `--minutes`, `--widescreen`, `--aspect`, `--fullscreen`, `--present`, `--added-delay`, `--high-refresh`, `--tick-timing`, `--jit-margin`, `--no-record` and `--replays` win over those, and without a readable file the form starts from the command line's values. A match the command line names plays as before, and Escape quits it. A repeated character takes the next costume, as the command line's default Fox ditto does.

**The match's rules.** A match from the launcher or the command line starts the way the VS mode starts one (`gmVsMelee_EnterVs`, in `game::gm::vs_mode`): the VS mode's start data with what the character select sets for each player, and the VS menus' rules of a new save (pausing on, friendly fire off, damage ratio 1.0) with the chosen stocks and minutes, and the launcher's items as the Item Switch screen would set them ([Items the player offers](#items-the-player-offers); the command line's matches have items off). Those rules also decide what the HUD shows: a start data filled in by hand without them draws no damage or stock display. `melee-oracle`'s `vs_rules` test compares the setup with the start data the benchmark replays recorded.

**Decision: a match with an Ice Climber runs the allocator model, laid out as a console's VS match from the menus.** The model of the original's allocators (`Settings::heap`, [the allocators](engine.md#the-allocators)) is off in the player's own matches, where no address reaches gameplay and it would only cost time. **Decision: the player's own matches unlock everything until melee-hd has its own saves.** `Settings::vs_with` sets the unlocks Slippi Dolphin's unlock-all codes give (`Unlocks::slippi`), not a save's, and keeps them until native saves (milestone 5); from then the save's unlocks decide. The coordinator's call. **Fullscreen.** F11 or Alt+Enter toggles borderless fullscreen on the window's current monitor (winit's `Fullscreen::Borderless`), in a match or on the launcher; `--fullscreen` starts that way, and the launcher's box does the same. The window keeps the frame's aspect ratio, letterboxed or pillarboxed, whether resized or fullscreen, and without `--scale` the internal resolution follows the window's size: at the next frame after a resize that changes the scale the renderer's EFB is made again at the smallest scale whose 480 lines cover the new height (5 on a 2160-line display), in place (`Renderer::resize_efb`, through `melee_render::gpu::Gpu::resize_efb`; on the renderer's own thread when it has one, in its turn). Only what the EFB's size decides is replaced: the EFB, its depth target and its multisampled target with MSAA, and the bind groups of the copies that read it, to textures and to the XFB (whose frame textures are made at each copy's size anyway). The copies to textures made from the old EFB are dropped, with the bind groups naming them and what they wrote, since their texels are its pixels averaged; the next copies come from the new EFB, as a new renderer's would. The new EFB is cleared with the GPU's state, as the last frame's copy to the XFB left the old one. Everything else stays: the renderer and its threads, the decoded textures, the pipelines (the sample count doesn't change with the window; a different one would need new pipelines), the copy and XFB pipelines, samplers and buffers, and the GPU's registers and texture memory, which the frames after need as they are: the stream sets much of that state once, at the match's first frame (`GXInit`'s setup), or only when it changes (HSD's state cache skips a write that matches what it last set). A renderer that started from a fresh state drew with color writes off until a new match, a black frame with only the odd particle drawn. **Cost**, measured with `--bench 1000 --size 1460x1200 --resize-at 300:2880x2160 --resize-at 500:1460x1200 --resize-at 700:1280x960 --resize-at 900:3840x2160` on fox-fox-fd (other agents' builds running, so the numbers are noisy): making the whole renderer again, as the player did before, took 41 to 62 ms on the game's thread (its pipelines remade and warmed 29 to 54 ms, saved 3 to 5, the old renderer dropped 2 to 13, its threads stopped 1 to 4), and the frame after spent 25 to 33 ms in the renderer re-uploading every texture against about 8 normally: 70 to 103 ms for the resize's frame. In place, the resize takes 0.5 to 1.3 ms (new targets about 0.5, the leftover draws flushed about 0.1, the bind groups 0.02 to 0.09), except the first time in a run the EFB grows to a size the driver hasn't had memory for, when making the 5x targets (about 56 MB) took 6.6 to 7.8 ms; the resize's frame takes about what the frames beside it take, a few ms more on that first growth. The frames after a resize are the frames a renderer made at the new scale from the match's start draws, pixel for pixel: `--bench` with `--resize-at TICK:WxH` (repeatable) changes the offscreen target's size before that tick, as a window resized or made fullscreen does, and reports the resize's frame with its parts and the frames beside it; `crates/melee-player/tests/resize.rs` checks it going up (3x to 5x, threaded), through a 4K fullscreen and back (3x, 5x, 2x, on one thread), and with MSAA (2x to 5x).

**Resolution.** The launcher's Resolution box picks the internal resolution: Auto follows the window (the smallest scale whose 480 lines cover its height, as without `--scale`), or a fixed scale up to the most the aspect's EFB allows, each shown with its EFB size; Antialiasing turns on 4x MSAA (`--msaa 4`). Both are kept with the last match's choices, `--scale` and `--msaa` win over them, and the match starts at the chosen scale instead of resizing at its first frame.

**Bug capture.** F12 in a match saves the next frame drawn to `captures/<milliseconds since 1970>` beside the executable (`crate::capture`): `shown.png`, the frame as shown; `fresh.png`, the same draws drawn again from the same state by a new frame builder and renderer on the game's thread, with the same blend between ticks; `fresh-unblended.png`, that again without the blend; `live-stream.png`, the player's own stream for the frame run by a new renderer from the GPU's registers as the frame found them (broken: the registers or the stream are wrong; whole: the player's renderer, its depth, textures or caches); `registers.txt`, every GPU register whose value after the frame differs from the new frame builder's and renderer's after the same draws (texture and vertex array addresses always differ: the address space places archives in the order frames first use them), with both frame builders' HSD state caches; and `info.txt`, the high-refresh mode, the tick, the blend's t, the scale, MSAA, aspect, and the frame builder's notes. A glitch in `shown.png` that `fresh.png` doesn't have lives in what the player keeps from frame to frame (the frame builder's state caches, the GPU's registers, the renderer's textures and depth); one both have lives in the draws, the state they read, or the blend. It was made to catch an intermittent glitch, the world but the background color and HUD disappearing for a moment or for seconds, seen with high refresh at 5x on Sarah's NVIDIA card (2026-10-17). The captures showed the stream, the registers and the renderer's state all sound, and the glitch only while the GPU ran frames behind (any mode once the GPU couldn't keep up: Off at 8x too; never with a wait for the GPU each frame, and never headless, where nothing presents). Reading the EFB's depth back after the broken frames found it all exactly the clear rectangle's vertex depth (0.5) instead of the clear's depth, which the shader writes: the same draw, pipeline and uniforms, with the shader's depth sometimes not taken, on Vulkan and D3D12 alike, with no hazard under Vulkan's synchronization validation. The clear's rectangle now lies at the clear's depth itself (`Renderer::push_rect`), so its depth is right whichever the GPU takes; the same hidden-desktop run that broke 8 to 18 sampled frames a minute breaks none. The clears are now made by the EFB render pass's load operation instead, with nothing drawn, wherever that leaves the EFB as the rectangle would, bit for bit: every clear of a match, since each covers all of the EFB drawn since the last and the rest already holds its values (the copy to the XFB clears 640 by 480 of the 640 by 528 EFB). The rectangle is left for a clear of part of the EFB whose rest holds other values, of alpha alone, or keeping alpha after something drew alpha (`Renderer::clear`). A new renderer's EFB is cleared as `GXInit` sets the copy's clear up, depth included: cleared with a state that hadn't seen `GXInit` yet, its depth stayed as made, all nearest, and a fresh renderer's first frame drew only what doesn't test depth (the background and HUD).

**Flicker scan.** `--flicker-scan` catches what F12 is too slow for: a frame that drops out for a single presented frame (`crate::flicker`; the idea and the neighbour test follow melee-unlocked's `--flicker-scan`, GPL-2.0-or-later). Each image the swap chain is about to present (before the F3 overlay) is copied into a ring of six on the GPU (the swap chain is made copyable for it; where it can't be, the frame is drawn into the ring again) and reduced there to a 64 by 64 grid of mean luminance over the picture's rectangle (up to 16 by 16 pixels sampled a cell), read back through a buffer mapped a frame or two later: the frame loop never waits for the GPU, and a frame finding all eight readbacks busy goes unscanned (and the frames beside it unjudged). A frame is a hit when it differs from both neighbours by at least 8 (the mean of its cells' differences, luminance 0 to 255) and by at least twice what they differ from each other, its detail (adjacent cells' mean difference) is at most half the lesser of theirs, and it's no more than 24 brighter than the brighter of them: the world gone, leaving the clear color and the HUD, which motion, camera cuts, fades and flashes don't do. Each hit logs a line with the measures (at most one a second; the rest are counted into the next line), and saves `captures/<milliseconds since 1970>-flicker`, at most one every 30 seconds and ten a run: `grid-1-before.png`, `grid-2-bad.png` and `grid-3-after.png` (the grids, 4 pixels a cell), `1-before.png`, `2-bad.png` and `3-after.png` (the presented images from the ring, at the window's size), `flicker.txt` (the measures, the rule, and each frame's number, tick, blend t and draw count), and `after/`, F12's capture of the next frame drawn, which shows the player's state a few frames after the bad one (it stalls the game for a few seconds at 5x, hence the long gap). `MELEE_HD_FLICKER_TEST=N`, with `--flicker-scan`, blanks every Nth presented frame to try it out. Without the flag nothing of it is made or run. **Measured** on the hidden desktop (a 1920 by 1080 window at scale 5, 16:9, Interpolate, mailbox at 144 Hz, Roy against Ganondorf on Great Bay, other agents' builds running): two off and on pairs drew 79.8 and 82.8 frames a second, and 105.2 and 107.5; at 3840 by 2160, 115.6 and 111.2, and 112.5 and 112.6: within the noise, a few percent at most at 4K. Normal play gave no false hits in 2,000 ticks of that match, the Fox-Marth Pokémon Stadium benchmark replay (7,000 ticks, Interpolate), and the Ganondorf-Captain Falcon Final Destination and Fox-Marth Battlefield ones (9,000 ticks each, Off). In the first three, the frames passing the neighbour test kept 0.93 to 2.8 times their neighbours' detail, and melee-unlocked's whole-frame thresholds (1.5 and 1.25) would have reported 46 frames in the Pokémon Stadium replay and 139 in the Final Destination one. Blanking every 300th frame gave 14 hits in 2,400 ticks, two captured 33 seconds apart and the rest logged as rate-limited. The scan's one real hit is at tick 6279 of the Final Destination replay, in Off: the stage, the fighters and the timer gone, the clear color, stock icons and damage left (detail 1.5 against 8.1 and 7.9), with the frames before and after whole. It's the same frame every run, and headless too (`--replay data/bench/ganon-captain-fd.slp --bench 6279 --shot F.png` shows it at scale 2), so unlike the GPU-timing glitch under Bug capture above, it lives in the draws or the state they read.

**Decision: the launcher is egui, drawn on the player's own device and window.** egui 0.36 (`egui-wgpu` for wgpu 30, `egui-winit` for winit 0.30) draws the form with the window's swap chain format into the surface the frames use, and takes the window's events through egui-winit; nothing is drawn with it while a match plays, so a match's frames and audio are what they were (the frame and audio checks don't run the player and are unchanged). It's a tool for manual testing, plain on purpose, and the seed of the menus and settings screen to come. `--launcher-shot` draws the same form offscreen, for looking at it without a window.

**Decision: the player minimizes latency rather than matching a CRT's.** Sarah's call: players' displays differ, so the player can't ensure a CRT's timings from software anyway, and the least latency leaves the most headroom to spend again, on netplay's input buffer above all. A player who wants a CRT's or a console's feel locally adds latency back on purpose (`--added-delay`, "backfill", below); the default is the least the player can do. The player is cross-platform: the loop and the measures are portable, and OS-specific tuning (WASAPI's low-latency and exclusive modes) sits behind `cfg(windows)` with a portable fallback (cpal).

**The loop.** Each tick reads the controllers immediately before it runs, and the frame it produces is turned into GX commands, drawn and presented at once; the swap chain is one frame deep (`desired_maximum_frame_latency` 1). Ticks keep Melee's 60 a second on a fixed timer, or with the experimental `--tick-timing` policies each starts just in time for the refresh that will show its frame, waited for precisely (see [Just-in-time ticks](#just-in-time-ticks)); after a stall of more than four ticks the loop drops the backlog instead of racing to catch up. The adapter's thread reads it at its full rate and the tick takes its newest report. Nothing waits on audio: the tick pushes its samples into the output's ring.

`--bench` plays a match headless, draws every frame and presents it to an offscreen target of `--size`, and reports the time per tick for the simulation, the GX stream, the renderer and presenting, and the median, 99th percentile and worst of a frame's ticks and drawing (the simulation, the GX stream and the renderer), with and without presenting. `--one-thread` keeps the renderer on the game's thread. `--resize-at TICK:WxH` resizes the target before that tick, the renderer following as it follows a window (see Fullscreen above).

### Stages the player offers

**Decision: the launcher and the command line offer a stage only once nothing a match on it can reach stops the match.** Sarah's call (2026-10-20): a stage plays its oracle match when its port lands, but a match from the player can go where that match didn't (a fighter falling into Kongo Jungle's barrel stopped the game), so the roster says separately whether a stage is complete. ### Items the player offers

**Decision: the launcher offers an item kind only once nothing a match with it can reach stops the match.** Sarah's rule for stages (2026-10-20), applied to items as she asked: the player offers only what nothing a match can reach can stop. The launcher's Items box sets the item frequency (Off, then the game's Very low to Very high) and its Item switch the kinds, a box each, as VS mode's Item Switch screen does. It starts off, with the switch all on as a new save has it, and the last match's choice comes back (`items` and `item-switch-off` in `last-match.txt`). A kind is offered when the items audit (`items_audit::missing_with_switch`, [below](#items-toggle-whats-left)) finds no gap an items-on match with it reaches for the chosen stage and characters (`crate::items::status`). A kind that isn't offered is shown off and disabled with a short reason: "not ported yet" for a gap every match reaches, "not with Kirby" or "not on Yoshi's Story" for one only a chosen character or stage reaches; hovering over it shows the gap. A kind the chosen characters or stage turn off is off for that match, the user's switch keeps it for the next, and the form says so under Start. With no kind left, or the switch all off, the match has items off, so the launcher never starts a match that its items can stop. The command line's matches (`--p1` to `--p4`, `--stage`) have items off.

**The containers.** The Item Switch screen's 32 entries (`lbl_803B7844`, one with no kind) list every random kind but the capsule, box, barrel and egg (kinds 0 to 3), which `gm_80167BC8` leaves on as the rules' defaults set them. **What's offered (2026-10-21, `main` at `b3a5321b`): nothing.** A box or barrel rolls a crate monster one time in 128 (the audit's task 5, being ported on `feat/monsters`), and a catch box can touch one (`updateItemGrabTarget`, `it_8027B4A4`); both gaps come with the box and barrel, so every items-on match reaches them, and the launcher shows every kind "not ported yet". ### Characters: what's left in their own items

This audit (2026-10-21, from `main` at `015e36da`) says what a plain items-off VS match from the player can reach in the items characters make themselves (projectiles, held items, and the copies' items under Kirby's hat) that isn't ported or can stop the match. Its machine-readable form is `melee_sim::game::fighter_audit`: an entry per roster character, keyed by its `CharacterKind`, with the item kinds its own moves make, what of them no match reaches (with why), what is unsure, and the gaps a match does reach (`fighter_audit::missing_with`). The items audit leaves the characters' items' units and modules to it.

**Method.** Each character's item kinds come from the decompilation's `ItemKind` list and the moves that spawn them (kinds 48 to 157 but Kirby's spit star, which only an inhaled item becomes, and Master Hand's and Crazy Hand's). The units and modules follow from the item tables (`it::tables`, transcribed from `it_803F3100`): a kind's units are the ledger's units of the callbacks in its logic and state tables, its modules those whose code dispatches on them. Every unaccounted function of those units is then ported awaiting a check (a `// Ports` comment, or code dispatching on its address), a kind's `evt_unk` (which only `it_8026B7F8` calls, at a fighter's unload when the scene ends), or named in the entry; every callback in the kinds' tables is dispatched or named, since an address nothing dispatches stops the match (`code::run_pred`'s and `run_proc`'s refusal); and every stop in the modules is named.

**What it found.** The items audit's 195 fighter-owned rows were almost all ported code waiting for an alias, not stops: every callback of every character's item kinds is dispatched but Ness's bat's second state's three, and each kind's `evt_unk`. What can stop a match:

- **Reachable, 1, since modeled:** Samus's grapple beam swung on the ground (A pressed while the beam's hitbox stage is on) as its links fall back (`it_802B99A0`) or hang (`it_802B9CE8`), or from the shot without the tip's matrix rebuilt. The swing copies its hitbox's grabbed-victim-only bit from a byte of its caller's frame that nothing sets ([the engine notes](engine.md#uninitialized-values)); the port modeled only the shot's frame, where `PSMTXConcat`'s save of `f14` (0.0) lies, and stopped in the others. Traced since (below), the bounced and hanging frames leave `HSD_JObjMakeMatrix`'s save of `r31` there, her `ThrowN` bone's address, which the port now takes from the allocator model; and every frame rebuilds that joint's matrix, so the stop that remains (a frame that didn't) is unreached. Uncommon in play: the beam's hitbox stage needs the input sequence that leaves `u.ss.x2240` at 4 or more when the beam is shot from the ground.
- **Unsure, 1, since settled unreachable (Link, Young Link and Kirby's copies of them):** the bow loosing an arrow whose owner is no longer the archer (`itLinkArrow_802A850C`'s refusal). A nocked arrow's state has no animation, so its hitbox is never live for a reflector or absorber; its pickup clears its pickup flag; the other owner writes are other kinds' callbacks, drops and throws of held items (the arrow isn't one), destroys and the unload walk; and a stale arrow can't be loosed, since the archer leaves the bow's states with one nocked only through a hit, a capture, the barrel or a KO, whose callbacks destroy it first ([the oracle](oracle.md#the-characters-own-items), "The bow").
- **Unreachable, settled:** the hookshot with one link (`it_802A2568`): its links number its attributes' count times the ground's or the air's share, the fighter's size counting only above 1 (a mushroom), so they are fixed in an items-off match: the oracle replays' hookshots make 15 on the ground and 22 in the air for Link, 10 and 15 for Young Link. PK Flash's charge on another kind: only PK Flash and Kirby's copy (kinds 68 and 145) have the state table that runs it. The blaster's state 10 (`ftCo_800BF228`) and Ness's bat's second state: their pickups enter them only with the command variables the demo fighters' spawns set (`it_802AE994`, `it_802AD590`); a match's blaster takes the fighter's state (`ftFx_SpecialN_GetBlasterAction`, 0 to 9). Dr. Mario's demo pill (`itDrMarioPill_802C09C4`, `itDrMarioPill_802C1180`), as the items audit found.

**Checked since.** The ported functions the oracle's replays run got their aliases and checks: a build of `melee-oracle` that counted every item callback it dispatched and every `// Ports` function it ran played each replay of the verify list against its golden, 244 of 246 matching (the ReDead and Octorok monster matches' goldens are older than their re-recorded replays and were left out), and the 136 functions some replay ran have `ledger/checks.txt` lines naming the replay that runs them most and how often. ### Playing it

`cargo run -p dist` builds the player with the `dist` profile (release with fat LTO, see [performance](performance.md)) and copies it to `dist/melee-hd.exe` at the repository's root (git-ignored), which a double-click starts; `-j N` limits the build's jobs. `cargo run -p dist -- --shortcut` also puts a `melee-hd` shortcut to that copy on the desktop (Windows, through PowerShell's `WScript.Shell`), and `--shortcut-dir DIR` puts it in another folder. A copy still running when the next one is made is moved aside (`dist/melee-hd.old-*.exe`), since Windows lets a running program be renamed but not replaced, and a later run deletes it once it has closed; if even that fails, the tool says the copy is in use. rustc writes the source path of every panic location into the program, dependencies' too, so the tool builds with `--remap-path-prefix` (added to the rustflags in effect) mapping the home folder, CARGO_HOME, rustup's folder, the repository and the target folder to neutral names: the copy names no user or local folder (cargo's `trim-paths` would do the same, once stable). The executable and its window carry ssbm-rs's icon, a hexagonal ring in the reflector's style drawn by `crates/melee-player/icon/make.py` (original artwork, nothing from the game): `build.rs` embeds `icon/melee-hd.ico` with the manifest on Windows, so the shortcut shows it too, and the window takes `icon/window.rgba`.

**The disc.** The player plays the disc `--disc` names, else `SSBM_DISC`'s, else the one it remembers. With none, or when the remembered one is gone or no longer opens, it says what it needs and shows a file picker (rfd), and keeps the disc chosen in `disc.txt` in its settings folder. A disc that isn't Melee NTSC 1.02 (game ID GALE01, revision 2) is refused with what it is instead (another revision, the PAL or Japanese version, or another game), and the picker asks again.

**The settings folder** is `%APPDATA%\melee-hd` on Windows and `$XDG_CONFIG_HOME/melee-hd` or `~/.config/melee-hd` elsewhere; `MELEE_HD_SETTINGS` names another folder (for testing). It holds `disc.txt`, `last-match.txt` (the launcher's last match, `key = value` lines) and, on Windows, `melee-hd.log`. The pipeline cache stays in `%LOCALAPPDATA%\melee-hd` (see [Resolution, aspect ratio and pipelines](#resolution-aspect-ratio-and-pipelines)).

**No console window.** The release and dist builds on Windows are windowed programs (`windows_subsystem = "windows"`), so a double-click opens no console. Started from a terminal, the player attaches to the terminal's console (`AttachConsole(ATTACH_PARENT_PROCESS)`) and prints there; output a parent pipes or redirects (`cargo test`, `Command::output`) stays where it was sent. With neither, as from a double-click, its output goes to `melee-hd.log` in the settings folder, made anew each run, and an error that stops it shows in a message box. Windows' shells don't wait for a windowed program: `cargo run` does, but from cmd or PowerShell the prompt comes back at once and the player's output lands after it (`Start-Process -Wait -NoNewWindow` waits). Debug builds keep their console.

### Recording

**Decision: every match of the player's own is saved as a Slippi replay, on by default.** The project's goal includes `.slp` output that Slippi's tools accept, and Sarah named the recorder as the next player work. melee-sim's recorder (`game::record`) runs Slippi's recording codes' part (slippi-ssbm-asm's `Recording/`, version 3.19.1, the newest the local replays carry) from the state: it reads what the codes read from the game's memory, at the points they inject, and builds the raw event stream they send over EXI. It only reads. It is presentation output, as the mix log is: `Settings::record` turns it on before the match starts, simulated code never reads it, a clone (Extrapolate's prediction, a rollback snapshot) starts without it and a restore leaves it alone (`#[clone_from(keep)]` on `Game::recorder`). `crates/melee-player/src/record_tests.rs` plays 2,400 ticks of a scripted match of the player's own with the recorder off and on, a pause included, and finds every tick's state (as the sync test compares it) and output the same.

**What it records.** The payload sizes (every 3.19.1 command's), the game start (the match's `StartMeleeData` with its callbacks cleared, Zelda holding A made Sheik and a costume past the character's count made the first, as the codes do; the seed; the UCF toggles; nametags; the PAL and frozen Pokémon Stadium toggles; the scene; the language), the code list in split messages, and for each frame the frame start (seed and scene frame count), each fighter's pre-frame update (inputs as the fighter took them, the master status's physical buttons and triggers, the poll's raw sticks), each awake fighter's post-frame update (the L-cancel status the codes keep past `Fighter` included), up to 15 items, and the bookend; then the game end with its method, who quit and each player's placement from the results as they stand (`gm_80166378` on a copy), the stream's last event: Slippi Dolphin closes the file there, so the rest of that tick isn't recorded. Frames are numbered from -123, one entry per frame (no rollback); paused frames aren't recorded, and the frame starts' scene frame count shows the pause, as Slippi's do. The metadata has `startAt` (UTC), `lastFrame`, each player's frames by internal character (the leader's, not Nana's) with empty `names`, and `playedOn: melee-hd`.

**Where melee-hd writes something else than the codes would.** A match of the player's own runs melee-hd's Vanilla ruleset, so its code list is empty and its UCF toggles are 0: 3.19's codes write 1 whatever runs, and melee-hd writes whether its rules run UCF. The codes' frame start and item processes belong to two GObjs Slippi's codes make, which a match of the player's own doesn't have, so the recorder takes their place in the run order (priorities 0 and 15, before the first process on link 7 or later): the seed a frame start records is the one Slippi's playback restores at the same place. The motion state's first word, which the post-frame update copies as "misc AS" and which some states fill with a GObj's address, is that address in the allocator model, 0 where the model is off (a match without an Ice Climber). The 3.18 stage events (Fountain of Dreams' platforms, Whispy's wind, Pokémon Stadium's transformations) aren't recorded: they hook stage code, and parsers treat them as optional; their sizes are declared, as the codes declare them. The display names, connect codes, Slippi UIDs, session ID and game number are online-only and zero, as the codes write them offline.

**Saving.** A match is saved when it's left, however it ended (its end, Escape, a stop, quitting): `Game_YYYYMMDDTHHMMSS.slp`, named by the local time the match started as Slippi Dolphin names its replays (another `-N` when two start in the same second), in the folder the launcher's Replays folder or `--replays DIR` names, else `replays` beside the executable (`dist/replays` for the dist build). The launcher's Save replays box, kept with the last match (`record`, `replays`), and `--no-record` turn it off. A replay played back (`--replay`) and the benchmark (`--bench`) aren't recorded. The log says where each replay went.

**Checked.** The recording reads back and plays back: `record_tests.rs` saves a scripted match's recording through the session's own saving, parses it, plays it back as the player plays a replay (`Settings::from_replay`, at a drive's pace, without the allocator model as the match ran) with the recorder on again, and finds every event the same but the game start's scene (2.2, the VS mode's match, against playback's 14.1) and the pre-frame updates' physical buttons and triggers (playback injects the processed inputs and polls controllers at rest, as `ssbm_slippi::compare` leaves them out). Recordings of Slippi replays, and of melee-hd's own recordings, are checked against their replays by `melee-oracle record` ([the oracle](oracle.md#recordings)). melee-slippi's, ssbm-rs's and Slippi's own (`@slippi/slippi-js` 9.1.3) replay parsers read the files ([the oracle](oracle.md#recordings)).

### Frame time

**Decision: the renderer runs on threads of its own, a frame at a time.** The renderer's CPU work on a frame comes in three stages: running the GX stream (decoding commands), fetching, decoding and transforming each draw's vertices into the GPU's words and triangles, and drawing (textures, uniforms, pipelines, handing the draws to wgpu). The game's thread runs the stream and sends each draw, with the state's changes since the last, the stream's bytes of its vertices and the vertex arrays they read (each once, as far as draws have reached it), in batches every thread reads. Transform threads (a quarter of the processor's threads, one to four; `MELEE_GPU_WORKERS` sets it), each with a copy of the registers, share the draws out, each draw to the one given the fewest vertices so far: it fetches, decodes, transforms and builds the draw (melee-gpu's `build`), and decodes the others' only as far as the normals they leave for the next draw. A render thread draws what they built in the stream's order (melee-gpu's `Threaded`, after ssbm-render's design). They all work at once on the same frame, and the game's thread waits at the frame's copy to the XFB until the render thread has drawn it (`Threaded::spawn_synced`), so the frame is presented as soon as it's drawn, no frame later than before: the loop keeps its one frame of latency, and the frame costs about what its slowest stage does rather than all of them. Draws go over in batches of 64, small enough for the stages to overlap within a frame, and the render thread sends its queued draw calls to the GPU every 160 (`MELEE_GPU_FLUSH_AT`) so encoding them overlaps the stream. A draw whose arrays the host doesn't hold as they are (a copy laid over them, a rewritten display list) is fetched on the game thread, and so is every draw when something observes them. `CHECK_THREADED=1` runs `melee-render-check` the same way.

The rest of the cuts change no output (every checked frame stays identical, at scale 1 and at 1440p, where a frame drawn by the old and the new renderer saves to the same PNG):

- Each indexed vertex array is looked up once a draw, over the stretch the draw's indices reach, and read in place where the address space holds it in one piece (`Memory::view`); display lists run where they lie instead of being copied out.
- A draw's vertices are transformed by a setup read once for the draw (`xform::Setup`: the projection, lights, channels and texture coordinate scales), and the binormals only when a texture coordinate reads them; a test checks it against the per-vertex steps on random states.
- A draw's vertices are written once and its triangles name them through an index buffer, instead of three vertices a triangle; the vertex shader reads each vertex's words from a storage buffer with only the texture coordinates its draw generates (most draws one), so a frame's vertex data went from about 6.4 MB (144 bytes for each of a triangle's three vertices) to 0.9 MB.
- Consecutive draws with the same state join into one draw call, and a pass sets its pipeline, bind groups and scissor only when they change.
- The hashes of textures in loaded archives, which never change, are kept between frames, and a copy's footprint found unchanged is checked again only the next frame; the vertex format's layout is kept while its registers stay the same; the renderer's maps use a fast hash.
- Lines and points write each corner once and name it twice (four vertices a quad, not six); uniforms are shared by every draw of a flush with the same state; whether the alpha test can fail is worked out once per register value; the registers' hashes are kept only once a run asks for digests.
- `GX_DIGEST=FILE` writes a line a frame digesting what the frame draws (every vertex in order, with the state it's drawn with, the clears and the copies), whatever the batching and buffers' layout: two builds that draw the same frames write the same lines, which checks a change to the CPU's frame building exactly.

| Before | 11.8 ms | 14.4 to 15.2 ms | 9.8 ms | 17.0 to 17.7 ms |

### Latency

**Options.** `--present mailbox|fifo|immediate` (and the launcher's Present) picks the swap chain's present mode. Mailbox, the default, shows each frame at the display's next refresh without tearing and without waiting: a newer frame replaces one still waiting. FIFO queues it for its refresh (vsync), and immediate shows it at once, tearing where the scan-out is partway down the screen: the lowest latency. A mode the display lacks falls back to mailbox, else FIFO, which every display has, so the default never tears (before, a display without mailbox got immediate). `--added-delay N` (the launcher's Added delay, 0 to 15 frames) is deliberate added latency: each controller read reaches the simulation N ticks later (`melee_input::Delay`; the first read stands in for the ticks before it), 16.7 ms a frame on top of everything below, for players who want a CRT's feel back. A replay's recorded inputs aren't delayed. `--tick-timing` and `--jit-margin` choose when ticks start (see [Just-in-time ticks](#just-in-time-ticks)). `--audio-exclusive` takes the audio device exclusively (Windows; see [Audio](#audio)). `--mute` mixes the sound as always but opens no audio device, so nothing is heard and no device's timing reaches the loop: for measuring runs on a machine someone is using (the audio columns of the latency log stay empty).

**Measuring.** `--latency-log FILE.csv` writes a row a tick and prints a summary (mean, median, 99th percentile and worst of each) when the player quits; `--latency-overlay`, or F3 in a match, draws the last second's ticks and frames a second and its means over the frame's corner (egui on the window's swap chain, only while it's on), with the GPU's time a frame by stage, from timestamp queries, and the CPU's time building and presenting it ([performance](performance.md#rendering-speed)). ### Just-in-time ticks

**Decision: ticks can start just in time for the refresh that shows them; experimental and off by default.** It changes no gameplay, only when each tick starts within its slot. It was the default at first, for the least latency (Sarah's call above), but in Sarah's testing (2026-10-16) it drew visual artifacts the fixed timer doesn't: the stage disappearing, black frames, black boxes on screen. So the fixed timer (`--tick-timing timer`, the launcher's Tick timing "Fixed timer") is the default and the just-in-time policies are labeled experimental until those are found and fixed. `crates/melee-player/src/jit.rs` is the scheduler, portable and tested with a fake clock; `timing.rs` is the per-OS layer under it.

**Melee's clock stays.** Ticks run 60 a second (`TICK_RATE`, the engine's pad-polling rate, as ssbm-rs's window has always run them; the console's 59.94 is 0.1% slower, which the audio queue's rate nudge already absorbs, and nothing documented asks for it). Tick n is due at the clock's start plus n ticks; the scheduler never starts a tick before its due time nor at or past the next tick's, so ticks stay one for one with that clock however the display runs, and the simulation is untouched: only where in its slot a tick starts moves. A stall of more than four ticks puts the clock back on now, as the fixed timer did, and a tick whose successor is due already runs at once without drawing its frame (the latest due draws it; the fixed timer drew every one).

**The deadline.** A tick's frame is meant for the first refresh D at or after `due + lead` that no earlier frame took, and the tick starts at `D - lead`, where `lead` = the 99th percentile of the last 300 measured costs (from a tick's start, its controller read, to the GPU having finished its frame) + the margin, at most a tick. A thread waits for each presented frame's last submission (`present::GpuDone`, `wgpu::PollType::Wait` once the present call has returned, since wgpu's present takes a lock that wait holds) and notes when the GPU finished it. A frame finished later than its refresh (less 0.3 ms for the flip to latch) missed it and shows a refresh late; the next tick's frame then takes a later refresh, never the same one. When the refresh a tick would take puts its start at or past the next tick's due time (a display slower than the ticks, 59.94 Hz against 60 about once in 1000 ticks, or a refresh a late frame took), the tick runs at its due time without a frame of its own and its state shows in the next frame: the display has no refresh for it. So a missed deadline costs one late frame and, at 60 Hz, one tick unshown, never a skipped or doubled tick.

**Refresh times.** On Windows the desktop compositor's timing (`DwmGetCompositionTimingInfo`: a recent refresh's time and the refresh period) gives every refresh, read afresh as ticks go; it describes the display the compositor runs on, so it's used only while its period is within 1% of the window's monitor's rate (winit's). wgpu doesn't expose the swap chain's own presentation clock (DXGI's frame statistics, `VK_KHR_present_wait`, `VK_GOOGLE_display_timing`), so the player can't see when a frame actually reached the screen, only when its refresh came. Other systems have no source yet (Wayland's presentation-time protocol, macOS's `CAMetalDisplayLink`); there the scheduler runs ticks at their cadence.

**Waiting.** The event loop sleeps until shortly before the next tick or frame (winit's wait, which wakes for window events too; on Windows a high-resolution waitable timer), and `timing::sleep_until` waits out the rest: on Windows a high-resolution waitable timer of its own (`CreateWaitableTimerExW` with `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`) for all but the last 0.3 ms, elsewhere the standard library's sleep (`nanosleep`), then a spin. How early the loop's wait ends (`timing::Guard`) is the 99th percentile of how late its timed wake-ups came (winit's `StartCause::ResumeTimeReached`) plus 0.25 ms, 0.5 to 4 ms. A key event that arrives in that last stretch is read at the next tick.

**The margin** starts at `--jit-margin MS` (the launcher's Timing margin, 0 to 8 ms, 1 ms by default): the trade between latency and the odd late frame. A missed refresh widens it by 1 ms, at most once a second (a stall misses several in a row) and only once the percentile is measured, up to 4 ms (past the 99th percentile a wider margin buys little but latency); every 600 frames on time in a row (ten seconds) narrow it by 0.25 ms, back to the one asked for.

**Policies.** `--tick-timing auto|refresh|vrr|timer` (the launcher's Tick timing, kept with the last match as `tick-timing`, and `jit-margin`):

- **Aligned** (`refresh`, or `auto` when it pays): as above. For displays that wait for refreshes, FIFO or mailbox at a fixed rate.
- **Cadence** (`vrr`, presenting immediately, no refresh times, or `auto` when aligning doesn't pay): ticks start at their due times, waited for precisely, and frames are presented as soon as they're ready. A variable-refresh display (G-SYNC, FreeSync) waits for the frame, so it shows when it's ready, at the ticks' even rate; immediate presenting shows it at once, tearing.
- **Timer** (`timer`): the fixed timer the player had, the event loop's wake-up and nothing more.

`auto` aligns only where it can't hurt and pays: the display's refresh times are known, the present mode isn't immediate, the refresh rate is a whole multiple of 60 (59.94, 60, 119.88, 120, 240 Hz, within 0.5%), where aligned ticks come evenly spaced whether or not the display is variable-refresh, and the lead is shorter than what a frame would wait without aligning, its median cost plus half a refresh (with 0.5 ms of hysteresis). A rate that isn't a multiple (144, 165 Hz) is taken to be a variable-refresh display, where aligning to a grid the display doesn't keep would space frames 2 and 3 refreshes apart; `refresh` aligns there anyway for a fixed-refresh display, where it cuts the wait for the refresh to the lead (on average half a refresh, 3.5 ms at 144 Hz, when the costs spread less than that).

**Interpolate and Extrapolate.** Frames are drawn on their own schedule, every refresh; each tick starts just before the first frame that will show it (`Scheduler::plan_before_frames`: the first frame start at least the tick's lead, its measured cost with the prediction plus the margin, after its due time), so its controller read is the freshest that frame can show. t still comes from Melee's clock (the tick's due time), so motion on screen stays even. Aligned, each frame starts its own lead (the frames' costs' percentile and margin) before the refresh it's meant for, and that refresh is its display time (`Pacer::align`); `auto` checks that this pays with the frames' costs.

**`--added-delay`** holds each read back N ticks as before; the read itself is just in time, so the delay adds exactly N ticks to the least latency, and Extrapolate's predictions stay exact with it.

**Measuring.** The latency log's `ready_ms`, `target_ms`, `shown_ms` and `missed` columns (see the table above) and its summary (tick start to GPU done and to shown, refreshes missed, ticks unshown, and the policy and the margin at the end) measure it; F3's overlay adds "to screen". `shown_ms` is an estimate: the first refresh after the GPU finished the frame, where frames wait for refreshes, else when it finished; a frame composed by the desktop compositor (a window rather than fullscreen) shows a refresh later than that. Input to photon is `adapter_age_ms` + `shown_ms` plus the display's own processing; PresentMon (above) measures what follows the present call where the estimate isn't enough. `--mute` keeps a measuring run silent.

That's what `auto`'s check is for; it would decline here even at 120 Hz. Aligned frames in Extrapolate dropped from 140 to about 100 frames a second: a frame's drawing (about 6 ms here) and the tick before it fill the 6.9 ms refresh, so a late frame's successor waits a refresh. The scheduler's simulation (`jit::tests::simulated_latencies`, 8 phases x 30 s against a mailbox display, `cargo test -p melee-player simulated -- --nocapture`) shows where it pays: costs of 4 to 5.5 ms (a quiet machine) give 6.5 ms from controller read to refresh at every rate, against 13.5 ms on average with the timer at 60 Hz (p99 20.8), 9.3 at 120 Hz and 8.5 at 144 Hz; costs like this machine's busy ones (7.5 to 11.5 ms with spikes) give 16.7 ms at 60 Hz against 17.9 (p99 16.7 against 27.1) and the same as the timer at 144 Hz.

### High refresh rates

**Decision: three modes, Off (the default), Interpolate and Extrapolate.** The design is the [architecture](architecture.md#frame-pacing-and-high-refresh-rates)'s: a frame is drawn from two simulation states and a fraction, (A, B, t), so any refresh rate and variable refresh work alike. `--high-refresh off|interpolate|extrapolate`, and the launcher's High refresh, which the settings folder keeps with the last match (`high-refresh = ...`), pick the mode. Interpolate came in the first slice, Extrapolate in the second.

- **Off** draws each tick's frame as the tick renders it, one frame a tick: the loop described under [Latency](#latency), unchanged.
- **Interpolate** runs the ticks on their own schedule, as Off does, and draws frames at the display's rate between the last two ticks, N-1 and N: every frame lies between two states the game reached, and a tick's state shows at most a tick later than Off shows it.
- **Extrapolate** runs the ticks the same way and after each predicts the next, N+1, on a copy of the state with the controllers held (`melee_render::predict`), then draws frames at the display's rate between tick N and the prediction: no latency added, tick N shown when Off shows it, and when an input changes the next real tick corrects at most a tick's motion. With `--added-delay` the next tick's controllers are already read (`melee_input::Delay::next`), so the predictions are exact, as they are for a replay.

**What blends.** `melee_render::blend` keeps what the tick before's display pass left (A, a `Capture`, about 0.05 ms a tick) and draws the latest tick's pass (B) with its transforms blended toward it: joints' world matrices (rotation slerped, scale, shear and translation lerped), the game camera, shadow cameras, the magnifier's and the stages' corner cameras (eye lerped, view slerped, projection lerped), instance joints' views, app-SRT views and particles' motion. Everything else is B's: the HUD's and other 2D cameras (every camera covering the screen but the game camera), colors, textures, materials, lights, text, afterimages, point particles, and whatever only one tick drew, which is drawn where B has it, seen through the blended camera. A joint or particle that moved more than 40 units in a tick, a joint that flipped, and a camera that cut (moved more than 60 units, turned more than 45 degrees, or changed its projection's kind) snap to B. The architecture records why each was chosen.

**Pacing.** Frames are due every refresh of the window's monitor (winit's refresh rate, 60 Hz when the system doesn't say; on a variable-refresh display its highest), and each takes t from when it should reach the screen, its display time D (`crates/melee-player/src/pacing.rs`): the frame's start plus the measured time from a frame's start to its present call returning, and presenting FIFO, snapped to the refresh grid the waits for the swap chain's images give (with a swap chain one frame deep the wait ends at a refresh). t = (D - lead - s_N) / tick, with s_N the time tick N was due and lead the average of D less a frame's start, so t stays between 0 and 1 while ticks are on time and frames' t follow their display times: 144 Hz's 2.4 frames a tick move evenly. Where the just-in-time tick aligns to the display's refreshes, each frame starts its measured lead before the refresh it's meant for and that refresh is its D, and each tick starts just before the first frame that shows it (see [Just-in-time ticks](#just-in-time-ticks)). A unit test runs the pacer against simulated displays (240 Hz and 144 Hz presenting at once, 144 Hz, 165 Hz and 50 Hz FIFO) and checks that the game time each frame shows moves on as its display time does, within half a millisecond.

**Extrapolate's frames.** Tick N is drawn live with its transforms blended toward the predicted N+1's, kept in a `Capture` like Interpolate's A: the blend runs from the prediction back to the tick (`Predictor::blend(t)` is a `Blend` at 1 - t), so everything but motion (the HUD, colors, what exists) is the real tick's, a frame at t = 0 is the tick's own, and a joint, particle or camera that snaps stays the tick's until the next comes. The prediction runs right after the tick, before the frames that need it; its sounds, rumble and events are thrown away and its mix log is off, and the real match is only read (the [architecture](architecture.md#frame-pacing-and-high-refresh-rates) gives the proof). The player's statistics line adds the average prediction time.

**Ticks that draw nothing.** About every 1001 ticks Melee runs a tick without its display pass (its controller alarm runs at 60 Hz, its video at 60000/1001 Hz; ssbm-rs's phase, so the fox-fox-fd replay skips ticks 1986, 2987, 3988 and so on). Off presents nothing new for it and the last image stays, as on the console, and so do Interpolate and Extrapolate (`crates/melee-player/src/paced.rs`): their refreshes until the next tick that draws keep the image shown. They used to draw the tick before's draws on the new state, which is neither image: a frame names objects by handle and reads them live, and the tick moves the state on without the display pass that would make it consistent. On tick 1986, of the 57 joints whose shapes tick 1985 drew, 7 have new world matrices (the ones the tick's logic recomputed) and 37 are left dirty for a display pass, so the frame mixed two ticks' poses, and the materials, particles and objects it read were the new tick's. Interpolate then blends from the last tick that drew to the next one (its transforms are kept until a tick draws again), and Extrapolate's prediction of a tick that draws nothing is no prediction, so the tick before it is drawn as it is and held through the skip: Off's image, command for command. Drawing the skipped tick from a display pass run on a copy of its state would continue smoothly, but it would show an image the game never drew and break the rule that a frame at t = 1 is Off's.

**The latency log** in Interpolate and Extrapolate writes a tick's row with the first frame drawn after the tick, its frame columns timed from the tick's start (its controller read), as Off's are.

**Checks.** Off's frames are the frames before these changes: every frame and mix check passes unchanged (`cargo test --release -p melee-render-check -p melee-audio-check -- --ignored`). `crates/melee-render/tests/blend.rs` plays the Fox ditto's benchmark replay and decodes each frame's stream as the frame checks do, every draw's vertices transformed to the screen: at t = 1 the blended stream is the tick's own byte for byte, for each of 60 ticks (600 to 660); at t = 0, on ticks whose draws pair up with the tick before's, every draw is where the tick before drew it (1,330 of tick 651's 1,367, 1,272 of them moved), but for what snaps (5 HUD draws, which moved), what the tick before didn't draw (6 particles, which a frame with only the cameras blended draws the same) and particles drawn at another place in the list (26, each where the tick before drew one); at t = 0.5 every moved draw lies between, and what snapped stays the tick's. Unit tests in `blend.rs` check the snap rules (a shape the tick before didn't draw, a reused handle, a jump, a flip, a cut, the HUD's cameras) and the decomposition. `tests/blend.rs` checks Extrapolate's pair too: at t = 0 the stream is the tick's own byte for byte, every tick from 600 to 660, and at t = 1, on ticks whose draws pair up with the next tick's, every draw is where the next tick draws it (1,330 of tick 650's 1,367), but for what snaps (the same 5 HUD draws), what the prediction didn't draw (7, drawn where the tick has them through the predicted camera) and particles at another place in the list (25); at t = 0.5 every moved draw lies between. `predict_tests` (see the architecture) checks that predicting changes nothing, state, outputs or sound. `paced_tests` plays fox-fox-fd through tick 1986, the first that draws nothing, with the player's paced state beside Off's frames: every tick that draws, Interpolate's frame at t = 1 and Extrapolate's at t = 0 are Off's byte for byte; on tick 1986 neither draws; Extrapolate's frames on tick 1985, whose next tick it can't predict, are the tick's own; and tick 1987's Interpolate blends from tick 1985.

**Cost.** At 1440p (internal scale 3), `--bench 1800` on Fox against Marth on Battlefield, release, with other agents' builds keeping the machine about half busy: Off's frame takes 0.50 to 0.57 ms in the GX stream, 3.6 to 3.9 ms in the renderer and 2.2 to 2.4 ms presenting with the GPU's wait; Interpolate's (`--frames-per-tick 1`) 0.58 to 0.60, 3.8 to 3.9 and 2.3 to 2.4 ms, so the blend adds under 0.1 ms a frame, and keeping a tick's transforms 0.05 ms a tick. With 4 frames a tick (a 240 Hz display), a frame's drawing takes 4.7 ms at the median and 7.7 ms at the 99th percentile (7.0 and 10.6 ms with presenting, which the headless bench waits for frame by frame); the player's renderer threads overlap the GPU's drawing with the next frame's, and on the hidden desktop at 144 Hz (mailbox) the player drew 144 frames a second at 1280 by 960, about 4 ms from a frame's start to its present call (the median of its latency log). Per-frame work scales with the refresh rate; the simulation's doesn't.

**Extrapolate's cost** is one prediction a tick, whatever the refresh rate: `--bench --high-refresh extrapolate` at 2560 by 1440 (scale 3), release, beside other agents' builds (the CPU about 40% busy). On Fox against Marth on Battlefield (1,800 ticks) a prediction takes 0.50 ms at the median and 1.15 ms at the 99th percentile (restoring the copy 0.13 ms, the tick with its display pass 0.36, keeping its transforms 0.03), on top of the real tick's 0.7 ms with its mix; with 4 frames a tick drawn beside it, 0.65 and 2.5 ms. On Ice Climbers against Peach on Pokémon Stadium (3,600 ticks) 0.51 and 1.10 ms, on Fox against Marth there 0.42 and 0.71 ms. The frames cost what Interpolate's do (the blend under 0.1 ms a frame). So a tick with its prediction takes about 1.2 ms of the tick's 16.7 ms, the prediction about 3% of it, at any refresh rate; the frames' drawing, which scales with the rate, is the budget's larger part, as in Interpolate. On the hidden desktop at 144 Hz the player drew 144 frames a second at 1280 by 960, mailbox and FIFO, predictions averaging 0.4 ms. A machine whose simulation tick takes several milliseconds would spend as much again predicting; Interpolate costs no extra tick (keeping a tick's transforms is 0.04 ms) and is the fallback there, and Off the fallback for a machine that can't draw more than a frame a tick.

## Open issues

- **Pokémon Stadium's screen** at frame 9000 is identical to ssbm-rs's in both images, and every draw but two compares the same: the two draws of the screen's feed sample an RGB565 copy melee-gpu keeps on the GPU, which `compare` hashes from memory the copy never writes, while the log's side hashes memory ssbm-rs's renderer wrote (`Expect::SameImages`, the sweep's `fox_marth_ps_9000`). The copy's content is the frame's draws, which compare the same, and the images show it.
- **Refraction images.** Draws that sample the refraction copies (`ImageRef::Refract`, `ImageRef::RefractFrame`) aren't drawn exactly yet.
- **Shape animations** aren't drawn; no checked frame uses one.
- **The particle pass's boundaries** are inferred from the display commands (runs of `Draw::Particles`), and the magnifier bubble's erase color is an average of the colors the original reads; both match every checked frame.
- **State cache resets** that fighter and item draw callbacks make (`ftDrawCommon`, `itDraw`) come only with their debug displays and aren't mirrored; the stage objects' are (`Draw::Invalidate`), and the refraction callback's TEV reset.
- **Speed.** At 1440p a frame's ticks and drawing take 6.8 ms at the 99th percentile on a busy machine (see Frame time); the GPU's drawing at high scales is the larger part of presenting, which the CPU work doesn't overlap.
- **Just-in-time ticks, what's left.** The player knows when refreshes come (on Windows, from the compositor) but not when a frame actually reached the screen, nor whether the display is variable-refresh, which `auto` guesses from the rate. Presentation feedback per OS would settle both and replace the estimate in `shown_ms`: DXGI's frame statistics (`IDXGISwapChain::GetFrameStatistics`) through wgpu's DX12 surface (`Surface::as_hal`; the default backend here is Vulkan), `VK_KHR_present_wait` or `VK_GOOGLE_display_timing` (wgpu presents, so it would have to pass the present IDs), Wayland's presentation-time protocol, and macOS's `CAMetalDisplayLink`, which are also the refresh times those systems lack today. Not yet measured: a 60 Hz display, visible runs on Sarah's variable-refresh display, and a quiet machine. The lead takes the costs' 99th percentile; at high refresh rates a lower one (a late frame costs only a short refresh) would pay on average. A window composed by the desktop compositor shows frames a refresh after the estimate. Raising the game's thread's priority on Windows (MMCSS's "Games" class) would keep ticks on time when the machine is busy.
- **Unchecked ports.** The port ledger counts a presentation port as checked when the frame or audio checks run it (measured with coverage over the references). Eighteen ported functions no reference reaches yet (refraction's material setup and indirect texture matrices, a few TEV register and alpha register helpers, GX getters) carry no ledger alias, only their names in their doc comments, until one does. The GX SDK functions Melee doesn't link (ssbm-rs's symbol table lacks them) are named the same way.
