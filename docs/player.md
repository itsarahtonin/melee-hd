# The player

melee-hd's player presents the simulation: it draws the display pass's commands, mixes the audio driver's voices into sound, and reads the controllers into the simulation's input. The [architecture](architecture.md) draws the line: everything here is presentation, and nothing here feeds back into `melee-sim`.

## Crates

| Crate | What it does |
| --- | --- |
| `melee-render` | Turns a frame's `display::Draw` commands into a GX command stream (HSD's display code ported to issue GX SDK calls), and draws that stream with melee-gpu |
| `melee-gx` | The GPU's command stream and register state: runs a stream, handing each draw and EFB copy to a renderer (ported from ssbm-rs's `ssbm-gx`) |
| `melee-gpu` | Draws the stream with wgpu (ported from ssbm-rs's renderer, `ssbm-render`) |
| `melee-audio` | Mixes the voices the simulation keeps into samples, as the DSP's AX microcode does, and plays them |
| `melee-ax` | The DSP's AX microcode (ported from ssbm-rs's `ssbm-ax`) |
| `melee-slippi` | Slippi replays (`.slp`) and what Slippi's EXI device answers playback's codes from them |
| `melee-input` | The keyboard, standard gamepads and the GameCube controller adapter, as the simulation's pad input |
| `melee-player` | The `melee-hd` binary: a VS match in a window |
| `tools/render-check` | Compares melee-render's frames with ssbm-rs's renderer's |
| `tools/audio-check` | Compares melee-audio's mix of a replay with ssbm-rs's recording of its audio |

`melee-sim` depends on none of them.

**Decision: no ssbm-rs code runs in the player.** ssbm-rs is the test oracle. The player's crates are melee-hd's own, ported from ssbm-rs where it has the piece (the GX stream decoder, the renderer, the AX microcode, the replay reader), as `crates/gekko-fp` is: idiomatic melee-hd code to change, not frozen copies. ssbm-rs's crates stay dependencies of the check tools, which compare against it. `crates/melee-player/tests/runtime_deps.rs` fails if `cargo tree` finds any ssbm-rs crate among the player's normal and build dependencies, and `leaf-check`'s `slippi` test parses every benchmark replay and a sample of Slippi replays with both melee-slippi and ssbm-rs's `ssbm_slippi` and compares the results.

## Rendering

The display pass names the objects it draws (a joint's display object's shape, a camera, a light set, a particle link) and leaves their state as it was when the pass drew them. `melee-render` ports what HSD would have sent GX for each: the camera's viewport, scissor and projection (`HSD_CObjSetCurrent`), the lights' GX objects (`HSD_LObjSetupInit`, `HSD_LObjSetup`), the material's colors, textures, texture coordinates, TEV stages and pixel-engine mode (`HSD_MObjSetup`, HAL's TEV expression compiler, `HSD_SetupRenderModeWithCustomPE`), and each shape's matrices, vertex descriptions and display list (`HSD_PObjDisp`). Those go through a port of the GX SDK (`melee_render::gx`), which encodes the same command stream the console's SDK would, register write for register write.

**Decision: the GX command stream is the interface to the GPU.** The stream is what melee-gpu (ssbm-rs's renderer, `ssbm-render`, ported) draws, and its frames match Dolphin's software renderer within tolerance. Encoding the stream and running it through `melee-gx` costs little next to drawing, and buys two things: the renderer is the one whose output is already checked, and each frame can be compared with ssbm-rs's draw by draw (`melee-render-check`), with every register, transformed vertex and texture of each draw, not only as an image.

**Decision: per-draw state the pass changes is snapshotted.** Most objects keep the same state through a frame's pass, so the renderer reads them as the pass left them. A few change between draws, and the simulation records what the presentation needs at the moment of the draw (in `display::Display`, so drawing allocates nothing once warmed up):

- a camera can draw more than once a frame, moved in between (the magnifier's, once per bubble): `Draw::Camera` names a `CameraView` with the viewport, scissor, projection and view matrix;
- the magnifier erases each bubble in a color it blends from the stage's colors by where that player's fighter is (see **Magnifier bubbles** below): `Draw::MagnifierErase` names the player;
- the lights' GX slots are given by every `HSD_LObjSetupInit` (a light GObj's callback, a fighter's lights, a fighter's overlay light): `Draw::Lights` names a `LightSet` with the active table, the light masks and each light's specular slot and vector;
- materials read the GObj being drawn (`HSD_GObj_804D7814`: a fighter's color overlays and translucency, a stage object's or item's overlay): `Draw::Rendering` names it;
- the shadow textures shadowed materials take after their own (`tobj_shadows`) change joint by joint while a stage object that receives shadows draws (see **Stage shadows** below): `Draw::Shadows` names the list as a shadowed material sets up, whenever it differs from the last named;
- a highlight texture takes the first current infinite light's vector, and render callbacks change the current lights between draws: `Draw::Hilight` names the vector as a material with one sets up, whenever it differs from the last named (see **Highlights and specular lights** below);
- a specular joint leaves its half vectors in the specular lights for what follows, whether or not any of its shapes draw in the pass: `Draw::SpecularInit` names the joint for every pass `HSD_JObjDispSub` draws it in;
- a particle's app-SRT takes the view of the camera drawing it, once per display frame, so the frame's last view is the last camera's: `Draw::AppSrt` names the view matrix and screen scales whenever the pass brings them up to date (see **Particles in the reflection** below);
- a stage object's render callback puts HAL's state caches out of date before it draws (`grDisplay_801C5DB0`'s `HSD_StateInvalidate(-1)`): `Draw::Invalidate` names the reset (see **State cache resets** below).

These are additions to `melee-sim`'s output only; no simulated value depends on them.

**Stage shadows.** A stage object that receives shadows (`x10_flags.b5`) draws joint by joint (`grDisplay_801C5B90`): before each joint, the stage's check (`stage_info.on_check_shadow_render`; Yoshi's Story's, `grStory_801E36D8`, asks whether the fighter stands above the joint) switches each fighter's shadow on or off, which adds its texture to or takes it from the list shadowed materials take after their own (`lbShadow_8000EFEC`, `HSD_ShadowSetActive`, `tobj_shadows`). Each material's setup then gives its chain texture maps, matrices and coordinates afresh (`HSD_TObjSetup`'s `HSD_TObjAssignResources`), so the shadows' slots, and a material's own UV coordinates, which come after the shadows', depend on the chain being drawn. melee-render read both as the pass left them at the frame's end: the last joint's list for every shadowed draw, and each texture's resources from the pass's last setup of it. So stage draws took shadows the original's don't (Yoshi's Story's, Dream Land's and Fountain of Dreams' platforms, Pokémon Stadium's floor and its transformations' ground), with resources from other chains: on Yoshi's Story the left platform's texture shared its coordinates with a shadow's and its top came out white, and on Pokémon Stadium the floor's textures took other slots, so a 256 by 256 CMPR texture went missing from some of its draws and a white band crossed the Poké Ball (PSNR 15.2 dB at frame 600). The pass now names the list (`Draw::Shadows`), and melee-render assigns each chain's resources as it sets the chain up (`hsd::Assigned`), as the original does. The frames those differences reached are identical now (Yoshi's Story's 600 and 6000, Pokémon Stadium's 600, 2600 and 11000) or keep only a difference of their own (Dream Land's, Fountain of Dreams', Stadium's screen at 9000). Mutation checks, each made by reverting part of the fix locally: reverting both fails 12 checks (`fox_sheik_ys_600` at 33.4 dB, `fox_marth_ps_600` at 15.2 dB, `sheik_fox_fod_600`, and the sweep's Yoshi's Story 6000, Dream Land 6000, Pokémon Stadium 2600, 9000 and 11000, Fountain of Dreams' three frames and its scaled 6000); reading the frame's last shadow list again, with the resources assigned, fails 7 (`fox_sheik_ys_600` at 65.7 dB in its second frame, and six of the sweep's); keeping the shadow list but reading the resources the pass left fails 5 (`fox_marth_ps_600` at 15.2 dB again, and the sweep's Dream Land 6000 and Pokémon Stadium 2600, 9000 and 11000). The floor's white band was the resources; the platforms' extra shadows were the list.

**Magnifier bubbles.** The magnifier's camera erases each bubble before drawing its fighter (`ifMagnify_802FBBDC`), in a color it blends from four of the stage's nine colors (`GroundParam::xB8` through `xD8`, a three by three grid around the camera limits): which four depends on which half of the limits, or which side past them, the fighter's camera bone is in (`ifMagnify_GetCornerColors`, `ifMagnify_803F984C`), and the blend on how far into that half it is. melee-render took the average of the magnifier's own four colors (`ifMagnify`'s `x4` to `x10`, the grid's corners) for every bubble, so on Pokémon Stadium's fire stage Fox's bubble was dark where ssbm-rs's is gray. The display pass now names the player whose bubble it erases (`Draw::MagnifierErase`, an addition to the output only), and melee-render blends the color with the original's single-precision operations (`magnifier_erase_color`). Pokémon Stadium's frame 6000 is identical now (it was 22.1 and 39.3 dB), against a capture made with ssbm-rs's renderer running (see **Copies made before a log** under [Results](#checking-frames)). Mutation check: putting the average back fails `fox_marth_ps_6000_fire` (39.3 dB in both frames); Dream Land's 12000 still passes: there the average and the blend come to the same color, and its recorded difference was the capture's.

**Compiled TEV.** A material's TEV stages are the ones its compile made as it loaded, not ones made from its textures as drawn ([the engine notes](engine.md#the-object-state)): melee-render draws from the compile melee-sim keeps on the material (`MObj::tev`). Recompiling at each draw left Fountain of Dreams' water a stage short: the stage turns the reflection's texture into a shadow lightmap after it loads, so the original's water still blends the reflection in by a constant (0x4C) and then multiplies by it, where melee-render only multiplied, and the water came out about 8 levels greener and 5 bluer once the reflection showed. It isn't the reflection's RGB565 copy, the earlier suspect: melee-gpu drawing ssbm-rs's log makes gxplay's frames exactly, and the copy's texels at the water's draw are the same on both sides. `compare` hadn't shown the draw, as it printed only the first 20 differing events and the stars' point size register differed in every draw. The sweep's frames 2600, 6000 and 9000 went from 32.3/32.4, 33.3/33.8 and 32.0/32.1 dB to 59.4/65.1, 40.6/55.1 and 50.0/49.3 dB (with the point size below). The comparer checks each material's compiled stages and constants against the original's memory; the four benchmark matches and Fountain of Dreams' replay compare every tick with no difference with it. Mutation check: compiling at each draw again fails `sheik_fox_fod_600` (48.5 and 48.8 dB) and the sweep's Fountain of Dreams frames (32.4/32.6, 34.4/35.1, 32.1/32.2 dB) and its scaled 6000.

**Highlights and specular lights.** Sheik's needle reflects a highlight texture (`TEX_COORD_HILIGHT`), whose matrix `TObjSetupMtx` makes from the first current infinite light (`HSD_LObjGetCurrentByType`). melee-render looked that light up in the current lights as the pass left them at the frame's end, which in the four-player match hold no infinite light, so it loaded the no-light matrix and the needle's texture coordinates came out constant (195 components, a 3 by 10 pixel box below the stock icons, and 3 pixels in the second frame at 59.5 dB). The pass now names the light's vector as the material sets up (`Draw::Hilight`). On Dream Land a few vertices' specular colors differed, by up to 43 levels, in about 80 draws a frame: `HSD_JObjDispSub` makes each specular light's half vector toward every specular joint it visits (`HSD_LObjSetupSpecularInit`), even one whose shapes are all hidden in that pass, and the last joint's vectors stay in the lights for the draws after; melee-render made them only for joints that drew a shape, so after Sheik's hidden parts in the translucent pass the original's lights held other vectors than melee-render's (`Draw::SpecularInit` now). Dream Land's few differing pixels (90.5 and 64.6 dB) were its background's: its billboard (`JOBJ_RBILLBOARD`) took its scale from `PSVECMag`, where `HSD_MtxColMag` is `sqrtf` of the single-precision sum, so the diagonal differed in its last bit and the depth test turned on it. `SetupSharedVtxModelMtx` always loads the normal matrices as texture matrices (its joint flags share their values with `SETUP_NORMAL` and `SETUP_REFLECTION`), which melee-render now does too; no checked draw reads them, but the transform unit's memory is compared (see [Checking frames](#checking-frames)). `four_fd_600` and `fox_sheik_dl_600` are identical now, draw for draw. Mutation checks, each made by reverting one part locally: ignoring `Draw::Hilight` fails `four_fd_600` (the needle's texture matrix, and 59.5 dB in its second frame); naming half vectors only for joints that draw a shape fails `fox_sheik_dl_600` (the specular light in the transform unit's memory and the colors of 167 draws, though no pixel); `PSVECMag` for the billboard fails `fox_sheik_dl_600` (positions and the position matrix; 90.5 dB in its first frame); loading the shared-vertex setup's texture matrices only by `GetSetupFlags` fails `fox_sheik_dl_600` (the transform unit's memory, every draw after Dream Land's first skinned shape).

**State cache resets.** Every stage object's render callback puts HAL's state caches out of date before it draws, whether or not it draws anything (`grDisplay_801C5DB0`'s `HSD_StateInvalidate(-1)`), so the original sends the next draw's vertex description, pixel engine and channel state again; as the last register it writes is then an XF register, it sends no flush primitive (`__GXSendFlushPrim`) before the next display list. melee-render's caches still held the last stage draw's, so it sent less and ended on a BP register: an extra 8-vertex degenerate draw between Final Destination's and Dream Land's opaque and translucent background passes, which drew no pixel. The pass names the reset (`Draw::Invalidate`). The fighters' and items' resets (`ftDrawCommon`, `itDraw`) come only with their debug displays (hitboxes), which a match never turns on. Mutation check: ignoring `Draw::Invalidate` fails `four_fd_600` and `fox_sheik_dl_600` (the extra draw, in both frames).

**Particles in the reflection.** A particle with an app-SRT (attached to a joint) is drawn through its app-SRT's view matrix, which its first draw in a display frame makes from the current camera (`psDispSubAppSRT`), and each camera starts a display frame (`psDispParticles` in pass 0). Fountain of Dreams' reflection camera draws them first, mirrored, then the game camera; melee-render read every app-SRT's view as the pass left it, the game camera's, so the reflection's attached particles (about 25 draws a frame) were placed tens to thousands of pixels from ssbm-rs's, a ring of difference in the water at frame 6000 (40.6 dB). The pass names each view as it makes it (`Draw::AppSrt`). The sweep's Fountain of Dreams frames 2600, 6000 and 9000 are identical now. Mutation check: ignoring `Draw::AppSrt` fails `sheik_fox_fod_6000` (the particles' positions; 40.6 and 55.1 dB).

**Point size.** Fountain of Dreams' stars are points of size 18 (`grIzumi_801CCB90`'s `HSD_StateSetPointSize`, `Draw::PointSize`), which melee-render noted and skipped; it now sets the point size, and melee-gpu draws each point as a square that size, as ssbm-render does. The stars and the line and point register of every draw after them now match, and `sheik_fox_fod_600` is identical (it was 41.1 and 41.2 dB). Mutation check: skipping the point size again fails `sheik_fox_fod_600` (41.9 and 42.0 dB) and the sweep's three Fountain of Dreams frames and its scaled 6000.

### Checking frames

ssbm-rs records a run's GPU command stream as a Dolphin FIFO log, and its `gxplay` draws the log with ssbm-render:

```sh
GX_DFF=f600.dff GX_DFF_FRAMES=600,2 ssbm-run "$SSBM_DISC" --replay data/bench/fox-fox-fd.slp --fp hardware --port all --fields 640
gxplay f600.dff f600
```

`melee-render-check` plays the same replay natively, draws its frames through melee-render, and compares:

```sh
melee-render-check align "$SSBM_DISC" data/bench/fox-fox-fd.slp f600.dff 560 600      # which native frame the log starts at
melee-render-check compare "$SSBM_DISC" data/bench/fox-fox-fd.slp f600.dff f600 FRAME out/
```

`compare` lines the two streams up event by event and reports each draw whose raster or TEV registers (TEV stages and colors included), the transform unit's registers (channel colors and controls, viewport, projection, texture coordinate generation) and memory (its matrices and lights, read or not), sampled textures and palettes (by content: a palette's entries up to the highest one the image indexes), transformed vertices (screen positions, the colors of the channels in use, texture coordinates) or copies differ, exactly, with no tolerance, then compares the images with ssbm-rs's render tolerance: a PSNR of at least 38 dB, and at most 0.25% of the pixels off by more than 32 levels. It exits with failure when a frame is out of tolerance. The native match runs on the timeline the boot's audio setup starts (see [The boot](#audio)), so its scene loop renders on the same rounds as ssbm-rs's, and a log's frame N is native frame N - 3 from the first checked frame to the last (without the timeline, rounds that tick twice and render once came at other times, and the two drifted apart by 13 frames over a match). `compare` takes the native frame within 16 either way whose draws share the most exact vertices with the log's (`CHECK_SEARCH` changes the range). `CHECK_FP=slippi` plays a Slippi replay in Slippi Dolphin's float mode; `CHECK_EVENT=N` prints one event of each side in full; `CHECK_DIFFS=N` shows the first N differing events (20 by default, so a frame where a register differs in every draw shows only the first few and hides the rest: Fountain of Dreams' water's missing stage hid that way behind its stars' point size); `CHECK_DRAW_LIMIT=N` draws only the first N draws of melee-render's side, to find the draw where two images part (with `play`, of the log's); `CHECK_COMMANDS=1` keeps each event's preceding stream commands (BP, CP and XF writes, display list calls), which `CHECK_EVENT` prints and `CHECK_COMMANDS_OUT=DIR` writes for every event of both sides, a file a frame, to diff; `melee-render-check play LOG.dff OUT/` draws a log alone. A summary's box is in the EFB's coordinates, which start at the scissor offset (342), so a draw at y 700 is on screen at 358. The native match draws the eight frames before the first compared (`native::WARM_UP`), whose copies it may sample: the shadows and bubbles copy the frame before, but Pokémon Stadium's screen shows a copy of the screen showing the copy before, each smaller, and with only two frames drawn a few of its feed's pixels differed at frame 9000 (70.8 and 84.1 dB).

Palette entries past the highest one an image indexes aren't compared: a palette region loads whole (256 entries for `GX_TLUT0` onward), so past a shorter palette it holds the bytes after the palette in memory, which no texel reads; the four-player match's stock icons load 176-entry palettes followed by a pointer, relocated in ssbm-rs's heap (`80E9xxxx`) and an archive offset in melee-render's address space. The texture cache's layout registers (`CHECK_ALL_BP`) still differ: melee-render loads textures into other cache regions than the original's round robin gives, and no checked draw preloads a texture, so where one sits doesn't reach a draw.

The Slippi replays' references are made with Slippi's name plates off (`SLIPPI_PLAYER_NAMES=0`, as the oracle's traces are), but for Fox vs Sheik and Zelda's, which keep them on, and with `--fields` at least 150 past the first frame logged (`GX_DFF_FRAMES=600,2 ssbm-run ... --fp slippi --fields 750`): a Slippi replay's playback starts its frame count earlier than a benchmark match's, and with only 20 fields past the start the log is never written. Pokémon Stadium's transformations come from snapshots of the match (`melee-render-check snap DISC REPLAY OUT FRAME...`, which saves native frames at 1x): on fox-marth-ps the fire stage shows around frame 5000 to 6000 and the water stage around 11000 to 12000. Ice Climbers vs Peach (`ics-peach-ps`) can't be drawn past its first few hundred frames, nor the four-player replay at frame 6000: melee-sim reaches a function no port covers (`ftCo_800DCFD4`, `ftCo_800DE854`) before them.

**Copies made before a log.** ssbm-rs run without its renderer, as these captures are, leaves memory as it was at each EFB copy: nothing draws what a copy would hold. Within a log, gxplay makes the copies itself, but a texture the log's first frame samples before that frame's copy holds whatever memory held: a magnifier bubble's draw comes before the frame's copy into it, so in the first logged frame a bubble showed its model's own image (a white bubble reading LUPE) where the console shows the copy of the frame before. A frame that samples such a copy is captured with ssbm-rs's renderer running (`GX_RENDER=- GX_DFF=... ssbm-run ...`, about five minutes to frame 6000 rather than one), whose copies write memory as the console's GPU does, into the game's `rendered/` folder (`ref-fox-marth-ps/rendered/f6000` and `f9000`, `ref-fox-sheik-dl/rendered/f12000`), and the check names it (`Capture::Rendered`). Both frames of Pokémon Stadium's 6000 and Dream Land's 12000 are identical against those; against the headless captures the first frame differs only in the bubble. Pokémon Stadium's screen at frame 9000 shows a feed copied frames before, and goes from 25.2 and 39.8 dB to 70.8 and 84.1. The headless captures stay as they are for the other checks.

**One command for the frames and the mix.** These frames and the Fox ditto's mix (see [Checking the mix](#checking-the-mix)) run as ignored tests, `tools/render-check/tests/documented.rs` and `tools/audio-check/tests/fox_ditto.rs`:

```sh
SSBM_DISC=... SSBM_RS_LOCAL=... SLIPPI_REPLAYS=... cargo test --release -p melee-render-check -p melee-audio-check -- --ignored --test-threads=4
```

It passes only if every result is what this page records: each frame without a known difference identical (every draw and copy the same, PSNR infinite, nothing melee-render reports as not drawn exactly), each frame with one (the `Expect::Known` cases, Fox vs Sheik's name plates, and the sweep's `Expect::SameImages` case, Pokémon Stadium's screen at 9000) with its image measures and what melee-render notes as not drawn exactly exactly as recorded, so any change to them fails until it's recorded again, the log's frame N lined up with native frame N - 3, three frames drawn at higher scales and in widescreen within the scaled tolerance (see [Scaled frames](#scaled-frames)), and the Fox ditto's mix sample-exact over at least 39.8 s from the trace's boot state and 39.9 s from melee-sim's boot. `REFS` (ssbm-rs's `local/`, `$SSBM_RS_LOCAL`, by default) and `SLIPPI_FOX_SHEIK` (the Fox vs Sheik replay, in `$SLIPPI_REPLAYS` by default) say where the references are, and the benchmark replays are the repository's; a missing one fails the test instead of skipping it. `compare` searches two frames either way for the log's first (`CHECK_SEARCH=2`), since the alignment is asserted anyway. With four test threads it took 43 to 60 s on this machine before Fountain of Dreams, Yoshi's Story, Dream Land, Pokémon Stadium, the four-player frame and the scaled checks joined it (measured back to back with the old set: 43.5 s against 54.6 s, and 60.5 s against 61.9 s on a busier machine): the nine new checks cost about 67 s of test time, about 17 s of wall time on four threads, and the narrower search took back most of it. Each check leaves what it measured in `target/tmp/render-check-results` (`RENDER_CHECK_RESULTS` moves it), for [the dashboard](#the-dashboard). The oracle can't catch a regression here: after the Pokémon Stadium merge a shadow's texture named its image as `ImageRef::Shadow`, which melee-render didn't draw, so the floor's draws sampled other textures in place of the shadows: every checked frame went out of tolerance, and in the player a floor turned black or noisy at every scale, while every simulated value still compared equal. melee-render now lists each kind of image it meets, so a new kind doesn't build until it's drawn or noted.

### Scaled frames

There's no reference above 1x, since ssbm-rs and Dolphin's software renderer draw at the console's size, so `melee-render-check scaled DISC REPLAY FRAME [OUT]` checks the scaled frames against melee-render's own frame at 1x, which `compare` checks against ssbm-rs's. It plays the replay once and draws native frame FRAME (and the two before it, whose copies it may sample) with six renderers of their own: the 640 by 480 frame copied to the XFB on the CPU, as `compare` draws it; the same copied on the GPU, as the player does; 2x and 3x at 640 by 480 (1280 by 960, 1920 by 1440); and at 3x the game's 73:60 (1752 wide) and 16:9 with the cameras widened (2560 wide). It compares the GPU copy with the CPU's (identical on every frame measured), 2x and 3x box-downsampled to 640 by 480 with the 1x GPU frame, and the 16:9 frame's middle 1752 columns with the 73:60 frame (at 3x both are whole pixels: widening keeps the pixels' size and adds 404 columns each side).

Pixel by pixel the scales differ a lot even when nothing is wrong: on frames ssbm-rs's check finds identical at 1x, 2x and 3x downsampled measure 27.6 to 34.3 dB, with 0.8% to 4.7% of the pixels off by 32, because edges are sampled nine times instead of once, textures at grazing angles take finer mip levels, the dither pattern scales, and copies to textures (shadows, the reflection, the bubbles) are drawn at the scale and averaged back. Those differences go both ways from pixel to pixel; a region drawn wrong doesn't. So the tolerance takes the mean difference of each block of 16 by 16 of the console's pixels, per channel, and allows at most 32 levels in the worst block, with a PSNR floor of 24 dB (`SCALED_BLOCK`, `SCALED_PSNR`). Measured on the 11 frames of every stage the standard set and the sweep check this way (and Fountain of Dreams' 6000 below), the worst blocks were 23.6 levels at 2x (Final Destination's edge and grid at a grazing angle), 13.3 at 3x and 11.7 for 16:9's middle against 73:60, and the PSNRs at least 27.7 dB (2x), 28.0 dB (3x) and 34.7 dB (16:9). One frame is beyond it for a known reason and recorded as it is: Fountain of Dreams' frame 6000, whose water shows the reflection, an 80 by 60 copy drawn at each scale and magnified over the water (worst block 49.2 levels at 2x and 32.4 at 3x; 40.3 and 28.6 before the water blended the reflection in as the original does, see **Compiled TEV**).

### The dashboard

`melee-render-check dashboard RESULTS_DIR OUT_DIR` writes a page of the checks' last results in `RESULTS_DIR` (`target/tmp/render-check-results` after the tests) to `OUT_DIR/index.html`, with the images beside it in `OUT_DIR/img/`: per stage, each check's frames, what they were compared with (ssbm-rs at 1x, or 1x for 2x, 3x and 16:9), PSNR, the shares off by 8 and 32, the worst block of a scaled check, and whether it passed, is a known difference (with the reason) or failed. Each comparison keeps three lossless PNGs at full size: the source (ssbm-rs's frame, or for a scaled check melee-render's own frame it's held against), melee-render's, and a third. Against ssbm-rs the third is their difference, `img/CHECK-FRAME-diff.png` (four times each pixel's largest channel difference, as ssbm-rs's ladder shows it; black when identical). For a scaled check it's a heatmap of what the check measures, `img/CHECK-FRAME-heat.png`: pixel by pixel a frame drawn at a higher resolution differs in detail the check means to tolerate (edges, finer mip levels, dither; in places it simply looks better), so a pixel difference mostly shows that. The dashboard draws the heatmap from the two recorded frames with the check's own block code (`block_means`): each block of 16 by 16 of the console's pixels is filled with its mean difference in its furthest channel, the quantity held against the 32-level limit, on inferno's dark-to-yellow ramp from 0 to 32 levels (near black for the few levels normal detail makes, orange and yellow nearing the limit) and cyan past it; the columns past the last whole block, which the check doesn't measure (24 at 3x 73:60), are transparent. The heatmap is the frames' size, so its blocks line up with the other two images, and the page and viewer show it over the source at 80% opacity, with a legend of the ramp and the limit; in the viewer the corner label names the block value under the pointer. An image several comparisons share (an identical frame's source and ours, a black difference or heatmap, a scaled check's 1x frame) is written once. Clicking an image opens a full-window viewer, as ssbm-rs's ladder had: 1, 2 and 3 (or its buttons) switch between the three, space flips the first two, and the view stays where it is, so differences stand out; the wheel or a pinch zooms at the pointer, Fit, 1:1, 2x and 4x set the size (pixels stay sharp from 1:1 up), dragging pans, a double click or double tap zooms in or fits, left and right step through the entries, and Escape closes. The page is published as a claude.ai artifact, so the folder keeps to 250 files and 60 MB: the images all go in when they fit, else the frames at the console's size first (each check's first frame before its others), then as many of the larger 3x 16:9 comparisons (about 4 MB each) as fit, those of checks not passing and then the standard set's first. On 2026-10-15 the standard set and the sweep (47 checks, 118 comparisons) made 175 files and 57.2 MB, six of the twelve 16:9 comparisons left without images (the heatmaps take 0.24 MB in all, where the scaled checks' pixel differences took 4.8 MB, room for one more 16:9 comparison); the PNGs are compressed with the png crate's strongest setting, the smaller of two filter choices, within a few percent of an optimizer's. `compare` and `scaled` write the measures and the images when `CHECK_RESULTS=DIR` is set (each check under `CHECK_ID`), and the tests write each check's status beside them; a check that ran earlier keeps its last result until it runs again.

### Resolution, aspect ratio and pipelines

**Resolution scaling.** melee-gpu is ssbm-render ported, with one addition: an EFB `scale` times the console's 480 lines tall, and as many pixels wide for the console's 640 as the frame is shown wide (`Renderer::with_device_efb`), so its pixels are square at the aspect ratio shown: 584 times the scale at the game's 73:60, 853⅓ (rounded to even) at 16:9, 640 at 4:3. Draws rasterize at the scaled size; EFB copies to textures (shadows, the magnifier's bubbles) average each block back to the console's size (a block's width is whole pixels from one console column's start to the next's), so the game's textures stay what it expects, and the copy to the XFB keeps the scaled size for the window, which only scales it uniformly. The dither pattern scales with it. `--scale N` sets it; by default it's the smallest whose 480 lines cover the window's height (3 for 1440p), and it follows the window as it's resized or made fullscreen. At scale 1 and 640 wide the output is ssbm-render's, which is what the frame checks compare: `melee-render-check` makes its renderer that way and draws the frames unwidened, so the aspect ratio doesn't reach the checks.

**Stage copies.** Fountain of Dreams renders its water's reflection through a camera onto the EFB's top left 80 by 60 pixels, in a white erase color (`Draw::EraseColor`), and copies that corner into the image the water shows with the copy's clear bit, which clears the corner's color and depth for the screen's pass (`grIzumi_801CCEA0`, `lb_800122C8`, `Draw::ReflectionCopy`); Pokémon Stadium's text screen does the same with 250 by 160 pixels, and its feeds copy the screen's frame without clearing (`Draw::ScreenCopy`). melee-render once sent none of these copies and erased those cameras as a magnifier bubble's (its corner colors, depth too), so at every scale, 1x included, the reflection's depth stayed in the corner and the screen's background lost to it there, a dark silhouette of the mirrored stage over the sky; Stadium's corner stayed black and its screen showed no text. It now sends each copy as `HSD_ImageDescCopyFromEFB` does, into images it keeps (`Dynamic::Reflection`, `Dynamic::Screen`) that the water's texture (the stage archive's descriptor, which the stage rewrites) and the screens' textures (`ImageRef::Screen`) sample. melee-gpu keeps RGB565 copies on the GPU like I4 and RGB5A3 ones, and masks copies' addresses to melee-render's 64 MB space, not 32 MB: masked to 32 MB, the copies it encoded on the CPU into those images landed on the loaded archives at 0x0180_0000 and changed their textures. `crates/melee-render/tests/corner_copies.rs` draws onto each corner and copies it, at 1x and at 3x at 73:60, and checks the corner comes out cleared. Against ssbm-rs's frames (`compare`, frame 600 of each), the reflection's draws and the water now match on Slippi replay Game_20260129T214216 (Sheik against Fox on Fountain of Dreams), whose frames then still differed in the stars' point size and the water's TEV, and the text screen's draws, copy and texture on fox-marth-ps, whose floor draws then still differed (see **Stage shadows**).

**MSAA.** `--msaa 4` draws with four samples a pixel: the draws go to a multisampled EFB (color and depth), resolved at the end of each pass into the EFB that copies to textures, readbacks and copies to the XFB read, so the game's textures and frames still come from one image. The TEV runs once a pixel, as before; triangles' edges are what it smooths. Off by default, where the output is unchanged. At 1440p it adds next to nothing to a frame (the GPU's work, inside presenting).

**Decision: frames are shown at the game's 73:60.** Melee's 640 by 480 picture isn't made for a 4:3 screen: on a GameCube and a CRT its 640 pixels fill less than the 4:3 width, and the game camera's perspective aspect is 1.2173333 (`lb_80013B14` widens descriptors' 1.18 to it; `DESC_ASPECT` in `game::camera`), about 0.913 of 4:3. Shown at a full 4:3, as the player first did, everything was about 9.5% too wide (4/3 ÷ 1.2173). The player shows the picture pillarboxed at 73:60 (`melee_render::frame::GAME_ASPECT`), the ratio Slippi Dolphin's "73:60" option uses (`Ratio /= (73.0f / 60.0f)` in Ishiiruka's `RenderBase.cpp`) and a whole-pixel 584 by 480 picture; the camera's 1.2173333 is 584.32 by 480, the same within 0.06% (a third of a console pixel across the screen). 73:60 is used rather than the camera's own number because it's the convention players know and compare against, and it gives the EFB a whole width (584 per scale) with square pixels. `--aspect 4:3` keeps the old look, the picture stretched to 4:3 as Dolphin's "Force 4:3" shows it.

**Decision: widescreen widens the drawn cameras, not the gameplay camera.** With `--widescreen` (16:9) or `--aspect W:H` wider than 73:60, each camera whose viewport covers the whole screen sees `aspect / (73/60)` times as wide at the same height (a perspective camera's aspect ratio, an orthographic or frustum camera's left and right about their center), and the frame is shown at that aspect ratio, so it has the target aspect with the proportions of the 73:60 picture: no stretch. The game camera, which the simulation runs and which decides who is off screen, stays as it is, as Slippi's widescreen code keeps it; only the rendered view sees more of the stage. The HUD's orthographic cameras widen the same way, so the HUD keeps its shape and its place in the 73:60 middle. Cameras that draw into textures (shadows, the magnifier's bubbles) are left alone. The render pass can't tell those apart by its offscreen flag, since the original leaves the frame in the shadows' offscreen pass, so the viewport decides.

**Measured.** A shield bubble is a sphere, so it should draw round. On the Battlefield Slippi replay Game_20260524T181118 at tick 6480 (Captain Falcon shielding, `--bench 6480 --scale 2 --shot`), measured in the saved frame, whose pixels are square as shown: the bubble is 140.4 pixels wide and 142.0 tall at 73:60 (1168 by 960, width over height 0.989) and the same at 16:9 (1706 by 960, 0.988), where before, at 4:3 (`--aspect 4:3`, the old look, 1280 by 960), it was 154.3 wide and 142.1 tall (1.086): 9.9% wider than at 73:60, against the 9.6% that 4/3 over 73/60 predicts. The old 16:9 showed that same 4:3 shape, widened and stretched alike. The edges are where the brightness falls halfway to the background; the lower rim lies over the lit floor, which moves that edge by a pixel or two with the threshold, so the absolute ratio is good to about 2% and the comparison between aspects, at the same threshold, to a fraction of a pixel.

**Decision: pipelines are kept by what they're made for, after Aurora's design.** melee-gpu runs the TEV in one shader, so pipelines differ only in blending, color and alpha writes and the depth test. The player records every pipeline key it has needed in `%LOCALAPPDATA%\melee-hd\pipelines.bin` (`$XDG_CACHE_HOME/melee-hd` elsewhere) and makes them all before the first frame of the next run, with the driver's own pipeline cache (wgpu's `PipelineCache`, where the backend has one) kept beside it. A frame never waits on a pipeline the player has made before.

### Slippi's name plates

**Decision: melee-hd's VS draws no name plates.** Slippi's playback draws each player's Slippi Online display name under the damage counters: an optional code of its playback set, on by default (`Optional: Show Player Names`, a `C2` code at `0x8016E9B4` after the VS scene's entry, `Playback/Show Player Names/InitInGame.asm`, which "shows players' Slippi Online display names as HUD elements when available"). It's a replay viewer's feature: the names come from an online replay's start, and the code makes a GObj of its own with a joint from a HUD archive and the names' text, objects the game doesn't have, so it isn't part of the Slippi ruleset a match plays (slippi-ssbm-asm keeps it under `Playback/`, not `Online/`), and a local VS has no display names to show. The oracle's traces leave it off (`SLIPPI_PLAYER_NAMES=0`); the one reference made with it on (Fox vs Sheik and Zelda's) stays as it is, its plates the only difference (35 or 36 draws, `Expect::Known`). Should melee-hd play replays back or play online with accounts (the netplay follow-on), the presentation can draw the plates from the replay's or the session's names without touching the simulation, as an overlay of its own.

## Audio

The simulation keeps the audio driver's voices, both copies of their parameter blocks, the sound banks' places in ARAM, the music stream and a DSP model that walks each voice through its samples (`docs/engine.md`). What it doesn't do is decode and mix the samples: that is `melee-audio`'s.

**The mix log** (`melee_sim::audio::mix`, `Audio::mix`) is the simulation's only addition, and it is presentation output: `None` unless the presentation turns it on, never read by simulated code, left alone by a rollback restore and empty in a clone. Each audio frame, right after `__AXSyncPBs`, where ssbm-rs's DSP stand-in runs the command list, it records a `MixFrame`: the DSP's 64 parameter blocks, each voice's sync flags, the voices whose depop the sync adds to the studio's sums (`__AXDepopVoice`, from a depop flag or a drop for the DSP's budget), the command list's mode and aux mixes as `__AXNextFrame` built it at the frame before, and the aux callbacks as `__AXProcessAux` finds them. Every write into ARAM is recorded as it completes (`AramWrite`, placed before the frame it precedes): a disc file's bytes from the device command queue (sound bank samples, music boxes), ARAM to ARAM (a bank's groups moved down), zeros, and each bank group again in whole when its load finishes. The presentation empties the log as it mixes; its vectors keep their storage, so recording allocates nothing once warmed up.

**The mixer** (`melee_audio::Mixer`) keeps a 16 MB ARAM image: the boot state's bank groups (each group's samples come from its `.ssm` file after the header: the file's first word plus 0x10, rounded up to 32 bytes), then the log's writes in order. Each frame it puts the frame's blocks, the studio (the depop sums faded as `__AXPrintStudio` does) and the command list in a small stand-in for main memory and runs the AX microcode (`melee_ax`, ported from ssbm-rs's `ssbm_ax`) over it. The words that depend on the samples' values (the ADPCM predictor and history, the resampler's last samples, the buses' last samples) come from the mixer's own last output for that voice unless the frame's sync flags say the CPU just wrote them (a new sound). The rest comes from the simulation, and the mixer counts any voice where the two disagree with no CPU write (`Stats::drift`; none so far). It then runs the aux effects, as the CPU's `__AXProcessAux` does, on the triple-buffered aux buses: the DSP sends a frame's aux mix, the CPU's effect processes it the next frame, and the DSP mixes the result back the frame after. Melee's boot sets up AXFX's standard reverb on aux A and its delay on aux B (`lbAudioAx_8002838C`), and a match uses both. Both are ported (`melee_audio::fx`): the reverb's float math follows the original's instructions through `gekko_fp`, and its comb filters' feedback comes from the game's own `powf`, as the original links it. The mixer makes them as that setup does (`AXFXReverbStdInit`, `AXFXDelayInit`, with the types the driver recorded), or, given a boot state's memory, takes their state, delay lines included, the depop sums, the surround buffer and the aux buffers from it. Each frame gives 160 stereo samples at 32 kHz, as the audio interface plays them.

**Output** (`melee_audio::Output`) plays them on the default device. The game loop pushes each tick's samples into a lock-free ring and never waits; the device's callback resamples them to the device's rate. On Windows the output talks to WASAPI directly (`output/wasapi.rs`): shared, it asks the audio engine for its smallest period (`IAudioClient3::InitializeSharedAudioStream`, 128 samples, 2.67 ms, on Sarah's PC; else the engine's current period if another program holds it, else the standard 10 ms) and keeps two periods queued on the device, from a thread in the multimedia scheduler's "Pro Audio" class; with `--audio-exclusive` it takes the device itself in WASAPI's exclusive mode at its smallest period, in a format the device plays natively (24-bit here), which saves the engine's mixing and its period: the lowest latency the device has, but no other program's sound plays while the match does, and if another program holds the device exclusively, or Windows' "allow applications to take exclusive control" is off, the output shares it instead. Elsewhere, and if WASAPI fails, it goes through cpal, shared, with buffers of about 5 ms where the device allows them.

**Decision: the audio queue is as short as stays glitch-free.** A tick pushes 16.7 ms of samples at once, so the ring rises and falls by that much between ticks, and a tick's first sample waits as long as the ring is full at its lowest, just before the push. The callback measures, each quarter second, the least slack it found (what the ring held beyond what the callback took) and nudges the rate by up to 0.5% so that slack comes to one more callback's samples plus a 2 ms margin: a tick that arrives a callback later still finds samples. Running dry anyway (an underrun, a gap) adds a millisecond to the margin, unless the dry spell lasted more than two ticks (a stall no margin covers: the first frame's pipelines, a dragged window), and a minute without one takes a millisecond back; a stall's catch-up beyond two ticks is dropped rather than played late for seconds. The game's ticks bring a little more than 32 kHz (the console's 59.94 frames a second come 60 times), so the slack settles a fraction of a millisecond above its target, on the safe side. The mix itself is untouched: it's the same samples, and the mix checks don't use the output. Before this, the ring aimed at 40 ms and sat at about 85 ms (the start's stall filled it, and a 0.5% nudge drains 40 ms in 8 s), behind cpal's 32 ms of device queue.

**The boot.** Voices need the boot's audio state: the sound bank, the banks every scene keeps, and the timeline the audio frames run on. melee-sim's match start runs the boot's audio setup (`game::boot`, [the engine notes](engine.md)), so a match from its settings or a replay plays sound from its first tick, with nothing from ssbm-rs. The player turns the mix log on before that setup runs (`Match::start_from`'s `boot`, which runs first), so the mixer sees the boot's own ARAM writes (the cleared silence, the banks' samples) and frames (silent ones, the effects running over them) and starts the effects new. A replay's start also plays the sound Slippi's playback scene does.

### Checking the mix

ssbm-rs records what its audio interface plays (`AUDIO_OUT`) and the boot state in the same run:

```sh
SLIPPI_PLAYER_NAMES=0 STATE_TRACE=audio-fox-fox-fd.trc STATE_TRACE_MEMORY=0..600 AUDIO_OUT=audio-fox-fox-fd.wav \
  ssbm-run "$SSBM_DISC" --replay data/bench/fox-fox-fd.slp --fp hardware --port all --fields 2400
melee-audio-check audio-fox-fox-fd.trc data/bench/fox-fox-fd.slp audio-fox-fox-fd.wav --fp hardware --ticks 2500
```

`melee-audio-check` plays the replay natively from the trace's boot state (`tools/audio-check/src/boot.rs` reuses `tools/oracle`'s trace reader and seeding), mixes it, and aligns the two streams: an exact match of 1024 samples if there is one, else cross-correlation. ssbm-rs's recording starts at power-on, and the native mix starts at the boot state, 4000 samples (25 frames) later. It then reports each window's SNR, largest difference and share of equal stereo samples, and the first sample that differs. On the Fox ditto on Final Destination (39.9 s compared) and Fox against Marth on Battlefield (59.9 s compared), the mix is sample-exact from the match's start to the recording's end, reverb and delay included: both effects processed sound in about 86% of the frames. The trace's game files that the fighters cache in ARAM (`PlFxAJ.dat`, `PlMsAJ.dat`) aren't sound and aren't in the device command queue's files, so the mixer skips them. On this machine mixing takes about 0.22 ms a tick.

With `--port` (and `-` for the trace) `melee-audio-check` doesn't read the trace: the match starts as the player starts one, from melee-sim's boot, and the mix covers the boot's frames too. Against the same recordings it is sample-exact from the native mix's first sample (the AX library's first frame, which lines up with the recording's sample 320) to the end: 40.0 s of the Fox ditto and 60.0 s of Fox against Marth.

`melee-audio-check --out MIX.wav` writes the native mix, and the check reports how often the music stream moved on to its next box and when it last did: a song that stopped stops moving.

**Decision: the player reads the disc at a drive's pace, unlike the replay checks.** The disc's speed is a match setting (`Settings::disc`, [the engine notes](engine.md)): at Slippi's fast disc speed, which ssbm-rs's traces and recordings of replays use and so every replay check keeps, about half of all songs stop 1.8 s in, in ssbm-rs's runs as in melee-sim's, because the stream's start and its addresses reach the DSP in one audio frame. ssbm-rs's window reads at a drive's pace, 3 MB/s on top of each read's latency (its `1fb4da3`), and the player does the same, for its own matches and replays alike; `--disc-speed fast` takes the fast speed. `melee-audio-check --disc-speed drive` checks that pace against ssbm-rs's runs with `DISC_RATE=3000000`:

```sh
SLIPPI_PLAYER_NAMES=0 DISC_RATE=3000000 STATE_TRACE=local/player/audio-drive-fox-marth-fd.trc STATE_TRACE_MEMORY=1 \
  AUDIO_OUT=local/player/audio-drive-fox-marth-fd.wav ssbm-run "$SSBM_DISC" --replay local/bench/fox-marth-fd.slp --fp hardware --port all --fields 4500
melee-audio-check - fox-marth-fd.slp audio-drive-fox-marth-fd.wav --port --fp hardware --disc-speed drive --ticks 4200 --out mix.wav
```

On Fox against Marth on Final Destination, whose song stops at the fast speed (the stream last moves in tick 109; the mix is sample-exact with ssbm-rs's fast recording for 66.7 s, song gone in both), the drive's mix is sample-exact with ssbm-rs's recording at that pace from the native mix's first sample to the recording's end, 75.0 s from melee-sim's boot (72.1 s from the trace's boot state), and the song plays throughout: the stream moves to a new box 42 times, the last in tick 4187, and the mix is about half again as loud in every 10 s of the match's first minute. Fox against Marth on Battlefield, whose song plays at either speed, is sample-exact for 75.0 s at a drive's pace too. A match from the player's own settings behaves the same: Fox against Marth on Final Destination lost its song at tick 109 at the fast speed for every seed tried, and keeps it at a drive's pace.

## Input

`melee_input::Inputs::read` returns the four ports' `PADStatus` just before each tick. GameCube controllers on a Wii U adapter (or a copy, such as Mayflash's in Wii U mode) take their own ports. The adapter is read raw over USB with nusb, as Dolphin's GCAdapter reads it, not through SDL, which rescales the axes; on Windows it needs the WinUSB driver (Zadig installs it). A thread keeps the latest report and sends rumble, and each read turns the report into what `PADRead` returns, with the origin calibration the console's SI and PAD library do (ported from ssbm-rs's player). Standard gamepads (gilrs) and then the keyboard take the first ports left. The keyboard: arrows for the stick, IJKL for the C-stick, X, Z, C and S for A, B, X and Y, D for Z, Q and W for L and R, Enter for start, and left shift to halve the stick. `--no-adapter` leaves the adapter alone.

## The player

```sh
melee-hd                                               # the launcher: pick the match in the window
melee-hd --p1 fox --p2 marth --stage bf [--stocks 4] [--minutes 8] [--widescreen | --aspect 21:9 | --aspect 4:3] [--scale N] [--msaa 4] [--size 1920x1440] [--fullscreen] [--disc-speed drive|fast]
melee-hd --replay data/bench/fox-fox-fd.slp            # a replay's match, its inputs played back
melee-hd --bench 1200 --size 2560x1440                 # headless, timing each frame
melee-hd --launcher-shot launcher.png [--size WxH]     # draws the launcher to a PNG, no window
melee-hd ... [--latency-log FILE.csv] [--latency-overlay] [--present mailbox|fifo|immediate] [--added-delay N] [--audio-exclusive]
```

Characters and stages are what melee-sim has ported: its `game::roster` lists them (the characters by `CharacterKind`, the stages by `StKind`, with their command-line names), a new port adds its line there, and the command line, `--help` and the launcher all read that list. `--help` prints the names. The match runs at 60 ticks a second.

**The launcher.** With no `--p1` to `--p4`, `--stage` or `--replay` (and no `--bench`), the window opens on a small form: a character or none for each port (at least two players), the stage, stocks (0 for a timed match) and minutes (0 for no time limit), the aspect ratio (the game's 73:60, 16:9, 16:10 or 21:9 widened, or 4:3 stretched), a fullscreen box, the present mode and the added delay (see [Latency](#latency)). Start (or Enter) plays the match in the same window; Escape in the match, or the match's end, comes back to the form, and Escape on the form quits. The other options (`--stocks`, `--minutes`, `--widescreen`, `--aspect`, `--scale`, `--msaa`, `--fullscreen` and the rest) still apply. The form opens with the choices of the last match started from it, which the settings folder keeps (`last-match.txt`, see [Playing it](#playing-it)); `--stocks`, `--minutes`, `--widescreen`, `--aspect`, `--fullscreen`, `--present` and `--added-delay` win over those, and without a readable file the form starts from the command line's values. A match the command line names plays as before, and Escape quits it. A repeated character takes the next costume, as the command line's default Fox ditto does.

**The match's rules.** A match from the launcher or the command line starts the way the VS mode starts one (`gmVsMelee_EnterVs`, in `game::gm::vs_mode`): the VS mode's start data with what the character select sets for each player, and the VS menus' rules of a new save (pausing on, friendly fire off, damage ratio 1.0) with the chosen stocks and minutes and the item switch off. Those rules also decide what the HUD shows: a start data filled in by hand without them draws no damage or stock display. `melee-oracle`'s `vs_rules` test compares the setup with the start data the benchmark replays recorded.

**Decision: a match with an Ice Climber runs the allocator model, laid out as a console's VS match from the menus.** The model of the original's allocators (`Settings::heap`, [the allocators](engine.md#the-allocators)) is off in the player's own matches, where no address reaches gameplay and it would only cost time. Nana's computer DI is the exception: with no knockback it pushes her stick by the low byte of her `Fighter*` (no Slippi code clears it in a match of the player's own), so `Settings::vs_with` turns the model on when a player is an Ice Climber (`CharacterKind` 14); a match without one leaves it off. A player's match is a VS match started from the menus on a console without Slippi's codes, so it's laid out as that heap is (`Layout::vanilla_vs`), not as Slippi's playback boots into the debug VS mode (`Layout::slippi_playback`, which this decision first took as a guess): four heaps rather than Slippi's six, no code list, `Fighter` at its own size, the preload cache's `AllM` heap kept, and the match's stage and fighters' files preloaded by the character and stage selects. Measured from ssbm-rs's runs of a new save through the title screen and the main menu into VS mode's Melee (Ice Climbers against Fox on Fountain of Dreams), the console gives Popo, Nana and Fox 0x80C7E000, 0x80CAF900 and 0x80CE1200, as the model now does, where the playback layout gave 0x80D94680, 0x80E43240 and 0x80EE1A60; the other ways into the match ssbm-rs tried (no memory card, another character picked first, `--mode 2` from the title screen) give the same; with the item switch set to none, as `Settings::vs` has it, the console gives 0x80C7DC20, 0x80CAF520 and 0x80CE0E20 (no random items' tables), and so does the model; and the model equals memory after every tick of the trace (`melee-oracle vs-heap`, `tools/oracle/tests/vanilla.rs`; the evidence is in [the allocators](engine.md#the-allocators)). A replay's match runs the model either way, laid out as playback lays it out (`Settings::from_replay`). The Ice Climbers are in `game::roster`, so the player's command line and launcher start such matches.

**Decision: the player's own matches unlock everything until melee-hd has its own saves.** `Settings::vs_with` sets the unlocks Slippi Dolphin's unlock-all codes give (`Unlocks::slippi`), not a save's, and keeps them until native saves (milestone 5); from then the save's unlocks decide. The coordinator's call. A console's own match takes its save's unlocks, and they reach gameplay in one known place: the stage's music choice (`gm_80164ABC`) reads them, and on some stages, Pokémon Stadium among them, that decides whether the choice draws from the random seed, so every draw after it shifts. ssbm-rs's run of a new save on Pokémon Stadium diverges from a match with the unlock-all set within six ticks (an extra particle from a later draw); `melee-oracle vs-heap` takes the trace's unlocks for that reason.

**Fullscreen.** F11 or Alt+Enter toggles borderless fullscreen on the window's current monitor (winit's `Fullscreen::Borderless`), in a match or on the launcher; `--fullscreen` starts that way, and the launcher's box does the same. The window keeps the frame's aspect ratio, letterboxed or pillarboxed, whether resized or fullscreen, and without `--scale` the internal resolution follows the window's size: at the next frame after a resize that changes the scale the renderer's EFB is made again at the smallest scale whose 480 lines cover the new height (5 on a 2160-line display), in place (`Renderer::resize_efb`, through `melee_render::gpu::Gpu::resize_efb`; on the renderer's own thread when it has one, in its turn). Only what the EFB's size decides is replaced: the EFB, its depth target and its multisampled target with MSAA, and the bind groups of the copies that read it, to textures and to the XFB (whose frame textures are made at each copy's size anyway). The copies to textures made from the old EFB are dropped, with the bind groups naming them and what they wrote, since their texels are its pixels averaged; the next copies come from the new EFB, as a new renderer's would. The new EFB is cleared with the GPU's state, as the last frame's copy to the XFB left the old one. Everything else stays: the renderer and its threads, the decoded textures, the pipelines (the sample count doesn't change with the window; a different one would need new pipelines), the copy and XFB pipelines, samplers and buffers, and the GPU's registers and texture memory, which the frames after need as they are: the stream sets much of that state once, at the match's first frame (`GXInit`'s setup), or only when it changes (HSD's state cache skips a write that matches what it last set). A renderer that started from a fresh state drew with color writes off until a new match, a black frame with only the odd particle drawn. **Cost**, measured with `--bench 1000 --size 1460x1200 --resize-at 300:2880x2160 --resize-at 500:1460x1200 --resize-at 700:1280x960 --resize-at 900:3840x2160` on fox-fox-fd (other agents' builds running, so the numbers are noisy): making the whole renderer again, as the player did before, took 41 to 62 ms on the game's thread (its pipelines remade and warmed 29 to 54 ms, saved 3 to 5, the old renderer dropped 2 to 13, its threads stopped 1 to 4), and the frame after spent 25 to 33 ms in the renderer re-uploading every texture against about 8 normally: 70 to 103 ms for the resize's frame. In place, the resize takes 0.5 to 1.3 ms (new targets about 0.5, the leftover draws flushed about 0.1, the bind groups 0.02 to 0.09), except the first time in a run the EFB grows to a size the driver hasn't had memory for, when making the 5x targets (about 56 MB) took 6.6 to 7.8 ms; the resize's frame takes about what the frames beside it take, a few ms more on that first growth. The frames after a resize are the frames a renderer made at the new scale from the match's start draws, pixel for pixel: `--bench` with `--resize-at TICK:WxH` (repeatable) changes the offscreen target's size before that tick, as a window resized or made fullscreen does, and reports the resize's frame with its parts and the frames beside it; `crates/melee-player/tests/resize.rs` checks it going up (3x to 5x, threaded), through a 4K fullscreen and back (3x, 5x, 2x, on one thread), and with MSAA (2x to 5x).

**Decision: the launcher is egui, drawn on the player's own device and window.** egui 0.36 (`egui-wgpu` for wgpu 30, `egui-winit` for winit 0.30) draws the form with the window's swap chain format into the surface the frames use, and takes the window's events through egui-winit; nothing is drawn with it while a match plays, so a match's frames and audio are what they were (the frame and audio checks don't run the player and are unchanged). It's a tool for manual testing, plain on purpose, and the seed of the menus and settings screen to come. `--launcher-shot` draws the same form offscreen, for looking at it without a window.

**Decision: the player minimizes latency rather than matching a CRT's.** Sarah's call: players' displays differ, so the player can't ensure a CRT's timings from software anyway, and the least latency leaves the most headroom to spend again, on netplay's input buffer above all. A player who wants a CRT's or a console's feel locally adds latency back on purpose (`--added-delay`, "backfill", below); the default is the least the player can do. The player is cross-platform: the loop and the measures are portable, and OS-specific tuning (WASAPI's low-latency and exclusive modes) sits behind `cfg(windows)` with a portable fallback (cpal).

**The loop.** Each tick reads the controllers immediately before it runs, and the frame it produces is turned into GX commands, drawn and presented at once; the swap chain is one frame deep (`desired_maximum_frame_latency` 1). The event loop sleeps until the next tick is due (winit's high-resolution timer on Windows); after a stall of more than four ticks it drops the backlog instead of racing to catch up. Nothing waits on audio: the tick pushes its samples into the output's ring. Ticks run on a fixed 60 Hz timer, not aligned with the display's refresh (see the follow-up under [Open issues](#open-issues)).

`--bench` plays a match headless, draws every frame and presents it to an offscreen target of `--size`, and reports the time per tick for the simulation, the GX stream, the renderer and presenting, and the median, 99th percentile and worst of a frame's ticks and drawing (the simulation, the GX stream and the renderer), with and without presenting. `--one-thread` keeps the renderer on the game's thread. `--resize-at TICK:WxH` resizes the target before that tick, the renderer following as it follows a window (see Fullscreen above).

### Playing it

`cargo run -p dist` builds the player with the `dist` profile (release with fat LTO, see [performance](performance.md)) and copies it to `dist/melee-hd.exe` at the repository's root (git-ignored), which a double-click starts; `-j N` limits the build's jobs. `cargo run -p dist -- --shortcut` also puts a `melee-hd` shortcut to that copy on the desktop (Windows, through PowerShell's `WScript.Shell`), and `--shortcut-dir DIR` puts it in another folder. A copy still running when the next one is made is moved aside (`dist/melee-hd.old-*.exe`), since Windows lets a running program be renamed but not replaced, and a later run deletes it once it has closed; if even that fails, the tool says the copy is in use. rustc writes the source path of every panic location into the program, dependencies' too, so the tool builds with `--remap-path-prefix` (added to the rustflags in effect) mapping the home folder, CARGO_HOME, rustup's folder, the repository and the target folder to neutral names: the copy names no user or local folder (cargo's `trim-paths` would do the same, once stable). The executable and its window carry ssbm-rs's icon, a hexagonal ring in the reflector's style drawn by `crates/melee-player/icon/make.py` (original artwork, nothing from the game): `build.rs` embeds `icon/melee-hd.ico` with the manifest on Windows, so the shortcut shows it too, and the window takes `icon/window.rgba`.

**The disc.** The player plays the disc `--disc` names, else `SSBM_DISC`'s, else the one it remembers. With none, or when the remembered one is gone or no longer opens, it says what it needs and shows a file picker (rfd), and keeps the disc chosen in `disc.txt` in its settings folder. A disc that isn't Melee NTSC 1.02 (game ID GALE01, revision 2) is refused with what it is instead (another revision, the PAL or Japanese version, or another game), and the picker asks again.

**The settings folder** is `%APPDATA%\melee-hd` on Windows and `$XDG_CONFIG_HOME/melee-hd` or `~/.config/melee-hd` elsewhere; `MELEE_HD_SETTINGS` names another folder (for testing). It holds `disc.txt`, `last-match.txt` (the launcher's last match, `key = value` lines) and, on Windows, `melee-hd.log`. The pipeline cache stays in `%LOCALAPPDATA%\melee-hd` (see [Resolution, aspect ratio and pipelines](#resolution-aspect-ratio-and-pipelines)).

**No console window.** The release and dist builds on Windows are windowed programs (`windows_subsystem = "windows"`), so a double-click opens no console. Started from a terminal, the player attaches to the terminal's console (`AttachConsole(ATTACH_PARENT_PROCESS)`) and prints there; output a parent pipes or redirects (`cargo test`, `Command::output`) stays where it was sent. With neither, as from a double-click, its output goes to `melee-hd.log` in the settings folder, made anew each run, and an error that stops it shows in a message box. Windows' shells don't wait for a windowed program: `cargo run` does, but from cmd or PowerShell the prompt comes back at once and the player's output lands after it (`Start-Process -Wait -NoNewWindow` waits). Debug builds keep their console.

### Frame time

**Decision: the renderer runs on threads of its own, a frame at a time.** The renderer's CPU work on a frame comes in three stages: running the GX stream (decoding commands and fetching each draw's vertices), decoding and transforming the vertices, and building the draws (the GPU's vertices and indices, textures, uniforms, pipelines) and handing them to wgpu. The game's thread runs the stream and sends each draw, with the state's changes since the last, to a transform thread, which sends the transformed draws on to a render thread (melee-gpu's `Threaded`, ssbm-render's design). The three work at once on the same frame, and the game's thread waits at the frame's copy to the XFB until the render thread has drawn it (`Threaded::spawn_synced`), so the frame is presented as soon as it's drawn, no frame later than before: the loop keeps its one frame of latency, and the frame costs about what its slowest stage does rather than all three. Draws go over in batches of 128, small enough for the stages to overlap within a frame. `CHECK_THREADED=1` runs `melee-render-check` the same way.

The rest of the cuts change no output (every checked frame stays identical, at scale 1 and at 1440p, where a frame drawn by the old and the new renderer saves to the same PNG):

- Each indexed vertex array is looked up once a draw, over the stretch the draw's indices reach, and read in place where the address space holds it in one piece (`Memory::view`); display lists run where they lie instead of being copied out.
- A draw's vertices are transformed by a setup read once for the draw (`xform::Setup`: the projection, lights, channels and texture coordinate scales), and the binormals only when a texture coordinate reads them; a test checks it against the per-vertex steps on random states.
- A draw's vertices are written once and its triangles name them through an index buffer, instead of three vertices a triangle; the vertex shader reads each vertex's words from a storage buffer with only the texture coordinates its draw generates (most draws one), so a frame's vertex data went from about 6.4 MB (144 bytes for each of a triangle's three vertices) to 0.9 MB.
- Consecutive draws with the same state join into one draw call, and a pass sets its pipeline, bind groups and scissor only when they change.
- The hashes of textures in loaded archives, which never change, are kept between frames, and a copy's footprint found unchanged is checked again only the next frame; the vertex format's layout is kept while its registers stay the same; the renderer's maps use a fast hash.

**Results** at 1440p (internal scale 3), `--bench 1800` on the Fox–Marth Battlefield replay, the old renderer and the new run alternately twice each, with other agents' builds and checks keeping about six of the machine's eight cores busy throughout (so both are slower than on an idle machine):

| | Ticks and drawing, median | 99th percentile | Renderer, mean | With presenting, 99th percentile |
| --- | --- | --- | --- | --- |
| Before | 11.8 ms | 14.4 to 15.2 ms | 9.8 ms | 17.0 to 17.7 ms |
| After | 5.0 ms | 6.8 ms | 3.5 ms | 9.2 to 9.4 ms |

The GX stream takes about 0.75 ms of that and the simulation about 0.7 ms a tick; presenting adds about 2.2 ms, most of it the GPU's own drawing at that scale. On the game's thread alone (`--one-thread`) the new renderer takes about 4.9 ms a frame (99th percentile 9.1 ms).

### Latency

**Options.** `--present mailbox|fifo|immediate` (and the launcher's Present) picks the swap chain's present mode. Mailbox, the default, shows each frame at the display's next refresh without tearing and without waiting: a newer frame replaces one still waiting. FIFO queues it for its refresh (vsync), and immediate shows it at once, tearing where the scan-out is partway down the screen: the lowest latency. A mode the display lacks falls back to mailbox, else FIFO, which every display has, so the default never tears (before, a display without mailbox got immediate). `--added-delay N` (the launcher's Added delay, 0 to 15 frames) is deliberate added latency: each controller read reaches the simulation N ticks later (`melee_input::Delay`; the first read stands in for the ticks before it), 16.7 ms a frame on top of everything below, for players who want a CRT's feel back. A replay's recorded inputs aren't delayed. `--audio-exclusive` takes the audio device exclusively (Windows; see [Audio](#audio)).

**Measuring.** `--latency-log FILE.csv` writes a row a tick and prints a summary (mean, median, 99th percentile and worst of each) when the player quits; `--latency-overlay`, or F3 in a match, draws the last second's means over the frame's corner (egui on the window's swap chain, only while it's on). The columns:

| Column | What it measures |
| --- | --- |
| `tick`, `time_ms` | The tick, and when it started from the first tick |
| `late_ms` | How long after its due time the tick started: the event loop's wake-up |
| `adapter_age_ms` | From the adapter's latest report coming off USB (the adapter thread's time stamp) to the tick's read: the input's age the player can see. The adapter's own sampling of the controllers comes before it (up to a report's period: 1 ms at 1000 reports a second) |
| `keyboard_age_ms`, `gamepad_age_ms` | The same for the newest key event (winit's delivery to the event loop) and gamepad event (gilrs's time stamp), on ticks that took in a new one |
| `adapter_reports` | The adapter's reports so far; the summary turns them into its rate |
| `sim_ms` | From the tick's start to the simulation's step and the sound's mix done |
| `frame`, `rendered_ms` | Whether the tick rendered, and from its start to the renderer having handed the frame's draws to the GPU (queued, not finished) |
| `acquire_ms` | The wait for the swap chain's next image: back-pressure, near zero when the swap chain isn't full |
| `presented_ms` | From the tick's start to the present call returning: the frame is the display's to show |

What follows the present call, the GPU finishing the frame, the compositor and the scan-out, the player can't see portably. On Windows, PresentMon measures it (as admin or a member of Performance Log Users): `PresentMon-2.6.0-x64.exe --process_name melee-hd.exe --output_file pm.csv --timed 10 --terminate_after_timed`. Its `PresentMode` says whether frames skip the compositor ("Hardware: Independent Flip", or "Hardware Composed: Independent Flip" on a hardware overlay plane) or go through it ("Composed: Flip", a refresh later); `MsRenderPresentLatency` is from the present call to the GPU finishing the frame and `MsUntilDisplayed` to its showing on screen. Input to photon is then about `adapter_age_ms` + `presented_ms` + `MsUntilDisplayed`, before the monitor's own processing.

- **Audio** was the large part: 117 ms from a tick's push to its first sample heard, now 16 (14 exclusive), with no gaps after the start. The rest is the ring's small margin and its sawtooth phase against the device's 2.67 ms callbacks (about 8 ms) and the engine's own two periods (8 ms shared, 5.3 exclusive). On this busy machine a single underrun came with a 13 ms stall of the game's thread; with ticks on time the margin stays at 2 ms.
- **Presenting** was already one frame deep and didn't change. Every mode, on Vulkan (which NVIDIA presents through a DXGI swap chain) and on DX12 alike, came out as "Hardware Composed: Independent Flip" with sync interval 0 and tearing allowed (even DX12's FIFO, which wgpu presents at sync interval 1, so the driver's settings override the vsync asked for), and the display changed whenever a frame arrived: the intervals between display changes spread evenly from 13 to 20 ms instead of falling on multiples of the 6.94 ms refresh. So the display runs variable refresh (G-SYNC) and the driver presents every mode at once; the modes measure the same here, about 3.3 ms from the present call to the screen, 3.0 of it the GPU finishing the frame. On a fixed-refresh display they differ: mailbox and FIFO wait for the next refresh (half a refresh on average: 3.5 ms at 144 Hz, 8.3 at 60), immediate doesn't and tears. On a desktop nobody sees, the mode reads "Composed: Flip" and nothing is displayed, so the display's figures come from visible runs.
- **Input to display** is about 11 ms: 0.5 of input age, 7.5 from the tick's start to the present call (the simulation 1, drawing at scale 5 the rest) and 3.3 to the screen, before the adapter's sampling and the monitor's processing. Drawing is most of it: a lower `--scale` shortens it.
- With variable refresh each frame shows when it's drawn, so the frames' spacing on screen follows the drawing time's spread (13 to 20 ms apart where ticks are 16.7): the follow-up below would even it.

## Open issues

- **Pokémon Stadium's screen** at frame 9000 is identical to ssbm-rs's in both images, and every draw but two compares the same: the two draws of the screen's feed sample an RGB565 copy melee-gpu keeps on the GPU, which `compare` hashes from memory the copy never writes, while the log's side hashes memory ssbm-rs's renderer wrote (`Expect::SameImages`, the sweep's `fox_marth_ps_9000`). The copy's content is the frame's draws, which compare the same, and the images show it.
- **Refraction images.** Draws that sample the refraction copies (`ImageRef::Refract`, `ImageRef::RefractFrame`) aren't drawn exactly yet.
- **Shape animations** aren't drawn; no checked frame uses one.
- **The particle pass's boundaries** are inferred from the display commands (runs of `Draw::Particles`), and the magnifier bubble's erase color is an average of the colors the original reads; both match every checked frame.
- **State cache resets** that fighter and item draw callbacks make (`ftDrawCommon`, `itDraw`) come only with their debug displays and aren't mirrored; the stage objects' are (`Draw::Invalidate`), and the refraction callback's TEV reset.
- **Speed.** At 1440p a frame's ticks and drawing take 6.8 ms at the 99th percentile on a busy machine (see Frame time); the GPU's drawing at high scales is the larger part of presenting, which the CPU work doesn't overlap.
- **Refresh-aligned ticks and variable refresh (follow-up to the latency work).** Ticks run on a fixed 60 Hz timer that knows nothing of the display: on a fixed-refresh display a frame waits up to a refresh for its scan-out (FIFO and mailbox) or tears (immediate), and on a variable-refresh one frames show when they're drawn, unevenly. The next step ticks just in time: start each tick so its frame is presented just before the refresh it's meant for (the refresh's predicted time less the simulation's, the renderer's and a margin's), keeping the simulation at 60 ticks a second by phase-locking it to the refresh and, on a variable-refresh display, presenting at a steady 60 Hz cadence. That needs when frames actually reach the screen, per OS, behind `cfg` with the fixed timer as the portable fallback: on Windows DXGI's frame statistics (`IDXGISwapChain::GetFrameStatistics`, present counts and their refresh times) and a waitable swap chain (`DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` with a maximum frame latency of 1, waking when a buffer frees), reached through wgpu's DX12 surface (`Surface::as_hal`), and for Vulkan `VK_KHR_present_wait` and `VK_GOOGLE_display_timing` where the driver has them; on macOS `CAMetalDisplayLink` (macOS 14), whose callbacks give each frame's target presentation time; on Linux Wayland's presentation-time protocol (`wp_presentation` feedback: when each frame was shown and the refresh period). Raising the game's thread's priority on Windows (MMCSS's "Games" class) would also keep ticks on time when the machine is busy.
- **Unchecked ports.** The port ledger counts a presentation port as checked when the frame or audio checks run it (measured with coverage over the references). Eighteen ported functions no reference reaches yet (refraction's material setup and indirect texture matrices, a few TEV register and alpha register helpers, GX getters) carry no ledger alias, only their names in their doc comments, until one does. The GX SDK functions Melee doesn't link (ssbm-rs's symbol table lacks them) are named the same way.
