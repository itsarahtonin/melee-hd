# The Slippi ruleset

A survey of what the Slippi ruleset needs for live play and a plan for splitting it into a handful of agent tasks, each checkable on its own. Surveyed on 2026-11-14 from `main` at `f7115325`, the day milestone 6's last rows landed and before its full verify; the counts and measurements are that day's. Sarah numbers the milestone.

What the ruleset is (Sarah, 2026-11-14, agreeing to this scope: "yes that sounds about right to me"):

1. **Slippi's gameplay rules in live play**: the 27 codes melee-hd already runs for `.slp` playback (`game::slippi`, `Game::rules`), on in a live match under a Ruleset setting. Vanilla stays the exact option.
2. **No memory card**, as in Slippi Dolphin.
3. **Slippi's unlocks** (milestone 5's call of 2026-10-23).
4. **Not** Slippi's menus, its online entries, m-ex, the netplay code set or Slippi Dolphin's other codes ("i mostly meant the no-memcard thing and the rules that decouple the bubble rendering from the sim code and fixes the CPU DI issue etc").

Also settled: `.slp` files recorded under the ruleset play back exactly in Slippi Dolphin ("to be clear yes .slp files recorded from our slippi ruleset should indeed play back exactly in slippi dolphin"); "also taking perf/code structure wins wherever we can get it; the decoupling and di fix et al should allow us to not have to do some messiness we otherwise have to do with the original ruleset"; under the ruleset and in playback a read of the GPU's pixels sees the bytes from before the copy (2026-11-07); Vanilla's heap leftovers stay modelled exactly (2026-10-29, 2026-11-12); no more players' own codes (2026-10-16); after this comes the refactor round, then the player's polish, each with its own discussion first (2026-11-13). Nothing here contacts Slippi's servers or online services.

The milestone is done when:

- The settings panel offers Vanilla and Slippi, with the default Sarah picks ([design calls](#design-calls)); Vanilla's sessions compare as before.
- Under the Slippi ruleset melee-hd boots with no memory card and Slippi's unlocks, and its menus compare clean tick by tick from power-on with ssbm-rs's trace of the same session run the same way, to each match's start.
- Every VS match under the ruleset runs Slippi 3.19's 27 gameplay codes in Slippi Dolphin's floating point, and **its `.slp` plays back exactly in Slippi Dolphin**: tick by tick the live match equals melee-hd's playback of its own `.slp`, whole state but a named list of playback's own bookkeeping; ssbm-rs's playback of the `.slp` (Slippi's real playback codes, `--fp slippi`) compares clean with melee-hd's and its replay check is clean; and Sarah's spot check in her Slippi Dolphin agrees.
- What the ruleset makes unnecessary is skipped in its matches where that wins speed or simplicity, each skip held by a tripwire or a test, and Vanilla unchanged ([What the ruleset makes moot](#what-the-ruleset-makes-moot)).

## What melee-hd has today

- **The gameplay codes, for playback only.** A replay's code list makes its rules (`Rules::from_codes`); `game::slippi`, `game::ucf` and `game::player_codes` port every gameplay code where it injects, in three versions of Slippi's set (3.19, 3.16, 3.14, `CodeSet`). `Rules::slippi_online()` (3.19 with UCF 0.84) exists and nothing calls it. Every session from power-on, and every match the player starts from the menus, runs Vanilla (`Game::rules` default).
- **The 27 codes are the whole of Slippi's gameplay.** Slippi Dolphin 3.19.1's netplay build runs 288 codes (7,256 lines), and each of Sarah's 156 replays from it records exactly those 288. Slippi's playback leaves 261 of them out of a replay's list (its denylist: every injection not tagged `[affects-gameplay]`) and applies 27, exactly the 27 tagged in the netplay injection list. melee-hd ports all 27: UCF 0.84's eight, neutral spawns, the freeze glitch fix, `Init Stage Data`, `Init Player Data`, off-screen damage from the stage's limits, the three dead-up-fall fixes, Final Destination's background, Pokémon Stadium's four 3.19 hacks, Whispy's direction, NanaDeterminism, Stadium's monitor and wobbling prevention's three. - **No card** already runs: the memory card scene with nothing in slot A is ported and compared (`card-sessions`' "no card"); Slippi Dolphin's setup has `SlotA = 255` (no device). On a console, and in melee-hd today, the scene then asks "No memory card in Slot A. Continue without saving?"; Slippi Dolphin skips the question with its Skip Memcard Prompt code (one `C2` at `gm_Scene_MemCard_OnFrame`), which this scope doesn't include ([design call 5](#design-calls)).

## Exact playback in Slippi Dolphin

### What a replay's playback rebuilds, and what it doesn't

Slippi Dolphin plays a `.slp` by booting its playback code set into its own playback scene, then into the debug VS mode's match (scene 14.1) built from the replay's game start: the start data, the seed, nametags, the language, UCF's pad buffer words (carried in the code list) and the code list, whose gameplay codes it applies. Each frame it injects the recorded inputs into the fighters (`Fighter_procInput`, after the game read its own controllers), restores the recorded seed, and ends the match with the replay. It rebuilds nothing else. So a live match plays back exactly only if nothing else reached its gameplay:

| What a live match could read that playback can't rebuild | Under Vanilla from the menus | Under the Slippi ruleset |
| --- | --- | --- |
| Heap addresses (a computer player's DI: Nana's no-knockback DI reads her `Fighter*` in r30 and a caller's r5) | reached: `ics-peach-ps`'s first recording (replaced 2026-11-19), made in a layout other than playback's, left its recording at frame 10,137 when played back ([the oracle](oracle.md), "Recordings") | cleared by NanaDeterminism (3.19 clears both registers) |
| The menus' heap bytes in the match's new blocks (Brinstar's bubbles' timer, Fountain of Dreams' star, Nana's input ring, a collision joint's stamp, Rainbow Cruise's parts, the enemy spawner's words, item links, a dropped fan's word) | reached; modelled from the heap's image | `Fighter` and `Ground` zeroed by `Init Player Data` and `Init Stage Data`; **the rest still reached** (the collision stamp, items', links' and effects' words, and every in-match reuse whose placement depends on the heap's layout) |
| The display pass's phase (a doubled round every 1,001 ticks, where the pass runs once for two ticks) | off-screen damage, Stadium's monitor, Whispy's side, Final Destination's background draws, homing, Onett's cars, Kongo Jungle 64's birds, Dream Land 64's clouds and stars | fixed by the codes but for **homing and nearest-opponent items through a KO'd fighter's render-placed joint** and **the view edges Onett's cars, Kongo Jungle 64's birds and Dream Land 64's flights read** (the birds and flights a stage joint, not gameplay), which Slippi doesn't patch ([Melee's bugs](melee-bugs.md#homing-and-nearest-opponent-targeting-through-render-placed-joints)); the view edges' fourth reader, the sound objects' pan, is sound only and dead |
| Disc timing (Pokémon Stadium's transformations load asynchronously) | reached | 3.19 loads them synchronously, and nothing else in a match waits on the disc (task 4: the same match at either disc pace) |
| The float mode | the console's | must be Slippi Dolphin's JIT's |
| The unlocks (the music's draw) | the save's | Slippi's, as playback's own codes are |

So the gameplay codes alone don't make a live match's `.slp` exact: the heap's contents and layout still reach a match through the leftovers no code clears, and through which freed block a new object lands on, which depends on where the heap starts and what the match's files took from it.

### Each match from playback's heap

The way to meet the requirement by construction is to start every Slippi-ruleset VS match in the state Slippi's playback gives it, which melee-hd already builds for every replay and checks against ssbm-rs's playback traces.

**Playback's heap**, precisely (`hsd::heap::Layout::slippi_playback`, [the engine notes](engine.md#the-allocators)): Slippi's bootloader raises the console's four OS heaps to six and takes `0xC0` bytes and the playback set's code list (`0x2E00`) from the arena before the boot's heaps; the scene's main heap is the OS's third, `0x80BD8B20` to `0x817F8AC0`, the debug VS mode letting the preload cache's `AllM` heap go (`lbDvdPreload_2`); the recording codes lengthen `Fighter` to `0x2600` bytes; the match's stage and fighters' files are read into the scene's heap, not taken from the selects' preloads (`from_menus` false); the playback codes allocate the replay's code list and the backup of what its codes replace (`playback::CodeListHeap`, sized from the list) and the recording codes their buffers in the scene's heap; and the memory is fresh (`Heap::fresh`: zero as the boot left it, but for the playback scene's one tick). `Settings::from_replay` and `Match::start_from` make exactly this, with the playback and recording GObjs and the scene loop's counts that the playback scene leaves.

**Reaching it from the menus.** At the VS match scene's entry (`fn_8016E730`, where the match takes its `StartMeleeData`) the ruleset takes the game start the recorder writes from it (the start data with its callbacks cleared, the seed, nametags, the language, the code list with UCF's words as they stand) and builds the match from that as `Settings::from_replay` does, in Slippi's float mode; the match runs with the controllers' live polls where playback would inject a replay's frames, and ends by the VS mode's own exit, not the replay's. The menus' session is set aside across the match scene (its allocator model, heap image and carried pools; the match scene's own heap would have been made anew and freed whole anyway) and takes back what the match leaves for the scenes after it: the match's results in `gm`'s static data, the scene's exit data, the audio and the timeline (since 2026-11-17 the match plays on the console's audio, handed over both ways with the timeline: [Live play and playback](#live-play-and-playback)). [Design call 3](#design-calls) weighs this against one continuous model.

**What it buys.** Every leftover a Slippi-ruleset match reads is playback's, so its `.slp` plays back as it played, with no tripwire needed for the heap; the match needs no heap image, and the vanilla layouts (`vanilla_vs`, `from_menus`) never apply to it. The check is direct: the live match and melee-hd's playback of the `.slp` it wrote run the same code from the same state, so they must agree tick by tick on the whole state, but for a named list (`Game::playback`'s replay-frame bookkeeping, the pad library's playback flag and queue, the recorder). `record_tests.rs` already plays a recording back and compares events; this extends it to the whole state every tick.

**What's left outside the construction.** Display-phase paths Slippi doesn't patch: a homing missile or nearest-opponent item targeting through a fighter in its KO toward the screen, and the camera's view edges, which Onett's cars read (their horn and centre decisions) and Kongo Jungle 64's birds and Dream Land 64's clouds and stars start from (a stage joint the oracle compares, not gameplay, and only with the camera far back, where the edges lie past 200). Each reads state the display pass placed, and Slippi Dolphin's playback doubles its rounds at its own phase, so a match where such a read falls on a doubled round can play back differently in Slippi Dolphin, as Slippi's own replays and online peers can. melee-hd can't make that exact, since Slippi Dolphin's phase isn't known; it can see it: at each such read, compute the outcome from both placements (the pass's and the logic's) and, where they differ, mark the match ([design call 9](#design-calls)). One more path is an input's: playback hands the recorded inputs to the fighters only, so port 2's A on Brinstar Depths steps Kraid's haze live and never in playback, and the haze's animations draw random numbers in the logic, ahead of fighters' and items' draws in the same tick; that is marked the same way (`live::Haze`). A pause, too, leaves the live match's camera a little off its playback's to the match's end (playback never pauses; [Slippi's defects](slippi-bugs.md#a-paused-matchs-recording)), so every read of the camera from the logic after a pause is marked (`live::DisplayPhase::paused`, on any stage): the view edges on those three stages, and the camera's transform and CObj elsewhere (Corneria's city part, Mute City's wrecks' smoke, enemies and Scizor flung toward the screen, the Unown's swarms, Pokémon Stadium's close-up, a nearest-opponent item's target through a fighter the camera places); the camera's width average, which the bonuses read, and its quake counters, which decide whether the looping quake's model stands, are followed as playback's camera holds them (the paused updates left out, the first frame's settling updates added) and those reads made both ways ([the engine notes' audit](engine.md#the-cameras-readers-after-a-pause)). These and Slippi's other defects melee-hd reproduces are in [Slippi's own defects](slippi-bugs.md).

### The scene entry's stall

On the console the VS match's first tick comes late: the scene change takes 1.4 to 2.8 fields at Slippi's fast disc speed (`pause-fd`'s 2.8: 1.0 from the stage select's last tick to the next scene's preparation, 1.5 in VS mode's scene entry waiting for the sound banks' loads, `HSD_SynthSFXWaitForLoadCompletion`, 0.25 the scene's setup and entry; 77 and 38 fields at a drive's pace in the Vanilla session `special-giant`), the pad alarm polling meanwhile, and the scene's loop starts with the newest poll. A live match built as playback builds a replay's started on playback's own timeline, so from the first input on the same reads landed a frame or two later in its frames than in the console's, and another random sequence followed (each match's first item another kind in another place).

So the live match goes on from the console's timeline (Sarah, 2026-11-15: "Yes, line them up"): at the handoff the session runs the VS scene's entry as the console does on a copy of the menus' session (`Session::console_entry`: the entry, its sound banks' loads waited for, the pad alarm's polls meanwhile taking the console's reads, the scene loop's start), and the match, built from its game start as before, takes up where that leaves the console (`live::Timeline`, `Game::go_on_from`): the clock's time and its hardware's events and counts (the retraces, the pad alarm and the polls it queued, the audio DMA and the DSP, the frame buffers, the scene loop's round, the perf timer; `Clock::take_up`, the match's own disc read and ARAM work keeping their place), the pad library's queue and statuses, and the rumble. Its ticks then wait for the same polls, take the same reads and render on the same rounds as the console's; at the scene's end the menus' session takes up the match's timeline the same way, so the scenes after it go on at the console's time. The game start, the scene frame count and the live-equals-playback property for gameplay stay as they were; what changes is which read lands on which frame, and where the 1-in-1001 doubled display rounds fall (the console's, not playback's).

**Netplay.** Sarah's condition (2026-11-15: "assuming that wouldn't desync with slippi in a potential future ability to connect with slippi matchmaking"): the change stays local. Online, inputs are tied to frames: each peer sends its input for frame N and both play frame N with the same inputs, so a peer's start-up stall changes only which of its local controller reads becomes its input for each frame, its own latency, never what the peers agree on: the game start, the frames numbered from -123, each frame's inputs once decided, the seed and the code list are the match's own and untouched by the stall.

**What still differs from the console's run** (`melee-oracle session` through each live match, [the oracle](oracle.md), "The Slippi ruleset's live matches"): the heap's layout and its fresh blocks, playback's GObjs and scene, and Slippi's DynamicsFix (`ftCo_8009DD94+0x2FC`, `Common/FastForward/DynamicsFix.asm`), which sets up every dirty matrix of a fighter's model in the tick: Slippi Dolphin's live play runs it as its playback does (it's in both code sets, unconditional), so the live match keeps it, and ssbm-rs's ruleset sessions, which apply only the 27 gameplay codes and the 16 writes, don't. It moves when the matrices are set up, and so what the fighters' bone chains swing from: on Fountain of Dreams in `matches-b` Mewtwo's tail's chain differs from tick 1584 (a scratch build without the code there compared past it). Since task 5's second part (2026-11-17) the matches the ruleset keeps in the menus' session run it too, as Slippi Dolphin does, and their comparison names it the same way (`menu-tour`'s attract match moves a chain from tick 2667; [the oracle](oracle.md#sessions), "DynamicsFix outside the live matches"). What plays no longer differs (2026-11-17): the live match plays on the console's audio, handed over with the timeline, where it played playback's (its boot's start sound 0xAD at the match's start where the console's menus' last sound plays on, and voices freed and stolen otherwise), and it runs no sound code of playback's.

### Checking it against ssbm-rs

ssbm-rs can't run Slippi Dolphin's netplay set, and doesn't need to here:
