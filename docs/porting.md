# Porting guide

How a function gets from ssbm-rs into melee-hd. Every port follows these rules, so gameplay stays identical and the ledger stays honest.

## What must be exact

melee-hd's target is identical gameplay and identical presentation (what players see and hear), not identical memory; modeling memory itself is ssbm-rs's job. Sarah, 2026-10-21: "the point of this repo is to rewrite idiomatically and preserve identical gameplay", "gameplay plus what players see and hear".

- Every value that can reach gameplay or presentation is exact, bit for bit: positions, states, the random seed's use, damage, timers, inputs, everything drawn or played, and every value any of those reads. A leftover register that steers a DI or an address a game rule reads is gameplay.
- A value may differ from the original only when it's shown, field by field, never to reach gameplay or presentation. The proof goes in [the engine notes](engine.md#uninitialized-values) and the comparer skips the field, naming the reason. A value nothing reads is the simplest case: unknown until written, which the oracle's stale-read check confirms on every diff.
- Exact stays the default: comparing every value against the oracle is the cheap proof that gameplay is identical. Take an exception where exactness costs real complexity or speed, never to move past a difference nobody has explained.
- Simulation state the oracle compares is modelled exactly, leftover and never-written words included (Sarah, 2026-11-12). A word costs nothing, while every exception is a hole in the comparison and a proof that can go stale as the code changes; and leftovers have turned out to be Melee's own behavior more than once (the Ice Climbers' leftover r5 steering DI, Yoshi's powershield timer counting down a grab's address, the item switch freeing the rules' description). A proof that a value never reaches gameplay or presentation is for host-side or presentation state, where exactness is costly (GPU state, the preload cache's internals, the EFB reads under the Slippi ruleset, host buffers).
- Where such a proof stands, make it a tripwire in the code wherever possible: the simulation stops by name if the assumption ever breaks, rather than differing silently. Example: a sleeping fighter's leftover animation tree word (`Fighter::x590`) is kept, answers the original's `!= NULL` tests as the original does, and stops by name if it's ever used as an animation.
- Optimizations follow the same rule: they may change only values proven to reach neither gameplay nor presentation.

## Sources

- **What to compute:** ssbm-rs's port of the function at `melee-hd-base` (`crates/game/src/tu/<unit>.rs` in ssbm-rs). Its generated code spells out what the C leaves to the compiler: which multiply-adds MWCC fused, where values round to single precision, evaluation order, inline copies (`inl_*`), and which functions were transliterated from machine code.
- **Why:** the decomp's C ([doldecomp/melee](https://github.com/doldecomp/melee)'s `src`) for names, structure and intent.
- **When those disagree or ssbm-rs transliterated the machine code:** the assembly listing (`build/GALE01/asm/...` in the decomp build) decides.
- Never port from nikhilunni/melee's source. Its documentation is fine to read.

## Floats

- A value in memory is an `f32`. A value in a register is an `f64` holding what the Gekko holds; `gekko-fp` does all arithmetic on register values (`fadds`, `fmadds(a, c, b)` = a·c + b fused, `frsqrte`, the paired-single `ps_*`).
- Loading from memory is `fp::lfs(bits)`; storing is `fp::stfs` for `stfs`, and `fp::stfs_ftz` for `psq_st` (hardware flushes a subnormal to zero there). Keep the store the original uses.
- Plain Rust float arithmetic is never used in the simulation, even where it would round the same: NaN propagation and the Slippi float mode differ.
- Single-precision scalar ops fill both paired-single lanes (`Ps::splat`); `lfs` does too; `psq_l` with one value puts 1.0 in the second lane.
- Use the game's own math (`melee_sim::math`), never `f32::sin` and friends.

## Names and the ledger

- Give ports idiomatic Rust names and types, and put `#[doc(alias = "OriginalName")]` on the item that ports each original function. One item may carry several aliases (wrappers, inline copies with a symbol).
- When you rename an item, keep its old name findable with `#[doc(alias("OldName"))]`, the list form: the ledger reads `alias = "..."` as a port of the function of that name and refuses a name ssbm-rs has no function for ([rename waves](refactor.md#task-12-wave-3-the-items-names)).
- The generated structs' fields (`game::structs`, from `tools/structgen`) are renamed in structgen's map, `tools/structgen/names.py` (C name to Rust name, by struct; wave 6's step 3 in `names_step3.py`, which it reads), never by hand: structgen puts the old name on the field as `#[doc(alias("x1964"))]` and labels the comparer's differences with both (`min_hitlag (x1964)`), and `tools/structgen/rename_readers.py` rewrites every use. To bring a branch that predates a rename up to it, check the branch out with the new map and structgen (merge them in, or check out `tools/structgen` from the renaming commit) and run `SSBM_RS_LOCAL=... python tools/structgen/rename_readers.py` from the repository's root: it regenerates `structs.rs` and `mirror_gen.rs`, then renames each use rustc reports, round after round of `cargo check --workspace --all-targets`, so only the renamed structs' uses change; then `cargo fmt --all`. It ends by listing lines that still name an old field after a `.` (code `cargo check` doesn't build on this host, or strings such as a test's state path), for a look by hand ([task 18](refactor.md#task-18-wave-6-step-1-fighter-and-cpufighters-names)).
- Some game structs are hand-written instead (`CollData`, `Camera`, `StageInfo`, `GroundParam`, `Ground`, `Fighter`, `Item` and their parts: `game::ft::types`, `game::it::types`; structgen's `OWNED` list in `tools/structgen/config.py`, [design call 3's second half](refactor.md#design-call-3s-second-half-the-owned-structs)). Their fields are named and typed in their source, with each field's place in the original's struct as an attribute: `#[at(0x50)]`, `#[at(0x341, bits(1, 2))]` for a bitfield, `#[at(0x344, union)]` for a C union kept as bytes; the struct's `#[mirror(..)]` declares the compiler's padding, `pad(0x12, 2)` in bytes or `pad(0x4, bits(1, 7))` for the bits a bitfield's byte leaves over. `#[derive(melee_derive::Mirror)]` makes their comparer mirrors from those (labelled `name (alias)` from the field's `#[doc(alias(..))]`), and `game::mirror`'s layout check holds them to the decomp's layout. To own another struct: write it in its subsystem's module from the generated one, field for field in the original's order, keeping each `#[doc(alias(..))]` and moving its names' comments from `names.py` or `names_step3.py` onto the fields; add it to `OWNED` and to the layout check's list; regenerate (`python tools/structgen/structgen.py $SSBM_RS_LOCAL/typegen/types.json crates/melee-sim/src/game`, then `cargo fmt --all`); run the layout check. Improve its types only so every bit pattern the game can store still fits (`c_enum!` keeps any other value as `Other`; a flag byte keeps its unnamed bits; a C union stays bytes with typed views) and each type hashes as the generated one did (fields in order; a sub-struct adds nothing to the hash, an array its length). Check it with the whole state's per-tick hashes on the verify list's replay diffs and a mutation the comparer reports by the new label.
- Where the SDK and the game compute the same thing differently, the SDK version is `sdk_*`.
- Every alias needs a check: a leaf-check test that calls `fns::OriginalName`, or a line in `ledger/checks.txt` naming the system-level check that covers it. Functions replaced by a native subsystem go in `ledger/replaced.txt`, provably dead ones in `ledger/dead.txt`, each with its reason. `cargo run --release -p ledger -- --check` must pass.
- A character that can play a whole match gets its roster fields in its registry entry (`vs`, the `CharacterKind` a match takes it as, and `keys`, below), and a stage its own (below), which the player's command line, `--help` and launcher list. A stage is offered only once its audit finds nothing a match on it reaches unported ([the player](player.md#stages-the-player-offers)).

## Characters

Every character is one entry of the character registry (`game::ft::registry::CHARACTERS`), at its fighter kind (`FighterKind`, the game's own number, the index of the executable's per-kind tables). The game numbers its characters twice: a `FighterKind` (`Fighter::kind`) says which fighter's code and files run, a `CharacterKind` which character a player chose (the select screen's, the rules', the replays' and the save's number; `ftMapping_list`, `pl::player::ckind_ftkind`, takes one to the other). A new character's port writes its module (`game::ft::<character>`: its hooks and its `#[callbacks(Fighter)]` `run` and `#[callbacks(Call)]` `call` dispatch) and fills its entry: its name, `tables` and `callbacks` (its rows of `ft::kind_tables` and `ft::co::kind_callbacks`, which `tools/tables` generates from the executable), the ports of its hooks (`first_init`, `on_load`, `on_death`, `load_special_attrs`, the addresses in its `tables`), `fighter` and `calls` (its module's dispatch functions), `attrs_size` (the bytes of its attributes its hooks copy), `kirby_copy` (Kirby's copy of it, a `ft::kirby::copy::KirbyCopy`: his neutral special on the ground and in the air, the hat put on and taken off, the copy's cleanups when he's KO'd and hit, the copy data's item entries and their `ItKind`s, and whether the hat takes his jumps' other states; `NO_COPY` for a kind without one, Inhale and no hat), `item_words` (the words of its `u` that keep GObjs, which the importer types), and once it can play a match its roster fields: `vs` (the `CharacterKind` a match takes it as) and `keys` (the command line's names). Nothing else lists characters: the callback table takes each entry's `fighter` and `calls`, the fighters' creation, spawn and attribute changes call the entry's hooks, Kirby's copy ability calls its `kirby_copy`, and the roster reads the entries with a `vs`. A new character's copy writes its `ft/kirby/special_<character>.rs` (its addresses and the descriptor its shared special runs over, [task 11](refactor.md#task-11-round-two)) and fills its entry's `kirby_copy`; nothing in `ft::kirby` lists the copies. Code asks which character a fighter is through the enums: `fp.kind == FighterKind::Fox`, `match fp.fighter_kind() { FighterKind::Link | FighterKind::Clink => .. }`, `CharacterKind::Zelda.id()`, and a computer player's kind through `CpuKind` (`cpu.kind == CpuKind::Defensive`); the state keeps the game's numbers, and the original's tables by number stay tables sized by `FighterKind::COUNT` or `CharacterKind::COUNT`. [Task 2](refactor.md#task-2-the-character-registry) has the why.

## Stages

Every stage is one entry of the stage registry (`game::gr::registry::STAGES`), at its ground kind (`GrKind`, the game's own number, the index of the executable's `stage_datas`). A new stage's port writes its module (`game::gr::<stage>`: its hooks and its objects' `#[callbacks(Proc)]` dispatch `run`, and `run_render` if it draws its own), its `StageData` and `StageCallbacks` in `gr::data`, and fills its entry: its name, `data`, the ports of its hooks (`setup`, `load`, `start`: `on_init`, `on_load`, `on_start`; `demo`, which takes the demo's number), `procs` and `renders` (its module's dispatch functions), `vars` (which `GroundVars` member each map's object uses), and once it can play a VS match its roster fields: `vs` (the `StKind` a match on it starts with), `keys` (the command line's names) and `audit` (`None` at first); `shadow` and `touch_line` are the ports of its data's shadow check and line-touch hook. Nothing else lists stages: the callback table takes the hooks by the addresses in `data` and the module's entries from the registry, and the roster reads the entries with a `vs`. Code asks which stage is loaded through the enums: `game.stage_info.grkind == GrKind::Castle`, `match game.stage_info.ground_kind() { GrKind::Kongo => .. }`, `StKind::Battle.id()`; the state keeps the game's numbers. [Task 3](refactor.md#task-3-the-stage-registry) has the why.

## Items

Every item kind is one entry of the item registry (`game::it::registry::ITEMS`), at its kind (`ItKind`, the game's own `ItemKind` number, which the state, the replays and the executable's tables use). A new item's port writes its module (`game::it::kinds::<item>`: its callbacks as arms of its `#[callbacks(Proc)]` `run_event` and `#[callbacks(Pred)]` `run_pred`) and fills its kind's entry: `events` and `preds` (the dispatch functions its logic table's and state tables' callbacks are in, its own module's and any it shares, such as `zako` for the enemies), and `vars` (the member of the item variables' union its code reads: a new member is a line of `it::vars`' `members!`, which adds its `VarsKind`; the importer reads `vars` to take a captured item's union as that member). Nothing else lists items: the callback table takes every entry's dispatch functions, and `vars_kind` reads `vars`. Its tables are the executable's (`it::tables_gen`, generated by `tools/tables/item_tables.py`), read through the enum (`ItKind::logic`, `ItKind::render`). Code names a kind through the enum, never a number: `ip.kind == ItKind::HeartContainer`, `match ip.item_kind() { ItKind::HeartContainer => .. }` (a number a caller knows is a kind: `ItKind::of(kind)`), `spawn::kind_on(game, ItKind::HeartContainer.id())`; the state keeps the number. `the_registry_is_indexed_by_item_kind` and `each_kinds_callbacks_are_in_its_entry` check the entries: a callback of a kind's tables that some item module ports must be in that kind's own entry. [Task 4](refactor.md#task-4-the-item-registry) has the why.

## Rules

Gameplay that differs by ruleset (Vanilla, the Slippi ruleset's codes in 3.19's, 3.16's or 3.14's version, UCF 0.8 or 0.84, players' own codes, the session's ruleset) asks `game::ruleset`, never the rules' fields: `Rules`' fields are private to that module, and each choice is one of its functions, grouped by the hook point it serves (`g.rules.prevents_wobbling()`, `match g.rules.fd_background() { FdBackground::KeepsTheSeed => .. }`, `g.rules.ucf_dashback()`, `g.ruleset.skips_memcard_prompt()`, `g.runs_playback_codes()`). The functions read the versions' tables (`SLIPPI_3_19`, `SLIPPI_3_16`, `SLIPPI_3_14` and `VANILLA` for the determinism fixes, `UCF_0_84`, `UCF_0_8` and `UCF_OFF`, `VANILLA_SESSION` and `SLIPPI_SESSION`), so a port of a code Slippi changed between versions adds an entry to each table and a function that reads it, and the port calls the function where the code injects. A new rule (a mod's, recorded in its replays as a code list is) is a field of `Rules`, its decoding, its tables' entries and its functions, all in that module. `the_tables_choose_as_the_versions_do` holds each table's choices. [Task 5](refactor.md#task-5-the-ruleset-interface) has the why.

## Callbacks

A function pointer the original keeps in its state (an action state's callbacks, a GObj process, a stage's hooks, an item's events and predicates, a render callback, a function `code::call` reaches) stays the original's address in melee-hd's state (`CodeRef`), so the oracle compares it and a snapshot holds it as a number. One table maps each address to its port (`game::code::table`), built once on the first dispatch, a hash lookup per callback.

- **Adding a port's callbacks:** write them where the port is, as arms of its module's dispatch function, a `match` on the address marked `#[melee_callbacks::callbacks(KIND)]` (`Fighter`, `Proc`, `Event`, `Pred`, `Call`, `Render`): `addr::SPECIAL_N_ANIM => g.fox_special_n_anim(gobj),`. The attribute turns each arm into a table entry. A module's dispatch function is reached from the roots in `game::code` through a delegation arm in its parent's (`a if fox::run(g, gobj, a) => {}`, or a body `init::run(g, gobj, a) || special_n::run(g, gobj, a)`); a new module adds one such line to its parent.
- **What an arm may test:** only the address: literals and constants joined by `|`, word ranges (`lo..=hi`), `x if LIST.contains(&x)`, `x if x == E`, and a leading `if addr == X { ..; return true; }`. Anything that depends on the state is a compile error; branch inside the arm's body instead. `crates/melee-callbacks` documents the shapes it reads.
- **An address in two places** stops the table's build by name with both places (`the_callback_table_builds`); there is no first-match order between modules any more.
- **Calling one by address** from game code: `code::run_fighter_cb`, `run_proc`, `run_event`, `run_pred`, `run_render` or `call`; a check that tries each kind uses `code::try_fighter_cb`, `try_proc`, `try_pred`. A fighter callback called through `code::call` with its GObj alone runs as the callback.

## State

- Simulation state is plain data: structs, fixed arrays, `Vec`s that only grow, and `Copy` handles. No `Box<dyn …>`, closures, `Rc` or references inside state, so a snapshot is a clone and a restore is `clone_from` without allocating.
- Objects the original allocates from an `HSD_ObjAlloc` pool or as HAL class objects live in a `hsd::pool::Pool`: a slot stands for the address the allocator model gives its object (the slot last at that address is reused), so identity comparisons behave the same and a handle kept past a free names the original's address ([the engine notes](engine.md#objects-and-identity)). A handle is the slot index.
- Function pointers become `Copy` tokens (enums) that the game dispatches on (see `hsd::gobj::Kinds`).
- Game data from the disc (`melee_data::archive::Archive`) is immutable and shared, not part of the state. A pointer into it is an offset. If the original writes into loaded data during play, that data moves into the state.
- Nothing implicit from the host reaches a tick: not the frame rate, high refresh mode, tick timing, window size, GPU, clocks, disc timing, audio state or rendering results. The state depends only on its start, the controllers' inputs and explicit toggles; a cosmetic toggle may change only state the display pass reads ([architecture](architecture.md#simulation-and-presentation)). Platform events the game polls are explicit inputs.

## Checks

- **Pure functions:** a leaf-check test that runs the function and ssbm-rs's port on special values, random bit patterns and values in the useful range, in both float modes (`tools/leaf-check/tests/math.rs` is the model).
- **Stateful subsystems:** a differential test that sets up the subsystem's globals in ssbm-rs's runtime (`leaf_check::reference()`, scratch memory at `SCRATCH`), drives both implementations through the same random operation sequences, and compares the full structure after every step. Register native functions at fake addresses for callbacks (`tools/leaf-check/tests/gobj.rs` is the model).
- **Systems in play:** the per-tick state comparison with ssbm-rs's `STATE_TRACE` (`docs/oracle.md`).
- After a new test passes, break the port on purpose (one constant, one fused op, one branch) and confirm the test fails. A test that can't fail checks nothing.
- When a difference turns out to come from the test (an input the game never produces), fix the test and say why in a comment. Never loosen a comparison to make a port pass.

## When to stop and ask

- The original's behavior depends on memory addresses, freed memory, or uninitialized values in a way plain data can't reproduce (example: `Archive::unaligned_relocs`).
- ssbm-rs looks wrong.
- A design question this guide and `docs/architecture.md` don't answer.
