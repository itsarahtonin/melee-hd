# Saves

`melee-save` (`crates/melee-save`) reads Melee's save files and writes them as a console does: raw memory card images (`.raw`, ssbm-rs's `.card`) and `.gci` files, judged as the game judges a card it loads, and written byte for byte as the console's card layers write them. It holds no simulation code: the memory card scene, `lbcardgame` and the native save that answers the game's card tasks (milestone 5's task 4, `melee-sim`'s `lb::save`) build on it, and the player's import and export (task 18). Where the player keeps the save is decided ([milestone 5](milestone-5.md#design-calls)); the player isn't wired to it yet.

## The layers

The game moves its save through four layers ([milestone 5](milestone-5.md#how-the-game-uses-the-card)). The crate has the lower three, each following the original's code:

| Layer | Original | Module |
| --- | --- | --- |
| Tasks | `lbcardnew.c`: lists of tasks (mount, check, open, read, write, create, status, delete, format, list snapshots, find a file), each run only when the one before ends with a result its mask takes | `tasks` (the lists `lbcardnew`'s builders make, in `tasks::lists`) |
| HSD card | `sysdolphin/baselib/card.c`, `crypt.c`: a card file of up to nine logical files in checksummed, enciphered blocks with sequence numbers | `state` (the format's arithmetic), `hsd` (each request's commands), `exec` (the command ring), `crypt`, `image` (a file's blocks deciphered without loss) |
| SDK | `dolphin/card`: the card's ID, two copies each of the directory and the block allocation table | `card` |

`melee` has the game's own files (the save's manifest and a snapshot's) and the load (`lb_8001BD34`), save (`lb_8001BE30`) and create (`lb_8001BC18`, `lb_8001BB48` for a snapshot) the game runs; `gci` the `.gci` format.

Every card or HSD call completes at once, as on ssbm-rs's card, whose erases and programs finish immediately; how many calls of `lbCardNew_CompleteNextTask` each task takes is the native save's to model (task 4). Nothing panics on a card's contents: each layer answers with its codes (`CardError`, the HSD layer's results, `lbCardResult` in `tasks::lb`), and `melee::Verdict` sums up a load.

## The save on the card

`SuperSmashBros0110290334`, 11 blocks: a direct-color banner and one indexed icon, so a header of 0x1E40 bytes (comment, banner, icon and palette) and its 0x30-byte digest, then block 0 in the rest of that sector, unused (the save has no file 0, and block 0 stays the zeros the header write left). Then ten blocks, each 0x20 bytes of header (checksum, logical id, sequence number, three entries of the file table) and up to 0x1FE0 of data, enciphered with the header:

| Physical | Holds |
| --- | --- |
| 1 and 10 | The save data (`GmSaveData`, 0x1790 bytes, flags 0: kept twice), both copies rewritten with the next sequence number on each save that changes it |
| 2 to 8 | The seven name tag banks (0x1F2C bytes each, flags 1: once, with a spare) |
| 9 | The spare: a bank's write goes to its stale copy or a free block, and the old copy turns stale, so the banks rotate through the blocks as they change |

A write first verifies what's there: when every block already holds the data at the newest sequence number, nothing is written. Each `CARDWrite` stamps the file's directory entry with the clock and writes the directory again (alternating its two copies, the check code one higher each time), so a save that changes the save data writes the directory twice. The header is verified the same way before a save's status update, which rewrites it (and stamps the entry) only when it differs.

Snapshots are files named by the clock's seconds, one logical file kept once (flags 3), from block 0 on: 32 blocks in the corpus.

## What a load sees

The load mounts the card (`CARDMount`'s checks: the ID's checksum, encoding and serial against the slot's flash ID, both copies of the directory and table), checks it (`CARDCheck`, which rewrites a bad copy from the good one and frees orphaned blocks), opens the file (its status, a read of the header with its digest, a scan of every block, the repair) and reads each logical file. The repair picks each file's newest whole set of blocks, marks older copies of files kept once stale, and for files kept twice clears surplus copies and copies a missing or out-of-step mirror from the other. So a load can write to the card; `melee::load` leaves the card as the game would.

| Verdict | When |
| --- | --- |
| `Loaded { open: 0 }` | The save read |
| `Loaded { open: -0x104 }` | No set of a file's blocks at one sequence number: the newest of each read |
| `NoCard` | No card in the slot |
| `Broken` | The ID, both copies of the directory or of the table, or a file's chain is bad (one bad copy is repaired) |
| `Encoding` | Formatted for the other font encoding (Shift-JIS on a US console) |
| `NoFile` | No save; another game's file of the same name doesn't count |
| `BadFile { hsd }` | The file's block count, header digest or icon address isn't the layer's (`lbCardResult` 3) |
| `Damaged { files }` | A logical file has a block missing or out of step, or one fails its checksum |

A console's slot takes the card's flash ID from the card; ssbm-rs's slot A, which made the corpus, keeps Dolphin's (`DOLPHINSLOTA`), and `Console::ssbm_rs` is that slot.

## Writes

`melee::save` and `melee::create` write as the game's tasks do, and `Card::format` formats as `CARDFormat` does. The clock is an explicit input (`card::Clock`, seconds since 2000-01-01), read wherever the library stamps the directory; `melee::comment` makes the save's comment from it (`lb_8001C658`, English or Japanese). The banner and icon come from the disc (`LbMcGame.dat`'s `MemCardIconData`, one of three banners by unlock state) and are the caller's to give.

A create writes each file's last block whole, so blocks take what follows each file in memory ([Melee's bugs](melee-bugs.md#a-new-card-files-blocks-run-past-their-files)): the next bank's first bytes, and after the seventh bank 0xB4 bytes of the game's memory, which `SaveData::after` carries.

A `.gci` is a file's 0x40-byte directory entry, as the directory holds it, then its sectors. `Gci::from_card` exports one; `Mounted::insert` brings one into a card (melee-hd's own import: the blocks allocated as `CARDCreate` allocates them, the table and the directory written once each); `Gci::folder_name` is Dolphin's GCI folder name (`01-GALE-SuperSmashBros0110290334.gci`).

## The native save on the timeline

`melee-sim`'s `lb::save` runs the game's task lists on the session's card (`CardDevice`, lent to each step like the allocator model): the list's tasks run at once through `tasks::Run`, the card data's memory as the files' buffers, and the time ssbm-rs's card takes passes on the timeline (`CardTime`). Every list starts with the mount, run at once from the list's start, then waits on `lbCardNew_CompleteNextTask` (`hsd_803AAA48`, a wait point on ssbm-rs's console when a card was in at power-on), and ends with the unmount.

A read is a chain of 512-byte segments: the code that asks for it issues the first with interrupts off, up to its DMA, which completes at once on ssbm-rs's card and raises the channel's transfer-complete interrupt (EXI0 TC, OS interrupt 10); its handler issues the next segment in 160 ticks (the deselect, the select again, three commands and the DMA: `clock::CARD_SEGMENT`), and so on, the last segment's handler finishing the transfer. Interrupts never come back on between the segments, so an event that comes due during a read runs at the next segment's boundary, and its interrupt goes ahead of the chain when the OS takes it first (the audio interrupt's, 5) and after the whole chain otherwise (the retrace's, 24; `Clock::card_chain`). ssbm-rs's probe of the boot's load and the scene's probe on five sessions (every interrupt change, EXI transfer, register read, event and interrupt delivery: `$SSBM_RS_LOCAL/research/card-chain`) gives each part's time:

| Part | Time base ticks |
| --- | --- |
| The mount's `CARDProbeEx`, interrupts off | the slot's probe and the ID's (48 with the card settled, `CardDevice::exi_probe_timed`) |
| The mount's first segment: the attach's two probes, `DoMount`'s status commands, the DMA (`MOUNT_FIRST`) | 384, interrupts off |
| The mount's other 79 segments (the ID, both directories, both tables) | 160 each |
| The mount's last handler and callbacks (`MOUNT_TAIL`) | 64, and 8 more the first time an ID passes its checksums (`VerifyID`'s `OSGetFontEncode`, which keeps the answer: `CardDevice::font_encode_known`) |
| A block's read from its step (`BLOCK_FIRST`: the select, three commands, the DMA), then 15 more segments, then its last handler (`BLOCK_TAIL`) | 96, 160 each, 64 |
| `CARDUnmount` at the list's end (`UNMOUNT`) | 24, interrupts off |

| List and outcome | Steps after the mount |
| --- | --- |
| A load that opens the file (intact or damaged) | 23: the check and the open (no transfer), then twenty block reads (steps 2 to 13 and 15 to 22), steps 14 and 23 none |
| A load that finds no file, a full card, or a broken one | 1: the check |
| A probe (`lb_8001C87C`) or a search for another game's file (`lb_8001C2D8`) | 1: the check |
| No card, or one pulled or not settled | none (the mount's failed probe takes a probe's time, below) |

The step counts are ssbm-rs's (`CARD_STEPS=1`, `CALLS=EXIDma,EXIImm,EXISync,hsd_803AAA48`). Until 2026-10-23 the transfers were fitted register reads with interrupts taken at each (`MOUNT_WORK` 1,643, `BLOCK_WORK` 323, `CHECK_WORK` 2 and `LOAD_WORK` 1): their sums came out right wherever a wait ended at an event, but each block was 24 ticks long (the unmount's 24 taken in the last block) and an event due inside a block ran at once; `clock-odd`'s audio frame and `progressive`'s last seven blocks ([the oracle](oracle.md#sessions)) showed both. `lbCardNew_CompleteAllTasks` after each scene is one more wait.

`lbCardNew_ProbeEx` (the memory card scene's probe every frame) and the pad alarm's probes (`lb_8001C600`, `lbSnap_8001D2BC`, at each alarm's time) ask the device: no card, a card not settled (the EXI library answers only three tenths of a second after it first sees one, `__EXIProbeStartTime`: a card in at power-on was first seen by `OSInit`'s `EXIInit`, at the boot's start), or one that answers. A session's card can be pulled and put back at video fields (`Setup::card_pull`, ssbm-rs's `CARD_REMOVE=F,G`; `melee-oracle session --card-pull F,G`). Each probe takes the time of the SDK's `__EXIProbe` on ssbm-rs's console (`CardDevice::exi_probe_timed`, [the engine notes](engine.md#audio)): the channel's status register, again to clear an insertion interrupt, the time base with a card in, and the card's ID read once it answers after a pull. The scene's probe (`CARDProbeEx`) takes 48 ticks with a card that answers (the probe and the ID's own probe), 24 with one settling and 8 with a pulled card's slot empty; the pad alarm's three take 56 with the card in and settled; a task list's mount runs while the channel is attached, when a probe reads the status register alone. With no card at power-on ssbm-rs stands in for the CARD library and none takes time.

## The save written from the menus

The main menu's entry marks the save to write (`lbCardGame_SaveChanges`: the power-on time added to the save's play time, read from the clock through `gmMainLib_8015FC74`'s `lbTime_GetTimeInSeconds`, a 16-tick time base read on the timeline; `dirty` set), and from then on each of the game's own waits runs the writer, `lb_8001CC84` ([the engine notes](engine.md#audio)): the first starts the save's list (`lb_8001BE30` through `dont_inline_helper`: the card's status brought up to date, the comment dated from the clock, `lb_8001C658`, the banner the unlocks pick, `getCurrentIcon`, and the icons), each later one a step of it (`lbCardNew_CompleteNextTask`), and the card indicator draws while it runs (`x10`). The list (mount, check, open, set status, write) runs through `tasks::Run` on a copy of the lent card at its start, which gives its steps: the HSD layer verifies each file's blocks and writes only those that differ. The card takes the list's writes after its last step (`Writer::step_done`), each directory stamp (`__CARDUpdateDir` from a write's callback, `CARDSetStatusAsync`) taking the second the step that makes it ended in, as Camera Mode's save does. Until 2026-10-30 the list ran on the card at its start with the library's clock read once, so a save starting in one second and stamping in the next stamped the directory entry a second early (`tie-sessions/tie4-mid`, its clock at 2000-01-09 23:59:59: the entry's time at 0x202B 777,752 where the console's is 777,753, and the directory's checksums and backup with it).

Its time is the card's work, a step at each of the game's waits after the start (`lb::save::save_steps`, handed to the clock as `CardWork` through `Frames::game_wait`): at the start the comment's `OSGetTime`, the mount's probe (`CARDProbeEx`, the slot's and its ID's) and the mount's segment chain, as a load's (`MOUNT_FIRST`, `MOUNT_SEGMENTS`, `MOUNT_TAIL`, with the font encoding's read the first time an ID gets that far); then, each after its wait point (`hsd_803AAA48`), the check's and the open's step (no transfer), a step for each sector the HSD layer reads (a block's segment chain, `BLOCK_FIRST`, `BLOCK_SEGMENTS`, `BLOCK_TAIL`, as a load's blocks: the open's scan, the status set's header verify, each file's block verifies) or writes (a write's interrupt chain, below; `Layer::log`; a request starts in the call that issues its first transfer, and a later request of the same task in the call its previous one ends in), between two tasks the call that sees the first's last transfer done, runs its callbacks and starts the next (`executeNextTask`, whose requests the HSD layer takes up at its next call), and the list's end, the call that sees the last transfer done, runs the callbacks and unmounts the card (`UNMOUNT`), detaching the channel, so the pad alarm's probes after it take their full time; a pad alarm that fires in that call's wait point, before the unmount, still finds the channel attached and its probes take 24 ticks (`CardWork::unmount`, the detach after the wait point). `2026-10-06_17-37-52`'s save runs whole inside tick 211 and the alarm fires there (ssbm-rs's probe, `write-17-37.log`: the unmount's step waits from 321,973,691, the alarm at 321,975,000 and the step's body at 321,975,048); until 2026-10-24 the writer detached as it handed out that step, and the tick ended 32 ticks late. Each file's result (`lb_8001B6E0`) changes where the original's does: at its request's callback (`fn_8001A0B0`, in the call that sees its last transfer done) and, for the write, when the write task queues it (`taskWrite`, `Run::write_queued`). The list's end leaves the writer idle and a failure noted (`fn_8001CC30` marks the card failed), and the game's side (`Running::card_writer_take`) takes up what the waits did at the scene loop's next tick and before the display pass; a scene's end runs the rest of the list (`lb_8001CDB4`), each step's wait point there.

A write runs inside its step's call, as an interrupt chain like a read's (`Clock::card_chain`, `CardChain::Write`): the HSD layer calls `CARDWriteAsync` from its step with interrupts off, which erases the file's sector (`__CARDEraseSector`, 88 ticks: `clock::CARD_ERASE`), and the `OSRestoreInterrupts` after it lets the card's interrupt in (EXI0's EXI, OS interrupt 9), which ssbm-rs's card raises as the erase ends. From there every transfer ends at once and raises the next interrupt, and interrupts never come back on until the whole write is done. ssbm-rs's probe of three sessions' saves (`$SSBM_RS_LOCAL/research/card-chain/write-17-44.log`, `write-menu-tour.log`, `write-16-58.log`: every interrupt change, EXI transfer, register read, event, interrupt delivery and the CARD library's callbacks) gives each part's time, the same to the tick in all three:

| Part | Time base ticks |
| --- | --- |
| The erase's interrupt: `EXIIntrruptHandler`'s status read and `__CARDExiHandler`'s lock, status read and clear and unlock (`CARD_STATUS`), then `EraseCallback`'s `__CARDWrite` starting the first page (`__CARDWritePage`: the lock, the select, two commands, the 128-byte DMA: `CARD_PAGE`) | 176 + 80 |
| Each of the sector's 64 pages: its transfer-complete interrupt (`TCIntrruptHandler`, `__CARDTxHandler`'s deselect, which ends the program and raises the card's interrupt: `CARD_PAGE_DONE`), then the card's interrupt, whose `BlockWriteCallback` starts the next page | 56, then 176 + 80: 312 a page |
| The last page's card interrupt: its `BlockWriteCallback` calls `CARDWrite`'s `WriteCallback`, which stamps the file's directory entry (`OSGetTime`, `CARD_STAMP`) and writes the directory (`__CARDUpdateDir`: the directory's sector erased from the handler) | 176 + 16 + 88 |
| The directory's sector, as the file's: its erase's interrupt and 64 pages; its last card interrupt's callback (`CARDDir`'s `WriteCallback`, then the HSD layer's) returns at once | 256, 312 a page, the last 56 + 176 |

A sector written is so 40,480 ticks from `CARDWriteAsync`'s entry to the step's return with nothing due, two erases and 128 page programs, 258 interrupts. No allocation table is written (`__CARDUpdateFatBlock` runs only for a create or a delete). An event that comes due during the chain runs as a handler returns, its interrupt ahead of the chain's next when its number is lower: in `2026-10-06_16-58-24`'s save an audio event due at 277,514,677 runs at 277,514,794, as a page's card interrupt returns, and the audio handler's 128 ticks go before the next page's transfer-complete interrupt, so that write takes 40,608 ticks; in `menu-tour`'s, a disc read ending inside the chain is taken at a page's boundary and its interrupt (21) after the whole chain. A status set (`CARDSetStatusAsync`, which the save's list makes only when the header verify finds it changed, `STATUS_SET`) is the directory's part alone, its stamp and erase from the step: counted from ssbm-rs's ports, as no session's save sets a status yet. A file created by the save's list (the table's write, then the directory's) stops as unported: the list creates nothing (it saves only to a file the load opened). By hand, a page's transfer-complete handler 8 ticks shorter makes `2026-10-06_16-58-24` differ in tick 152, `17-13-21` in 559, `17-25-31` in 301 and `2026-10-07_23-52-34` in 64 (each on the timeline), and the directory entry's stamp left out between a write's sectors makes all of those but `17-13-21` differ at the same ticks; the audio interrupt taken after the chain instead of ahead of its next interrupt changes nothing the sessions compare (the next frame is scheduled from the event, at the same boundary), so the clock's unit test checks it with `16-58-24`'s times (`a_card_write_takes_events_between_its_interrupts`).

Until 2026-10-24 writes were fitted as three waits a sector with no time inside (`SAVE_WRITE_WAITS`, `SAVE_WRITE_WORK` 0, `SAVE_OTHER_WORK` 0), 20 ticks short of a write's 40,480 over its two waits but with events taken at the waits instead of the chain's boundaries: eight of the thirteen recorded sessions compared clean through the main menu, and no fit of that shape covered the menu sessions' tick 383, `2026-10-06_16-58-24`'s audio frame at tick 152 and `17-13-21`, `17-25-31` and `2026-10-07_23-52-34` at once ([the oracle](oracle.md#sessions)).

The steps' order and count follow the layers (`melee-save`'s run of the list), and everything else is exact: what's written (the card's bytes, by `melee-save`'s layers), the tasks' order, the comment's date, the results the game reads and when the indicator draws.

## The save created in the memory card scene

On a card with room and no save, the memory card scene asks to create one, and its answer runs the native save's create (`lb_8001C8BC`, `lb::save::card_game_create`, since task 18, 2026-10-28) inside the scene's call: the save's task list started (`lb_8001C658`'s `OSGetTime` for the comment first), then each of its steps after the one before, each after its wait point (`clock_card_work`), as the HSD layer runs a list the game waits on, and the list finished. The create writes each file's last block whole ([Writes](#writes)), so the last bank's block takes what memory holds after the card data, `GmCardData`'s 4 bytes of padding, the power-on state (`gmMainLib_8046B0F0`, 24 bytes) and the pad library's queue (`gmMain_8046B108`, `HSD_PadData[5]`), the queue as it stands at that block's write, the eighth block (`BANK7_WRITE_STEP`), after the pad alarm's polls that came due before it (`after_card_data`, `pad_queue_bytes`). The scene then shows the created save's message (0xC) or the failure's (0xD). `card-sessions/nofile` and the player's `first-run` compare clean from power-on through the creation, and each card after is ssbm-rs's block for block ([the oracle](oracle.md#sessions)).

## Unlock all

`melee_save::unlock::unlock_all` edits a save's data into a complete save without play records ([milestone 5](milestone-5.md#design-calls), Sarah's call of 2026-10-23), once, as the player's Unlock everything does (task 18, 2026-10-28: the settings panel's, the old save kept in the saves folder's backups, Melee restarted from power-on to load it; [the player](player.md#the-player)). It runs no game code and leaves the game nothing to announce, so a session from the edited card is a console's session from a complete save, its random seed untouched; it changes the save's data and nothing else (no code patch, unlike Slippi's unlock code).

It is HAL's own unlock-all, the one `gmMainLib_8015FA34` runs on a debug ROM (`DbLevel` above `DbLKind_DebugDevelop`, deferred to task 19): the features byte to `0xFF`, the eleven characters (`gm_80164F18`) and stages (`gm_8016468C`), every special message (`0x00` to `0x41`) the save hasn't announced announced with the time given and not waiting for its notice (`gm_8017297C`; the Pokémon records `gm_80165084` asks for are among them, so Celebi can come out), and the 300 record trophies' bits (`gm_801741FC`), so no record earns a trophy notice. The design call adds every trophy held, each the save didn't hold given as `Toy_SetUnlockState` gives a first one (one of it, flagged new, counted in `trophy_count`), and every event cleared (`x1A68`'s 51 bits), which is what opens the events (`gmMainLib_8015CEFC`). Records stay: the matches, times, scores, the events' best, the coins, and a special message already announced keeps its time and, if it waits for its notice, its notice. The trophies' classes' marks (`0x4000`) and the categories, which the game sets as notices and records come (class 5 at 200 VS matches), stay as the save had them.
## The album's lists

The Data menu's album ([the oracle](oracle.md#sessions), the album) starts its lists on the lent card with `start_list_run` and steps each itself (`lbCardNew_CompleteNextTask`, `lb::snap_read`) in the tick that starts it: a snapshot's read with its header (`lb_8001BF04`: the open's scan, the header, the file, each block a step as a load's), a delete (`lbCardNew_DeleteSnap`) and a swap of two snapshots' names through a third (`lb_8001C0F4`: three renames, each after an open of the file it renames). The CARD library's own tasks transfer from the call that starts them, the one that sees the open before them done, after which another call starts the next task or ends the list: a rename (`CARDRename`, melee-save's `Mounted::rename`) stamps the file's entry and writes the directory, a status set's chain (`STATUS_SET`); a delete (`CARDDelete`) writes the directory, then from its callback frees the file's blocks and writes the allocation table, with no stamp between (`CardChain::Delete`). A swap's stamps take the clock at their steps, so it runs on a copy of the card first and on the card at its end with those times, as the snapshot's save does. A list the album starts resets the files' results (`resetState`), and a read's bytes reach the snapshot's buffer, comment, banner and icons in the step whose read brings them (the HSD layer's copies, `Run::puts`), which a list stepped over several frames shows. The copy to the other slot (states 15 and 16) reads the snapshot a step a frame and then saves it on the other slot as Camera Mode's save does; between them, and after the save, `lbCardNew_CompleteNextTask` runs once more with no list, which returns the last list's result after its wait point.

## Slot B

A session's console can have a card in slot B too (`Setup::card_b`, ssbm-rs's `--card-b`), with its own pull (`card_b_pull`, `CARD_REMOVE_B`): `lb::save::CardDevice` holds both slots (`CardSlot`: the card, the slot's flash ID, its pull and its probe's state), and every list, probe and chain takes its slot. Slot B's flash ID is the one that formatted its card, as ssbm-rs's runner puts it in the SRAM (Dolphin's `SetCardFlashID`, `Console::ssbm_rs_slot_b`), so a card formatted in slot A mounts in B. Its transfers run as slot A's but for the EXI library's interrupt mask updates (`EXILock`, `EXIUnlock`, `EXISetExiCallback`), 8 ticks each where slot A's take 16, as slot A's channel masks the third channel's interrupt with its own (`CardChain::on`, `SLOT_B_MASK`; ssbm-rs's probe, `$SSBM_RS_LOCAL/research/card-chain/slotb-*.log`):

| Part | Slot A | Slot B |
| --- | --- | --- |
| A read's segment (the unlock and the next segment's lock) | 160 | 144 |
| Its last segment's handler | 64 (a block's), 64 or 72 (the mount's) | 8 less |
| Before the first segment (a block's read: the lock; the mount's: the lock and `EXISetExiCallback`) | 96, 384 | 88, 368 |
| `CARDUnmount` (`EXISetExiCallback`) | 24 | 16 |
| An erase (the lock and unlock) | 88 | 72 |
| A page's card interrupt (the status's lock and unlock, then the page's lock) | 256 | 232 |
| A page's transfer-complete interrupt (the unlock) | 56 | 48 |

Its interrupts are EXI1's (12 and 13), which come where EXI0's do relative to the audio's, the disc's and the retrace's. The boot's probe of slot B (`lbSnap_8001E290`) finds a card in at power-on settled and reads the time base (16 more), and the pad alarm's probes of slot B are a probe like slot A's. The player's console keeps slot B empty (its album says so on a copy or the other slot).

## A card pulled out in the middle of a list

A card comes out or goes in at a video field's start (ssbm-rs's `CARD_REMOVE` and `CARD_REMOVE_B`, a session's `--card-pull` and `--card-b-pull`). While a list has the slot's channel attached (from its mount to its unmount), `EXIAttach` has unmasked the channel's insertion interrupt, so the pull raises it (EXI0's EXT, 11, or EXI1's, 14) and the timeline delivers it with the field's retrace, after the transfers' interrupts and before the disc's and the retrace's (`Frames::card_ext`, `Clock::ext_pending`). Its handler (`EXTIntrruptHandler`, then `__CARDExtHandler`) masks the channel's interrupts (a register read), writes its status register, detaches the channel and the card, and clears the card library's callback (`EXISetExiCallback`, which on slot A masks the third channel's interrupt too): 8 ticks on slot B and 16 on slot A (`lb::save::EXT_HANDLER`; ssbm-rs's probe, `$SSBM_RS_LOCAL/research/card-chain/slotb-pull-saveb.log`). Detached, the slot's probes go on as an unattached slot's, reading the insertion interrupt the pull left.

The list's next step (`lbCardNew_CompleteNextTask`) still waits at its wait point, then its call into the CARD library finds no card: the HSD layer's `CARDFastOpen` for the step's sector fails (`CARD_RESULT_NOCARD`), its callback (`fn_8001A0B0`) gives the request's file (0 for a snapshot's) and the list 15 (`convertSdkResult`), and the list's end task's `CARDUnmount` finds no card either, so the step takes no time past its wait point and nothing unmounts. The card keeps what the steps before wrote: a snapshot's save pulled between its writes leaves the create's allocation table and directory (a file of its full length) and the sectors written so far, the rest of the file's blocks as they were. melee-save's `Run::pull_after` (the HSD layer's `Layer::budget`) runs a list with the card gone after that many of the layer's transfers; `lb::snap_write`'s save reruns its list on the card that way at the step that finds the card gone (`snap_save_lost`), and the album's read ends there with the bytes of the steps before (`snap_task_lost`). Camera Mode's menu then says the save failed (state 8), and the album goes back to choosing a slot.

Only a pull between a save's sector writes or a read's block reads is ported, as the sessions reach (`camera-pull-saveb`, `camera-pull-saveb-late`, `camera-pull-savea`, `album-pull-saveb`, `album-pull-read`, [the oracle](oracle.md#sessions)); a pull before a list's open, create, delete, rename or unmount step, during a transfer (`__CARDExtHandler` ending it), or during a list the game waits on whole (the memory card scene's, the save's writer) stops the simulation, naming it. The boot's `card-sessions/pulled` stays uncompared: it pulls the card at the load's fifth step (`CARD_REMOVE_STEP=5,300`), not at a field's start, which a session's setup can't say, inside a list the game waits on whole.

## A snapshot that doesn't fit

`lbSnap_8001DC0C` compresses the frame's copy (`hsd_803B51C8`) into 256,000 bytes; one that doesn't fit makes it return 0, and Camera Mode's menu goes back to watching (`gmCamera_801A28AC`, state 0), which melee-sim ports as the decomp has it. No session reaches it (2026-10-30, `feat/m5-cards-2`):

- *What it compresses.* On a console, and in ssbm-rs with its renderer drawing (`GX_RENDER`, which reads the copy back into memory), the copy is the frame, 640 by 480 RGB565, written whole. Without a renderer (ssbm-rs's headless runs, the sessions) nothing writes the buffer (`0x811AD6C0` in every run tried), and the snapshot compresses what it held: 248,093 bytes in every history tried, the twelve stages, fifteen characters and, newly, the whole opening movie played before Camera Mode (`try-movie` in the task's notes), so a headless session can't make it overflow.
- *Frames.* HAL's encoder at quality 3 (melee-sim's `hsd::jpeg::encode`) on 333 frames of 40 replays' matches drawn by Dolphin's software renderer (`$SSBM_RS_LOCAL/gx/frames/*/ref`) gives at most 83,162 bytes (median 64,090), a third of the room; with ssbm-rs's renderer drawing (`GX_RENDER=-`), Camera Mode's snapshots on Pokémon Stadium and Fountain of Dreams fit with room to spare (the offer, then the save's question, where the headless runs' 32 blocks find `2026-10-06_17-44-10`'s card full), and render-check's frame of `2026-10-06_17-11-18` takes 11 blocks. Only noise overflows: uniform RGB565 noise compresses to 315,117 bytes, black-and-white pixel noise to 328,429 and eight-color noise to 403,683.

So a player reaches it only with a frame as busy as noise over most of the screen, which no rendered scene seen comes near. This is evidence, not a proof: a frame's content can't be bounded short of rendering every view. The player's console hands the game its own frame (`give_frame`), so its snapshots compress as a console's do.

## The boot's probe of slot B

`lbSnap_8001E290`'s probe at the save data's reset takes 16 more ticks with a card settled in slot B (`audio::boot::console_reset_slot_b`): the time base read. Part 1's mutation (8 instead of 16) isn't caught because the boot absorbs time there: the reset's time is followed by the bank loads, waits whose ends don't move with a few ticks. Measured by adding K ticks to the probe (2026-10-30): with a card in each slot, `camera-slotb` at a drive's pace compares clean to tick 400 for K up to 2,500 (3,000 ends tick 0 12,685 ticks late), and `bootb-sessions/boot-fast` (its first 600 reads at Slippi's fast disc speed, 653 ticks, clean) for K up to 1,000 and at 2,000, with 1,500 ending tick 0 26 ticks late. The probe can take at most 176 ticks more than none (the insertion interrupt read, the time, the ID read), so in these boots no value it can take reaches the game. The windows that do (fast disc, about 1,500) come from where the boot's audio frames fall against its code, which the boot's delay for slot A's card (whole fields, from the clock: `console_boot_delay`) moves; a clock whose boot puts such a window within the probe's 0 to 176 ticks isn't excluded, and none was found. A card put in slot B after the boot isn't the boot's probe: the pad alarm's probes find it (`camera-slotb`'s and `album-slotb`'s are in from power-on).

## Checks

- **leaf-check `card`** runs `crypt.c`'s five functions and the HSD layer's format and request functions against ssbm-rs's on the original's `CardState` bytes: every byte pair through `encryptByte` and `decryptByte`, thousands of buffers through the checksum, encryption and decryption, and random states (the save's layout, a snapshot's, random files of every flags, blocks scattered with stale copies and sequence numbers about to wrap) through each planner and the repair, comparing the state after, every queued command's fields, the active request and the result.
- **The corpus** (`crates/melee-save/tests/corpus.rs`, reading `$SSBM_RS_LOCAL`): the 1,155 card images ssbm-rs's runs left (1,132 of the lockstep campaign, its 6 fault cases, the 13 beside the recorded sessions, 4 in `local/cards`). Every image and each of its 1,212 files reads and writes back byte for byte, and all 11,759 valid blocks are what the layer's block write makes of their contents (1,143 of them written whole by a create). The load judges 1,125 saves loaded, 14 cards with no save, 10 broken, 3 of the other encoding and 3 of ssbm-rs's hand-made layouts damaged; the fault cases as they were made (one bad directory repaired, both bad broken, Shift-JIS refused), and the card whose one good table is the format's, older than the save, broken, as `CARDCheck` finds its chain running into free blocks. The three freshly made saves in the corpus come out of a format and a create byte for byte, card and all, and each of the twelve recorded sessions' cards turns into the next one's through the saves the session made (and, once, a snapshot), all 512 KiB.

Run them with `cargo test --release -p melee-save` and `cargo test --release -p leaf-check --test card` (`SSBM_DISC` set).
