# Engine

How melee-sim models HAL's sysdolphin engine (HSD) and the game's state. [The porting guide](porting.md) has the rules every port follows; this explains the shapes they produce.

## One state, plain data

The original runs everything in one address space: joints, display objects, materials, animations, fighters, items, the scheduler. melee-sim keeps all of it in the simulation state, as the original does, including display objects and their material and texture animation. The display pass that walks them each frame is simulation too, since it spawns particles and draws from the RNG ([architecture](architecture.md)); it emits draw commands for the presentation layer, which never feeds anything back. Keeping display objects in the state costs some snapshot size but keeps one model of what the game's code touches, and rollback stays a clone. A restore is `clone_from`, which the state's types derive field by field (`melee_derive::CloneFrom`), so it reuses the target's vectors and pools rather than allocating; spare storage that isn't state (freed shapes' envelope lists kept for reuse) is marked to stay with the target.

## Objects and identity

- Every object type the original allocates from an `HSD_ObjAllocData` pool lives in a `hsd::pool::Pool` of its own (`FObjs`, the scheduler's GObjs and processes, list nodes, and so on). A handle (`FObjId`, `GObjId`, …) is a slot index.
- Freed slots are reused last in, first out, as the original reuses addresses, so code that compares identities or keys by them behaves the same. Ordering comparisons of addresses would not carry over; none has been found yet, and one that turns up must be reported.
- HAL's class system (`class.c`: `hsdNew`, class info, method tables) becomes typed pools plus a class variant on objects whose class the game overrides: fighters set custom joint, interpolated-joint, shape and material classes, stages and items custom materials, refraction effects custom display objects and shapes. A variant picks the overridden behavior where the original dispatched through its method table. Default classes for loading (`HSD_JObjSetDefaultClass`, `HSD_PObjSetDefaultClass`) are state too. Fighters' materials carry their class (`MObjClass::Fighter`); the fighters' joint class (`ftJObj`, a fighter's model's root) is the joint's class mark (`heap::Class::FtJObj`): the display pass names the root's drawing (`Draw::FighterJoint`), whose position matrix leaves the fighters' depth scale (`ft_jobj_scale`, which only Flat Zone's flat fighters set) for the fighters' shapes' normals in the presentation (`ftParts_JObjMakePositionMtx`, `ftParts_PObjSetupMtx`).
- Shadows (`hsd::shadow`) keep what allocating one changes: a camera and a texture from their pools, references on the joints they cast from, and the texture on the materials' shadow list. Rendering into the texture is the display pass's.
- Reference counts stay where the original keeps them: they decide when objects are freed, and so which slots are reused next.
- A hitbox's victims (`HitVictim::victim`, the user data of what it hit) are a `lb::hitcapsule::Victim`: a fighter or an item by handle, or, for something no longer live, the old address, which nothing follows.
- An item's destroy (`Item_8026A8EC`) can run twice: Mr. Game & Watch's trampoline's animation callback (`itGamewatchrescue_UnkMotion1_Anim`) destroys it once its fighter leaves Fire, clears its fighter and owner again in the item it just destroyed, and returns true, which has the animation process (`Item_80269528`) destroy it again. The GObj's free waits for its process to return (`HSD_GObjPLink_80390228`), so the item is still there the second time, and its destroy's hooks, effects, sounds and camera box run again on it; the port runs both destroys, as the original does, and the trampoline's every exit compares on Mr. Game & Watch's six replays.
- `ftcoll.c`'s damage logs and clank flags (`dmg_log0`, `dmg_log1`, `ftColl_804D6560`) are scratch each fighter's attack collision starts over and nothing reads afterwards; they live in `ft::attack::HitLogs`, outside the mirror, and the logs hold which fighter's hitbox and which hurtbox each hit came from rather than pointers (and a stage device's description); only a device's entry reads what an earlier one left ([Uninitialized values](#uninitialized-values)).

## The object state

`hsd::Objects` holds every HSD pool (FObjs, AObjs, joints, references, display objects, materials, textures, shapes, world positions, cameras, lights, fog, particles, generators and their app-SRTs) and the HSD globals that point into them (the ID table, the current joint, the current lights, the effect banks, the random seed). The original's objects reach each other freely: an animation can bind a joint, a joint owns display objects and references, a shape references the joints it is skinned to, and an update function can do anything mid-animation (a joint's particle event spawns an effect that loads joints and animations). So functions that cross object types take `&mut Objects`, and animation passes it to update functions with no borrow held across the call.

Reference counts follow the original's: a joint stays alive while shapes, constraints or bindings refer to it, so a removal can leave joints for their last reference to free, exactly where the original does.

Recursion follows the original's too (joint trees load along sibling chains), so the simulation needs a deep stack: the tests run it on a thread with one, and the player must as well.

**Decision: a material's compiled TEV is state.** `HSD_MObjCompileTev` builds a material's TEV stages and the constants they read when the material loads (`HSD_MObjLoadDesc`) and when game code asks again (Pokémon Stadium's and Poké Floats' stages after changing a render mode), and keeps them on the MObj (`tevdesc`, `texp`); `HSD_MObjSetup` draws with them every time after, whatever the material's textures have become. So the compile is the original's own state, not something the presentation may redo: melee-sim keeps it on the material as the original stores it (`MObj::tev`, a `hsd::texp::TevDesc`: the stages, last first, each with the texture it samples, and the constants left in the expression list, newest first), set by `mobj::compile_tev` wherever the original compiles, and melee-render draws from it (a material it finds uncompiled is noted as not drawn exactly). Only the display pass reads it; no simulated value depends on it. It matters when game code changes a texture after the compile: Fountain of Dreams' setup (`grIzumi_801CBE64`) turns the water's reflection texture into a shadow lightmap (`flags` `0x103`) after the stage loaded, so the compiled stages still blend the reflection in as the texture it loaded as, and the setup's volatile stages add the shadow stage that multiplies by it. Recompiling from the textures as drawn, as melee-render once did, left the blend out and the water came out a few levels greener than the original's. The comparer checks it against the original's memory with each material (the stages' operations, inputs, registers, swap and constant selections, the texture each samples, and each constant's register and what it reads, which it names by where the pointer lands: the material's colors, a texture's blending or its TEV block's colors), leaving out the map and coordinates of a stage that samples a texture, which `HSD_TExpSetupTev` rewrites from the texture at each setup; the importer reads it from memory the same way.

## Game data

- Archives load from the disc into `melee_data::archive::Archives`, numbered in load order. A pointer into loaded data is a `DataRef` (archive and offset). Archives are shared and immutable, not part of the state.
- The original occasionally writes into loaded data: `JObjLoad` sets the top bit of each particle-list entry it loads, `HSD_ArchiveLocateExtern` patches extern slots, and `psInitDataBankLocate` relocates an effect bank's offsets and sets each command list's draw order. Such writes become state or derived facts on the reader's side, decided per case: a bank is resolved and its kinds fixed as they are read.
- `HSD_IDInsertToTable`'s table, keyed by descriptor addresses, is a map keyed by `DataRef`.
- Fighters' files are an input like every disc load (`game::ft::data::LoadedFiles`): the frontend loads a match's fighters' data, costume and animation files before it starts, as the character select's preloading does (`vs_match::load_fighter_files`), and `Fighter_Create` finds them there by name where the debug VS mode would read the disc mid-tick. In a match that follows the VS mode's menus (`Layout::from_menus`) the character and stage selects have preloaded the fighters' data, costume, effect and animation files and the stage's archive, so their loads read nothing and take nothing from the scene's heap (`LoadedFiles::preloaded`, `vs_match::preloaded_files`). An animation file sits in ARAM, one archive per animation; its ARAM address is part of the input, since fighters keep it to know which animation they last loaded (`Fighter::x5A4`). `Match::start` lays the files out from the ARAM heap's start in slot order, as the debug VS mode's loads do; where a preloaded match puts them is up to the preload cache, which isn't simulated, so a full-state comparison with such a match would see other addresses in those fields. Where `Fighter_Create` would load each file (its data file, its costume, its animation file into ARAM), it loads it on the audio timeline (`Audio::load_file`, `lbFile_8001668C`) with the file's entry number, destination and size: its ARAM address, or for main memory the block the allocator model gives it (0x80000000 where nothing is modelled). A load into main memory also takes its blocks from the allocator model ([the allocators](#the-allocators)). Without a timeline nothing is timed.
- The preload cache's bookkeeping (which files are resident, their load scores) stays outside the simulation.
- A scene's loop takes a poll only when none is queued, as the original's waits for one (`lb_80019894`): its first round ticks on the poll its setup left (the timeline counts the pad alarm's polls while the scene sets up, which a started match queues), and a frontend's input for a step whose poll was already queued would go to the queue, a matter for the frontend.
- An item's block comes from `HSD_ObjAlloc` uncleared (`Pool::alloc_stale`), and item creation leaves its variables union (`it::vars`) as the block's last item left it, so a new item's variables hold that item's bytes until its kind writes them. One rule covers every new item, whatever its block held: each field of its kind's member starts stale (`it::Var`, marked as the item is made, `Item_8026862C`). A stale field keeps the block's value where melee-hd knows it (the same member's, or raw bytes read as the member, their pointers null) and is zero where it doesn't (another member's, whose bytes melee-hd's types don't keep). Writing a field makes it live; the comparer leaves a stale field out; reading one marks a stale read, which the comparer reports (`Cx::stale_read`) and the oracle lists with its tick, so gameplay depending on the leftover bytes (a held needle's owner pointer under a thrown needle's spin, say) can't pass unnoticed. Over the Fox vs Sheik replay's first 1222 ticks nothing reads one. On the Fox vs Marth benchmark match, an Illusion made in tick 7082 in a block a Fox laser had left keeps the laser's word in its never-written `xDD8`, which stays stale for its life.
- The Pokémon and their items (kinds 0xA1 to 0xCF) share the variables' first 0x60 bytes as the Poké Ball's release's (`itPokemonSpawn_ItemVars`: the growth out of the ball, the root bone's motion), and each kind's own fields overlap them where its code wants (Bellossom's `x8` is the bone motion's y). So their variables are one member kept as the union's bytes (`it::pokemon::PokemonVars`), read and written at the decomp's offsets, under the same rule as `it::Var`: each byte is stale until written, a stale byte doesn't compare, and reading one counts a stale read. A bitfield store into a stale byte (Marill's and Cyndaquil's flags) writes only its bits, so those bits compare and the rest stay the block's. A word holding a GObj, joint or data pointer holds a handle, as a fighter's variables do ([Fighters' variables](#fighters-variables)); no Pokémon ported so far keeps one.
- A fighter's mushroom scale joint (`Fighter::x2184`, `fn_800D299C`) loads, the first time a mushroom scales the fighter, from a descriptor in the executable's data rather than an archive (`lbl_803C6FF0`: flags 8, nothing in it, an identity transform). melee-sim builds the joint as `JObjLoad` would from those values and files it in HSD's ID table under the descriptor's address (`hsd::id::address_key`), which nothing looks up.
- Pixels the game renders into only for the screen are presentation. The magnifier's bubbles copy their texture's image descriptor for each player but the first and point it at a buffer from the heap (`ifMagnify_802FC3C0`); only the display pass reads the pixels, so the copy's `image_ptr` is whether there is a buffer (`hud::magnify::TexBuffer`).

## Callbacks

Function pointers in the original (process functions, render callbacks, user-data and object release functions, animation update functions) become `Copy` tokens the game dispatches on, or, where a callback is only passed down a call (an animation update function), a closure parameter that is never stored. The game's functions the scheduler and the particle system call (processes, particle user functions, the new-generator hook) are dispatched through a trait the caller passes down (`gobj::Host`, `particle::Hooks`). Joints' particle callbacks, which efLib sets (an animation's particle events, and a particle list's first display), go through `particle::Hooks` too, so joint animation (`jobj::anim`, `jobj::anim_all`) takes the hooks; the game passes `code::ParticleHooks`.

Render callbacks that only decide what to draw (the HUD's, `game::hud`, and the debug text's, `game::hud::devtext`) are functions returning that decision (`hud::Draw`, `devtext::Draw`), checked against the draw calls the original makes; the name tags' camera (`fn_802FCAC4`) also moves the names as it decides, so it takes the state mutably.

## Uninitialized values

A few original functions read memory or registers they never set, and plain data can't hold what was there. Each case is probed in ssbm-rs to see what the word is in play, then modeled explicitly where it can reach gameplay or presentation, or given the simplest stand-in with the proof that it can't ([what must be exact](porting.md#what-must-be-exact)):

- An FObj channel whose data ends right after its first key hands its update function a stack word instead of a value (`hsd::fobj::Value::Stale`). Over every VS stage and a Final Destination replay, that word was always a RAM address, a tiny negative float; every channel was a joint's branch visibility, which an address hides. Update functions resolve what any address gives where the result doesn't depend on which address, and count the rest as stale reads, which the oracle reports, so a case that matters can't pass unnoticed.
- `resolveIKJoint1` reads two registers and two stack vectors it never set when the effector sits on the chain's root. No joint on the disc has an IK role and no game code gives one, so it can't happen in play; the port counts a stale read if it does.
- `Camera_RequestQuake` never sets a quake's length for a kind other than the four quakes and stores what its epicenter argument's register holds: 0 for a null epicenter, else the epicenter's address. The port stores 0 and counts a stale read when there is an epicenter; no caller passes such a kind.
- The cutscene camera's orbiting eye (`Camera_8002E234`) eases only the parts of the orbit its script set and reads the others (pitch, yaw or distance) from stack slots it never wrote. Master Hand's and Crazy Hand's entrances set orbits that way. The port panics there until a probe of those slots in play decides the model; the camera's other transitions never read a register they didn't set except a fourth transition kind no code sets, which panics too.
- `mpLib_80056C54` adds to a register its caller left (f27) when a walk starts on a wall (a line the walker stood on turned into one). The port takes that value as an explicit parameter, which ftDonkey's port must supply. The ReDead's (`it_802EA804`, under its damage callback `it_802E8CD8` and the item's reaction process `Item_8026A294`) is what every GObj process finds in f27 (`hsd::gobj::PROC_F27`): nothing from `main` down the scene loop to `HSD_GObj_RunProcs`, nor those three functions, writes it, the SDK never clears the FPRs, and none of the playback, bootloader or replays' Gecko codes writes it (a scan of their injected instructions: the character select screen's one load into f27 is in a function that saves and restores it), so it holds the boot's value. Saved calls of the callback and the walk on the ReDead matches have 0.0 there both with every unit in the interpreter and with every port (ssbm-rs boots through the disc's apploader, as Dolphin does without the IPL; its `ps1` holds what a callee's single-precision use left, which the callee's `lfd` restore doesn't reset and the walk doesn't read). A console booted through its IPL wasn't measured. So the walk stops on the wall as a reset length would.
- A stage object's user data (`Ground`, from `alloc_user_data_ground`) is uncleared heap. At stage creation the heap is fresh, zero memory (the captures show it), and Slippi's playback codes zero the block anyway, so a new `Ground` starts as zero; a block reused mid-match (Final Destination's phases 14 and 17) would hold a freed object's bytes, which nothing reads before writing. A typed member of the stage variables compares only its own fields (`game::gr::vars`).
- Final Destination's fog blend (`grLast_8021C500`) hands the fog (`Ground_801C205C`) a stack color whose alpha it never set. Probed over a replay's two background cycles, that byte is the low byte of whatever the frame's earlier calls left in the slot: the caller's stack pointer that `Camera_RequestQuake` saved there in phases 10 and 11 (0x68), a fighter pointer `ftCo_800DF0D0` saved (0x80), or an int-to-float temporary's 0 from `grLast_8021C40C`, so it depends on addresses and on which code ran before. Nothing reads a fog's alpha (`GXSetFog` takes the color's RGB, and the readers of `Ground_801C2090` look at RGB only), so the port sets the RGB, keeps the old alpha and marks it stale (`Fog::stale_alpha`), and the comparer leaves a stale alpha out; any later write of a whole color clears the mark.
- `efLib_Create` leaves an effect's `params` and `user_data` (and two bytes nothing reads) as the pool's slot had them. Every spawn sets the parts its effect's update reads before the update runs, and nothing else reads them, so a new effect starts them at zero and the comparer compares the parts the effect's update reads (`ef::Update::reads_params`); `user_data` is only ever a fighter, which `efLib_Cb_SetRotYAndTransition` reads as a joint's x scale: a fighter's facing is at that offset. Deferred spawns (`EF_QueuedEffect`) likewise compare the words their spawn kind uses.
- Some spawn cases are a character's own and read its fighter: `efSync_Spawn`'s 0x501 reads Peach's part 85, past a shorter parts table, and the action-state callbacks read the character's `mv` words. Spawned for another character, the original reads past the table or another layout; the port stops on the first and reads the same words for the second.
- `mpColl_8004A45C_Floor`, `mpColl_8004A678_Floor` and `mpColl_8004C328_Ceiling` take the floor (or ceiling) at the edge an object stops at, probed at that edge. A few floors in the data run right to left (on Great Bay, Pokémon Stadium and Big Blue), and such a floor can fail to reach its own end; the original then takes line -1 with the flags and normal its stack held. The port leaves those two fields as they were and counts a stale read (`mp::coll::CollStatics::stale_reads`).
- `lb_8001044C` (a dynamic bone chain's swing) turns a joint by writing its rotation from a stack `Quaternion` whose x, y and z come from `HSD_QuatLib_8037EB28` and whose w it never sets, so the joint's `rotate.w` becomes a stack word: probed over Final Destination captures, usually 0, sometimes an address, an int-to-float temporary's 0x43300000 or a float. The joint isn't a quaternion joint (the same code clears `JOBJ_USE_QUATERNION` on it and its descendants), so nothing reads that w. As with the fog's alpha, the port keeps the old w and marks it stale (`JObj::stale_w`), the comparer leaves a stale w out, a whole rotation written clears the mark (copies carry it), and a quaternion read of a stale w counts a stale read, as does a dynamics link taking a stale joint's rotation (`lb_8000FD48`).
- On a flat floor (`x2228_b1`), `lb_8001044C` probes with `lb_800103D8`, which reports a crossing without writing its point when the probe is level and above the floor; the chain then reads that unset point. Only a link lying exactly level above the floor's height gets there; the port stops there rather than read a stale vector.
- `lb_8000FCDC` takes the dynamics links' block from the scene's heap and `lb_8000FA94` sets only each link's joint and next; the rest of a link is written by `lb_8000FD48` and `lb_80011710` before anything reads it, except the last link's dominant axis (`unk_54`), which nothing reads. melee-sim's new block starts at zero, like a fresh heap; the importer gives each link its slot by address so the reset's order matches.
- `mpColl_80043754` returns a register its caller left when a move is so long its substep count overflows (over about 10¹⁰ units, or infinite) and no substep runs. The game never moves that far; the port returns false.
- `ftMapping_list` (a character's fighter kinds) has 33 entries, and the player blocks index it by a slot's character kind, which an empty slot can hold past the table (33 and up). The original then reads the executable's bytes after the table: a padding byte and `player.c`'s message strings, constant data the port carries along with the table (`pl::player::FT_MAPPING`). A kind past those bytes stops the simulation.
- `Player_80031AD0` hands `Fighter_Create` a `plAllocInfo` on its stack and sets two of its third byte's bits, the second fighter's and the transformation's; the other six are whatever the stack held. `Fighter_Create` reads only those two (`x6.b0` in `Fighter_UnkInitLoad_80068914`, `has_transformation` after the spawn), so `ft::create::AllocInfo` holds just them.
- A fighter's blocks (`HSD_ObjAlloc` from `fighter_alloc_data`, the attribute, parts and DObj-list pools) come back uncleared, and `Fighter_Create` leaves about 5,200 of the fighter's 0x23EC bytes, 850 to 910 of its attribute block's and 980 to 1,220 of its parts table's unwritten for Fox and Marth. Creation reads none of them: probed with the blocks filled with zeros and with ones, ssbm-rs ends with every written bit the same. In a fresh heap the rest are zero, and Slippi's playback zeroes the blocks anyway; the debug VS mode's captures show a previous scene's bytes there even in a session's first match (the opening movie's first frame, [the oracle](oracle.md)'s "Debug VS heaps"). melee-sim starts a fighter's blocks at zero, and its check zeroes the reference's (`leaf-check` `fighter_create`). A later read of a field creation leaves unwritten would see zero where a vanilla console sees stale bytes (the decomp notes Luigi's `x222C`); such reads belong to the code that makes them, and each must be checked for it.
- `fn_8016DEEC` (facing players toward their opponents) takes a player's first opponent without measuring its distance, keeping the last distance it measured, or before any, what its caller left in a register (`f26`). The VS scene's entry leaves 0 there in every capture, debug matches' and a replay's alike, so `place_players` passes 0; with three or more players that decides who the first player faces.
- `ftColl_8007A06C` picks the logged hit with the most knockback, above -1; a log whose knockbacks were all NaN or -1 and below would leave the index it reads uninitialized (a register its caller left). Knockback can't go there with the game's data; the port stops.
- Mario's cape, picked up (`it_2725_Logic41_PickedUp`), picks its state by `ftLib_GetGroundAir` on its own GObj: the word at the fighter's `ground_or_air` offset (`+0xE0`) is, in an item, its first dynamic bone set's count, which the cape (it has no dynamic bones) never writes, so it holds what its block held. Probed on a ranked Mario replay, it was zero (a fresh block). The port reads the block's kept value (`Item::xD4_dynamicBones`), which melee-sim's item pool keeps from the slot's last item as the original's does.
- A thrown fighter's hitbox keeps its thrower in a union (`x1064_thrownHitbox.x134`, `Fighter::x1198`) that other hitboxes use for flags, so the mirror holds its bytes; the attack collision stops when it's set, until a throw's port models it.
- Like creation, the debug VS mode's later matches leave a fighter's unused entries (dynamic bone sets past `dynamics_num`, costume textures past their count, a human's computer-player pointers) and an item's unused dynamic bones holding an earlier scene's bytes, which aren't valid handles. Nothing reads them; the per-frame processes' check zeroes them on both sides before it runs (`leaf-check` `fighter_procs`).
- A fighter's address (`ft::Globals::addresses`, its `Fighter*`), the case below, is recorded when `Fighter_Create` allocates it: the allocator model's (below) in a match started from settings with a layout the model knows, else `Settings::fighter_addresses` where the frontend gives them, and from the captured struct's address in an imported state.
- `it_802ADF10` (the blaster's muzzle flash) keeps the pointer `efSync_Spawn` returns as an `s32` in `itFoxBlaster_ItemVars::xDE4[0]`, and code only ever moves it along the six-entry history the shots keep, never reads it otherwise. The port keeps an effect handle there (`[Option<EffectId>; 6]`), which the shift moves as it moves any address: RAM addresses are 0x80xxxxxx, negative as `s32`, and nothing tests or compares them. The importer pairs each word with the effect at its address, a live one or a freed slot (an older flash has usually ended), and the comparer pairs it as it pairs any effect pointer. The address never reaches gameplay, so the rule below for addresses that do doesn't apply; if code that reads the word turns up, the flash carries its address under that rule.
- Samus's grapple beam's spawn (`it_802B7C18`) fills a `SpawnItem` on its stack but never its `x40`, which becomes the item's ignore id (`xAC4_ignoreItemID`); in a CPU match it held a code address a call before had saved. The id is `it::IgnoreId(None)` there: the comparer leaves it out, and reading it (items sharing an id share their hitboxes' victims; the beam has no hitboxes) counts a stale read. The beam's button-sequence swing (`it_802B7160`) copies its hitbox's grabbed-victim-only bit from a stack byte its caller never sets (`x134_4`, byte 0x15 of the caller's `itSamusGrapple_HitboxData`, past the 0x14 bytes of hitbox words it copies), and the bit decides whom the swing can hit, so the port models what the original leaves there. Three frames swing it, and each sets up the links' joint's matrix (`samus_grapple_setup_pos`, `HSD_JObjSetupMatrix`) just before: the shot beam's (`fn_802B805C`, through `it_802B9328`), the bounced beam's (`fn_802B8384`, through `it_802B99A0`) and the hanging beam's (`fn_802B8524`, through `it_802B9CE8`). In the shot, the byte's word lies 0xA8 below `fn_802B805C`'s stack pointer, where `HSD_JObjMakeMatrix`'s `PSMTXConcat` saves `f14` (a double); the game's code never leaves `f14` live at that depth (the compiler saves and restores it, and nothing above the item's process uses it), so the word is 0.0's and the bit is clear. In the other two, `it_802B99A0`'s and `it_802B9CE8`'s frames are smaller (0x88) and the word lies 0x54 below their caller's stack pointer: the top word of `HSD_JObjMakeMatrix`'s frame under `HSD_JObjSetupMatrixSub`'s, its save of `r31`, which holds the joint being set up. That joint is the links' (every link's `jobj` is her `ThrowN` bone), so the bit is bit 19 of `ThrowN`'s address. Nothing writes either word between the matrix and the swing: the callers don't, and what they call runs deeper. The joint is always rebuilt there: the beam's frame runs in her accessory process (`it_802BAC80` from `Fighter_procAccessory`, priority 8), after `Fighter_procMap` (priority 6) has set her root joint's translation and so dirtied her whole skeleton, and only `Fighter_procIK` (priority 7) sets matrices up between them, her legs'; `ThrowN` has a parent, no IK role, no constraint, and its animation binds no object. Watching the words (`WATCH_ADDR`) in ssbm-rs's interpreter and its `--port all` run, names off, the last writes before every swing were those: `PSMTXConcat` writing zeros in `hf-roy-samus-fd-56052455`'s frame 6217 and in the `grapple-samus-bf` oracle match's four shot swings, and `HSD_JObjMakeMatrix` writing `ThrowN`'s address (`0x80D9E900`: the bit set) before its three bounced and three hanging swings ([the oracle](oracle.md#the-characters-own-items)). Under Slippi's playback with Show Player Names on, the heap sits 0x4C0 higher and the address read `0x80D9EDC0`, the bit still set, so it follows the heap's layout, which melee-hd's allocator model gives (`samusgrapple::SwingSlot`: `SavedF14`, and `SavedR31` with the joint's address from the model, which `--heap` checks). A frame that didn't rebuild the joint stops, naming it, as nothing reaches one. leaf-check's `samus_swing` runs all three frames against the machine code. The bit restricts the swing to the fighter she holds, and only while she holds one (`ftColl_80078C70` lets any fighter through while `victim_gobj` is null), so it shows in a hit only when she swings holding someone; the comparer checks it with the hitbox either way. On `hf-roy-samus-fd-56052455` ssbm-rs parts from the recording at frame 6336, after the swing; Slippi Dolphin's playback with resync off parts from it there too, with the same values, so the recording is at fault and the trace is the reference.

When the pick's own calls don't write r5 (a coin flip leaves the seed pointer, compiling the standings `MatchEnd + 0x30`, a charge's release 1), it holds what the pick's last floor check (`mpCheckFloor`) left, and that depends on the last line the search tested: the flags pointer the pick passed when no line got through the joint and flag checks, the pointer to the search's own frame slot it hands `mpLib_8004ED5C` after a level line, or `mpLineIntersection`'s flag (b's end within 0.1 above the line) after a sloped one. The search returns that as data (`Geometry::check_floor_r5`, `mp::FloorR5`, from `search_r5` and `intersect_r5`, which `check_floor` and every other search share unchanged), and the pick turns it into the word with its stack pointer, which the depth it's called at decides (`cpu_floor_r5`, from `r1` at the CPU frame's entry, `cpu_ai::CPU_FRAME_SP`, and the frames on the way). A floor found asks the stage's excluded floors (`ftCo_800A1B38`), a call that leaves its own r5 on the four stages that have them: Big Blue's check (`grBigBlue_801EF844`) leaves 1 when the floor's joint is 33 or 35 to 41, the last of the chain of flags it tests the joint against that it keeps in r5, else 0, and Mushroom Kingdom's the joints' array's address (`Running::excluded_floor_r5`). A filtered search isn't modeled (the filter is a call that leaves its own r5), nor Corneria's and Venom's excluded floors (stage code, off the roster), nor a pick whose depth isn't given (Nana's, whose decision overwrites r5): those leftovers are `Leftover::Unknown`, and a DI reading one stops. The VS DI reads only the word's low byte.

The same rule covers a stack word the computer player's code reads unwritten. Heading for an airborne fighter (`ftCo_800A75DC`), the VS decision asks for the island end beside it when no floor lies below (`ftCo_800A4768`), which fills the vector it is handed (at `r1 + 0x18` in `ftCo_800A75DC`'s frame) only when some end is in reach: with none, as for a target under Final Destination between its two ends, the destination takes the vector as the stack held it. Under the VS decision that slot (`0x804EE920`) is where `ftCo_800A4BEC`'s frame (the target search) began moments before, and nothing called since writes it: its x is that frame's back chain, the VS decision's stack pointer (`0x804EE980`), and its y the frame's link register slot, which only its calls to `ftCo_IsAlly` and `ftCo_800A0F00` fill, with their return addresses (`0x800A4CB4`, `0x800A4D48`), the last of them called. (The common item search stores a distance over the y only once it has an item to go for, which sends the decision to `ftCo_800A866C` instead.) So the destination becomes two tiny negative floats (about -7.2e-39 and -9.5e-40), about the stage's middle at floor height, and the behavior pick reads it. The target search returns that word (`cpu_find_target_lr`), and the VS decision hands the vector to `cpu_toward` (`unset`); a caller that doesn't give one stops. ssbm-rs's ports write their frames' back chains but not their callees' saved link registers, so its `--port all` traces hold an older word in the y, whatever wrote the slot last (0, an island end's height on Final Destination, in `cpu-ics-fd` and `cpu-sweep-samus-fd`); its interpreter (`--port sysdolphin/baselib/perf`, the original code but the trace's hook) leaves the console's word, so those two matches are checked against interpreter traces ([the oracle](oracle.md#the-cpu-ai)).

Off camera on the ground (`ftCo_800AE7AC`, a frame below the VS decision), the decision looks for another island toward the blast zones' middle (`ftCo_800A6FC4`) and, with none, heads for its target the same way (`ftCo_800A75DC`). There the vector's slot (`0x804EE8B8`) lies inside the frame `ftCo_800A6FC4` has just left, where its prologue saved f20 (`stfd f20, 0xA8(r1)`, a double), and nothing writes it between: the destination takes f20's high and low words. Nothing from `main` down the scene loop to `HSD_GObj_RunProcs`, nor `Fighter_procCpu` and the computer player's frame down to `ftCo_800AE7AC`, writes f20, so it holds the boot's 0.0, as f27 does under the ReDead's walk (`hsd::gobj::PROC_F20`), and the destination becomes (0, 0). ssbm-rs's ports don't save registers in their frames, so its `--port all` traces hold an older word there.

The stages' own cases (`feat/cpu-stages3`) read nothing unwritten. `ftCo_800A229C` fills the vector it's handed before every return but 0 (Brinstar's case with the blast zones' bottom middle, the others with the fighter's position), so `ftCo_800AE7AC` hands `ftCo_800A8210` a written vector; `ftCo_800A8210`'s generic case calls `ftCo_800A6700` without setting r4, which still holds that vector, its own second argument; and it reads its result vector only after a search (`ftCo_800A6FC4`, `ftCo_800A6700`) reports filling it. Icicle Mountain's (`feat/cpu-icemt`) likewise: `ftCo_800A229C`'s case returns 2 only after writing the fighter's position, `ftCo_800A6A98` and `ftCo_800A6D2C` read the floor point and line only after `mpCheckFloor` reports a hit (its line starts at -1, and the platform flag is asked only of a line that isn't), and `ftCo_800A8210` reads `out` only after one of them reports filling it. The behavior pick after it starts with its own floor check, so the DI's leftovers don't depend on which case ran.

The approach to an enemy with a Starman or a hammer and the shrunk Yoshi's jump (`feat/cpu-items-last`) read nothing unwritten either. `ftCo_800AB224` hands `ftCo_800BA2E8` its target without testing it after its own null test, but the VS decision sets the target on every frame it allows the approach (`xF9_b1`), and nothing before the walk clears it, so the roll always has one (the port expects it; [Melee's bugs](melee-bugs.md#latent-defects)). The attack's `xF8_b6` is written only on those frames and read stale on others, but it is state the CPU keeps, cleared when its computer player is set up (`ftCo_800A101C`), so the port keeps it as plain data ([Melee's bugs](melee-bugs.md)). All of them are behaviors other than the DI, which runs alone in its frame, so the registers the DI reads (above) are unchanged.


## The allocators

The original's addresses reach gameplay in at least one place (a computer player's DI, Nana's among them, below), and ssbm-rs's memory names every object by its address, so melee-sim models the original's allocators as plain data beside its own pools (`hsd::heap`): the scene's main heap (a Dolphin OS heap: first fit over an address-ordered free list, a block split when 64 bytes or more are left, merged with its neighbours when freed), HAL's memory pieces (`hsdAllocMemPiece`: size classes of 32 bytes that every HSD class and several parts share, each a last-in-first-out free list split from a larger class or from a new block of the heap), and `HSD_ObjAlloc`'s pools (each a last-in-first-out free list grown one object at a time from the heap). It replays every allocation and free the original makes on that heap, in the original's order, so each object gets the address the original's allocator gives it.

- **Where objects ask.** A pool that stands for one of the original's (`hsd::pool::Pool` with a `Kind`: GObjs, processes, animations, list nodes, fighters and their blocks, items and their links, effects, particles, generators, app-SRTs, shadows, the sound objects' user data) asks the model on each allocation and free and keeps each slot's address. Class objects (joints, display objects, materials, textures, shapes, cameras, lights, world objects, fog) ask for a piece of their class's size and keep their class, which `hsdChangeClass` can change and whose counts the model keeps (`ftJObj`, `ftIntpJObj`, `ftPObj`, `ftMObj`, the stages' and items' material classes). Everything else the original allocates asks where the original does and keeps what it needs to give it back: the archives the scene loads into its heap (`lbArchive`: the file's bytes, then its `HSD_Archive`) and the `HSD_Archive` of each Pokémon Stadium transformation file registered from its buffer (`grDatFiles_801C6478`, freed with its entry), the ID table's entries, a joint's `scl` and `envelopemtx`, a camera's inverse view matrix, a texture's palette, TEV stage and animated palettes, a material's material and pixel engine blocks, a shape's envelopes and their list nodes, a shadow's image and list, the scene's lists and buffers (the GObj lists, the text arena, the camera boxes, refraction's images, the dynamics links, the collision arrays and islands, the stage objects' user data and start hooks, the HUD's magnifier buffers and name tags, the background flash, Fountain of Dreams' reflection and Pokémon Stadium's screens and transformation buffer).
- **Expressions.** `expEvaluate` (an RObj's expression, `hsd::robj`) takes its argument buffer, 100 floats, from the heap the first time any expression runs (the static `arg_buf`) and never gives it back; `RObjs::arg_buf` says whether it has, and the importer reads it from memory. Under Slippi's playback nothing evaluates an expression before the match, so the first one in the match allocates it (in the items-on replays, a Fire Flower's model). The pointer outlives the scene whose heap it came from, so a session whose earlier scenes evaluated one would hand the match a buffer in a heap made anew, which melee-hd doesn't model ([Melee's own bugs](melee-bugs.md)). The expression bytecode's stack (`HSD_ByteCodeEval`) is a list of nodes from the list pool, one per value pushed, freed as it's popped: `hsd::bytecode` keeps the values in a local vector and asks the allocator model for each node, so the pool's counts and free list come out as the original's.
- **TEV expressions.** Compiling a material's TEV as it loads (`HSD_MObjCompileTev`) allocates each expression it makes as a piece, then a piece per stage, and frees the operations and the constants no stage reads. The compile is melee-sim's (`hsd::texp`), kept on the material (`MObj::tev`, see [The object state](#the-object-state)), and `hsd::texp_heap` replays its pieces; the material keeps its stages' and constants' addresses until it goes.
- **Stack descriptors.** Some joints load from a descriptor on the stack (a stage object's scale joint), and `JObjLoad` files them in HSD's ID table under that stack address: the entry is real and takes a block, and the next joint loaded from the same frame replaces it. The table keeps such entries under a key naming the frame (`hsd::id::stack_key`), each call passing the stack address its descriptor has in the original (measured from ssbm-rs's calls; `gr::setup::SETUP_FRAME` and each stage's other frames). Stages' spline joints file themselves under their own address (`grMaterial_801C8B68`), which the model gives. Nothing looks either kind up, and the comparer counts only descriptor keys.
- **Lending.** Allocating code runs everywhere and most of it can't reach the state as a whole, so a match's start and each step lend the model to the thread (`heap::Lent`), where `heap::with` reaches it; the step puts it back before it returns. Between steps nothing is lent, and a function run on its own (a leaf check) allocates at address 0. The loan moves the model rather than copying it, so a tick still allocates nothing.
- **Layouts.** Each scene makes its main heap anew (`lbHeap_80015900`), so a match's heap starts empty; what decides its range and contents is the setup the match boots from (`heap::Layout`, `Settings::heap`). The heap runs from the arena past `OSInitAlloc`'s heap descriptors, the audio heap and the preload cache's `Seq` and `Stay` heaps (`lbHeap_803BA380`) to the arena's top, or to the cache's `AllM` heap there when the scene keeps it: the debug VS mode's scenes let it go (`lbDvdPreload_2`), the VS mode's keep it (`lbDvdPreload_3`). Under Slippi's playback (every replay the oracle traces, benchmark matches included) the bootloader raises the console's four heaps to six and takes room for its code list out of the arena before the boot's heaps (`Layout::slippi_playback`: the playback set without Show Player Names, `PLAYBACK_CODE_LIST` bytes and the bootloader's 0xC0; the scene's heap is the OS's third, after the bootloader's and the audio heap), the recording codes lengthen `Fighter` to 0x2600 bytes, the playback codes allocate the replay's code list and the backup of what its codes replace (`playback::CodeListHeap`, from the list's length and its codes' kinds) and the recording codes their buffers in the scene's heap, and the preload cache holds none of the buffers the stages and the HUD would otherwise take from it. A VS match a console without Slippi's codes starts from its menus (`Layout::vanilla_vs`, which `Settings::vs_with` takes for a match with a computer player or an Ice Climber) has the console's four heaps (the scene's the second), no code list, `Fighter` at 0x23EC bytes and the `AllM` heap kept, so its heap is 0x80BD5C40 to 0x811AD6C0 where playback's is 0x80BD8B20 to 0x817F8AC0; and the menus leave what the debug VS mode's boot doesn't (`Layout::from_menus`): the match's stage archive, the stage's buffers (Fountain of Dreams' reflection, Pokémon Stadium's screens and transformation buffer) and its fighters' files in the preload cache (`lbDvd_80017960`), so none of them takes from the scene's heap, and the fog class's size, which the selects' fog set. **Evidence.** ssbm-run (interpreter, only `HSD_PerfSetCPUTime` ported) booted a new save with no Slippi code, its menus driven by `MONKEY_HOLD`, into VS mode's Melee with Ice Climbers on port 1 and Fox on port 2 on Fountain of Dreams, its `CALLS` logging `OSInitAlloc`, `OSCreateHeap` and the OS heap's allocations and frees, and its `STATE_TRACE` the fighters: `OSInitAlloc(0x8065CC00, 0x817F8AC0, 4)`, the scene's `OSCreateHeap(0x80BD5C40, 0x811AD6C0)`, and Popo, Nana and Fox at 0x80C7E000, 0x80CAF900 and 0x80CE1200. Four ways into the match give the fighters the same addresses and the heap the same blocks after every traced tick: through the title screen and the main menu (down to VS mode, Melee) with the saved card, the same with the Kirby picked and dropped before the Ice Climbers, with no card (the boot's two warnings dismissed), and `--mode 2` straight into the character select from the title screen. The preload cache's contents don't reach the scene's heap, and the scene's heap is made anew whatever came before, so the path doesn't matter; the console's default, a new save through the main menu, is the first. The model's start makes the first way's 3,532 allocations and frees of the scene's setup exactly as its log has them, and `melee-oracle vs-heap` ([the oracle](oracle.md)) compares it with memory after each of the trace's ticks; a run on Pokémon Stadium the same way gives 0x80C651C0, 0x80C96AC0 and 0x80CC7FA0, which the model gives too. With the menus' new-save rules the random items are on, whose tables (`it_8026CB9C`, `it_8026CF04`) the scene's heap gives before the stage's collision data; with the item switch set to none in the menus (Custom Rules, Item Switch), as the player's own matches have it (`Settings::vs`), they aren't made, and ssbm-rs's run gives Popo, Nana and Fox 0x80C7DC20, 0x80CAF520 and 0x80CE0E20, six blocks (0x3E0 bytes) lower, which the model gives too, the layout otherwise the same. A computer player changes nothing: the same run with Fox on both ports, the item switch at none and port 2 switched to a computer player on the character select screen (level 1, the default) gives the fighters 0x80C7DC20 and 0x80CC2C00, and the model equals memory after each of its 343 ticks, the computer player playing (`traces/vanilla/menus-cpu-fox-fox-fod.trc`, 2026-10-21). A layout the model doesn't know (Show Player Names on, Slippi's online play) is `None`: the model stays off and addresses come from the frontend or are 0.
- **What the oracle checks.** `melee-oracle diff` starts every match with the model on: the fighters' addresses must equal the trace's as the match starts, and each tick the comparer checks every fighter's address with its other fields. `--heap` also compares the whole model with memory after each tick (the OS heap's free and allocated blocks, every size class of pieces with its free list, every pool's counts and free list, every class's counts), and `--heap-log FILE` writes the model's operations, which tools compare call by call with a log of the original's allocator calls (ssbm-run's `CALLS`). A match from the menus has no replay: `melee-oracle vs-heap` starts it from `Settings::vs_with` and checks the fighters' addresses and the whole model against ssbm-rs's trace of one.

## Fighters' variables

A fighter's character variables (`Fighter::u`) and action state variables (`Fighter::mv`) are unions each character's and state's code reads at its own offsets, so they stay big-endian bytes (`ft::vars::Vars`). A word that holds a GObj or joint pointer (Fox's and Falco's blaster in `u`; their Illusion's ghost, a grab's hold joint and a thrown fighter's thrower in `mv`) holds a handle instead of bytes once code stores one there, and compares as a handle. A state leaves its handles behind for the next, so several words can hold one. The importer types the blaster's word for Fox and Falco and the `mv` words in the states that read them (the hold joint while pulling, holding or pummeling, the ghost in the side special, the thrower while `x21EC` is `fn_800DE798`); elsewhere an imported word stays the bytes memory held. Reading a handle's word as bytes, or bytes as a handle, stops. A narrower write into a handle's word (a held victim's byte flag where its last state kept its thrower) leaves the rest of the word holding part of an address in memory, which melee-sim doesn't have: those bytes are marked stale, the comparer leaves them out, and reading one stops.

The cargo knee bend (`ftCo_CargoKneebend_Anim`) counts its lag down in `mv` x8 after the check that starts the cargo jump, so on the frame the jump starts the count's step lands on the jump's own `mv` x8, the jump multiplier `ftCo_800CB110` has just set (1.0 becomes 0.0); the cargo landing (`ftCo_CargoLanding_Anim`) does the same to the cargo wait's `mv` x4. Nothing reads either afterwards, and the ports keep the order, so the words compare as the original leaves them.

Mewtwo's variables hold his items too: Disable's flash and the Shadow Ball in his hands (`ftMewtwo_FighterVars` `x222C`, `x2230`), which the importer types. His `x2238_shadowBallGObj` is named as a GObj but no code ever stores one: Shadow Ball only tests it before destroying his effects and clears it, so it stays a zero word (`u` `CHARGE_EFFECTS`). Confusion's victim passes through two states in one call (`ftCo_800BCF18`, `ftCo_800BD000`): the capture (`ftCo_MS_CaptureMewtwo`, a state with no animation and no callbacks) and at once the throw (`ftCo_800BD0E8`, whose callbacks do nothing either), held there until Mewtwo's script throws it.

Kirby's variables hold his copy's hat and items (`ftKb_FighterVars`): the hat's model and its DObj list for a hat that sits on his head (Samus's, `hat.jobj`, `hat.x14.data`), or for a copy that dresses him in its costume (Falco's) the costume's two DObj lists, which hold the DObjs it hangs on his own bones, and its animated textures (`x44`, texture handles), with the hat's variants' lookups (`hat.x24.xC`, data handles); and the Charge Shot in his hand (`xA4`) and the blaster (`xB0`). The importer types them for him. Taking a costume off frees both lists but clears only the first word (`ftKb_SpecialN_800EF69C`), so the second keeps the freed list's handle, as memory keeps its address; the textures' handles stay too, and nothing reads either until the next costume writes them. The ID table keeps the costume's joints filed under the bones they stood for, the costume's own parts among them (`ftKb_SpecialN_insert_joint_refs`), after those parts are taken down and freed: the comparer compares a joint ours has freed by its address, as it does one the capture held freed. A hat with dynamic bones (Pikachu's copy's ears) takes his chains' place: his chain count and sets become the hat's, run down the hat's tree to the joints its data names (`ftCo_8009D2A4`), and taking the hat off gives every chain back and leaves none (`ftCo_UnloadDynamicBones`).

A fighter's parts table is a block of `MAX_FT_PARTS` entries of which a character's bones fill the first; melee-sim keeps only those. Samus's grapple beam puts its tip's model in the block's last entry (`parts[0x8B]`, `it_802B7C18`) so her grab boxes ride the tip: her table then grows to the last entry, the ones between unknown, and the importer and comparer take that entry (it stays when the beam goes, pointing at the freed model). The beam's scale (`it_802A2428`, the hookshot's unit) reads its owner as an item: the item's `scl` sits where a fighter keeps its height (`x34_scale.y`), so the beam takes her height times its attributes' scale.

## Seams

Where game code calls a subsystem no port covers yet (the HUD's magnifier, most fighters' own callbacks), it goes through `game::code::call`, by the original function's address with its arguments as register values (`code::Val`), and stops there until that subsystem's port adds its arms. With the feature `stubs` (leaf-check enables it) a check can stand a function in on both sides and compare the calls each side made and their arguments, so the code around a seam is checked before what it calls is ported. The simulation itself never registers a stand-in.

## Effects

An effect (`game::ef`) is an `Effect` in its own pool, the user data of a GObj of class 8 on process link 11 or 12. Spawning goes by id through `ef::spawn` (`efSync_Spawn`), whose variadic arguments are `ef::Arg`s read in order as each case asks (`ef::Args`, which can also decode them lazily from a caller's registers). Which effect files are loaded is state (`ef::Globals::tables`); the files themselves come from the frontend, which loads every effect file it may need with the match's other archives into `ef::Globals::files`, so a sync load (`efAsync_LoadSync`) only registers the file's banks. An async load only asks the disc for a preload that the sync load later takes, so it leaves no state (`ledger/replaced.txt`). Functions other code reaches by address (`efLib_Init`, the loads, `efSync_Spawn`, destroying, pausing and flagging effects) answer `code::call`; Rust callers use `game::ef` directly, and `ef::queue` with a fighter's or item's queue head for `efAsync_Spawn`.

A captured state imports what memory holds: a freed effect, deferred spawn, generator or app-SRT that a pointer outlived (a spawn's `next`, a fighter's queue while `efAsync_QueueFlush` runs, which empties the queue head only at its end, or Final Destination's swaying piece, which keeps its generator after the generator's life ends and reads the app-SRT its removal cleared) becomes a freed slot that pairs by identity, and the display pass's cached first particle of a link, which can name a particle freed since the pass that sorted it, imports as none. A spawn captured inside a flush can hold a live deferred spawn only in the flush's registers; the pool then counts a block no memory reaches, and such a capture can't be imported (the effects' tests keep those out).

The display pass runs after each frame's engine ticks, as the scene loop runs it (`game::render`, `hsd::display`): the max render link's cameras, each camera's passes over the render links its GObj names, and the callbacks there. HSD's joint traversal (`HSD_JObjDispAll` down to `HSD_PObjDisp`) brings joint, skin and envelope matrices up to date, runs materials' texture setup and a specular material's light loads, and spawns a joint's particle list on its first display through `particle::Hooks`; cameras bring their view matrices up to date, and light GObjs take GX slots (`HSD_LObjSetupInit`). Where the original issues GX commands, the pass appends `display::Draw` commands to the frame's output (`Frame::draws`): a camera's start and end, lights, fog, the shadow textures shadowed materials take (which a stage switches joint by joint), the light vector highlight textures take, each specular joint's half vectors, each app-SRT's view as a camera brings it up to date, a stage object's state cache reset, each shape with its joint, display object and transparency pass, and each particle link drawn (docs/player.md lists why each is named where the original reads it). Only the screen render pass is modeled, and the depth-sorted lists stay empty as in Melee. The HUD's render callbacks decide what to draw (`hud::Draw`: a GObj's joints in a pass, or a camera over the links its mask names) and the pass carries the decisions out; the debug text's drawing makes its camera current and hands its glyphs on as `Draw::Text`. Refraction (`lb::refract`) is set up with the VS scene: `LbRf.dat`'s table and a texture chain per entry, whose generated indirect maps and screen copy are the presentation's images (`ImageRef::Refract`, `ImageRef::RefractFrame`); the game camera's callback keeps the screen copy's projection and copies the screen while anything uses refraction. The game camera's callback (`fn_800301D0`) runs its whole pass: the fighters' shadows (`lb::shadow`: each shadow camera is aimed down the stage's shadow light, fitted around its fighter, and renders the fighter's joints offscreen into the shadow's texture, `Draw::Offscreen` and `Draw::ShadowCopy`), then the stage objects, fighters and items in the camera's passes, their materials set up by class (a fighter's through `display::FighterMaterial`, what `ftMaterial_800BF2B8` reads of the fighter being drawn, `HSD_GObj_804D7814`). The screen pass starts in the scene loop (`HSD_StartRender`), so the render pass a frame ends in is the shadows' offscreen one, as in the original. The magnifier's camera (`game::hud::magnify`) clears which players are off screen, then draws each fighter off screen into that player's bubble (`Draw::MagnifierCopy`) and marks the player; the bubbles turn toward their fighter and show or hide the HUD's arrows. The erase color it blends from the stage's colors is the presentation's and isn't computed. The background flash (`lb::bgflash`) draws its color over the screen as `Draw::Quad`s; its fades, wipe and `LbBf.dat`'s color animations (run on its overlay GObj) are simulation. A particle with an app-SRT brings its matrices up to date as the pass draws it, once a display frame, and a one-shot app-SRT freezes (`psDispSubAppSRT`). A text's drawing (`HSD_SisLib_803A84BC`, `hsd::sis::draw`) runs SIS's interpreter: it lays the string out line by line (measuring each, `HSD_SisLib_803A8134`), pushes and pops the text's scale, color, size and alignment on its state stack in the arena, growing it there, and types the text out, stopping at the glyph or line due and counting its delay down; what it leaves is state, and its quads are `Draw::SisText`. A cursor the stack saves (a subroutine's return) is a pointer into loaded data in the original; the stack's record holds a token for it (`SisLib::saved_cursors`), which the capture importer and comparer map to and from the pointer. A text's own render callback isn't ported and stops. Render callbacks no port covers yet stop the simulation (`code::run_render`). A fighter KO'd toward the screen is positioned by the camera (`x2220_b7`): its state keeps its place in the game camera's view, and the fighter's render callback (`ftDrawCommon_80080E18`, in the camera's pass 1) puts it in the world through the camera's inverse view matrix (`Camera_800310B8`), as its position and its root joint's translation; the camera's matrices are simulation, so this is too, and the next tick reads that position. Under the Slippi ruleset, Slippi's FreezeDeadUpFallPhysics codes keep the camera out of the fighter's position (not its joints, [below](#state-the-render-pass-writes)): the callback places only the root joint (`80080E80`), the fighter's position stays where the KO started, and the slide down the camera falls on a speed the state keeps rather than the fighter's (`800D4C1C`, `800D4D68`). A sword's afterimage (`ftCo_800C2600`, Link's, Young Link's, Marth's and Roy's) is `Draw::Afterimage`: the presentation builds its triangle strip from the fighter's afterimage ring, widths and sword attributes as the pass left them; a held sword item's stops. Inside the ported callbacks, these stop: Kirby's own drawing, an item's outline passes, a metal or otherwise swapped fighter material (`ft_804D6580`), and the debug drawings a retail disc never turns on.

## State the render pass writes

The game's logic runs on the pad alarm's 60.00 Hz and video on 59.94 Hz, so about once every 1,001 frames the scene loop finds two polls queued: that round ticks twice and renders once ([the oracle](oracle.md)). Whatever only the display pass writes is then a tick older on the round's second tick, and logic that reads it there sees it twice. Where the doubled rounds fall depends on CPU time: on a console it's the real CPU's, in Dolphin an estimate, and in ssbm-rs, where CPU work takes no time, the alarm overtakes video fields at fixed ticks (on the benchmark matches every 1,001 ticks from tick 1,983 or 1,984, 11 to 14 a match). Slippi's peers each double at their own phase, so Slippi stays in sync by making gameplay independent of the display pass, not by aligning it. melee-hd runs the display pass as simulation exactly where ssbm-rs does (`scene::step_tick` renders when the timeline's round is over; with no timeline, after every tick), so it matches ssbm-rs bit for bit, and two melee-hd peers on the same timeline double together. Rollback must therefore re-run the display pass's state changes on the rounds it re-simulates.

An audit of every render callback a match installs (`GObj_SetupGXLink` and `GObj_SetupGXLinkMax` over `src/melee`: the game camera's `fn_800301D0` with its shadows, stage, fighter, item and particle passes; the magnifier's, the name tags', Fountain of Dreams' and Pokémon Stadium's cameras; the HUD's, the text's and the background flash's callbacks; the scene loop's `HSD_StartRender` and `lb_800195D0`) found these paths from the pass into logic. Line numbers are the decompilation's.

## Audio

`Game::audio` holds:

- HAL's AX driver: its 96 virtual voices, the free and active lists, the handle counter and the sound bank's command stream tables.
- The synth: 64 nodes, the loaded effects, the channel volumes, the volume update list and the music stream's state.
- The AX library's 64 voices, with both copies of each parameter block (the CPU's and the DSP's) and the priority stacks.
- HAL's device command queue (`audio::devcom`), which the music stream, the sound banks and the game's file loads read through.
- The synth's sound banks and their load queue (`audio::bank`), and the audio heap (`audio::heap`, an OS heap) the queue's nodes and the banks' effect groups live in.
- The game's audio library's own state (`lb::audio::LbAudio`): the banks' load states, the crowd's loops, the queued sounds and the mix settings.
- The DSP model.
- The timeline (`audio::clock`).

The sound bank (`smash2.sem`), the sound effect files (`audio/us/*.ssm`) and the music files are game data: `Archive::raw`s that the driver, the bank loads and the stream read by offset.

**Sound banks** (`audio::bank`, `lb::audio`). A scene's entry picks the banks it wants (`lbAudioAx_8002785C` for a match: its characters' and its stage's) and loads them through the synth's queue of up to six loads. Each load reads the file's header into `hsd_SynthSFXLoadBuf`, then its effect group into a block of the audio heap, then its samples to ARAM. When ARAM runs short the library drops banks the scene doesn't want and moves the rest down (`HSD_SynthSFXBankDeflag`, ARAM-to-ARAM through a relay buffer). Where heap blocks land is state: the effect table points into them. The library waits for the loads with interrupts taken, so the audio frames run during the wait. `vs_match::Match::start` loads the match's banks this way when it has a timeline (from the boot's audio setup, below, or a seeded boot state), and otherwise still hands the frontend an `Event::Audio`. Before the match's scene it runs what comes between the boot's last tick and it: that scene's loop ends (its last frame's render and copy, and `HSD_VIWaitXFBFlush`'s wait for the next retrace, after which the scene change reads no clock), and the VS mode loads the announcer's bank (`gm_LoadAnnouncer`), which a bank load the menus left running finishes before. The stage's music then starts as the stage chooses it (`lbAudioAx_80023F28`), its file named by the disc's entry numbers for `/audio/` (`lb::audio::HPS`).

**The boot** (`game::boot`, `audio::boot`, `lb::audio::boot`). Before a match's scene, `Match::start` runs what the boot does to audio (unless `Settings::boot_audio` is off, or what the boot leaves already brought a timeline, as the oracle's seeding does): `main`'s `lbAudioAx_8002838C` (the three sound banks' sizes from the bank table, `HSD_AudioInitMultiPStream` with `AXInit`, `HSD_SynthInit` and the driver's voices, the aux effects' types, the banks' room in ARAM) and the save data's reset of the sound settings, `lbAudioAx_80028690` (the settings handed to the synth, the common bank, the sound bank `smash2.sem` read into the audio heap, the banks every scene keeps, each load waited for). Then the boot's first scene: its preparation preloads its five files through the device command queue, one read's callback starting the next (the preload cache isn't ported; `game::boot::PRELOADS` lists what it reads and where), and its one tick runs. In a replay run that scene is Slippi's playback scene, whose tick wants the replay's characters' and stage's banks, starts loading them, plays its start sound and resumes the channels (`Running::playback_scene_audio`); a match from its settings boots the same way with a first tick that does nothing. The timeline starts at the audio setup, on ssbm-rs's clock: where the boot's unported code takes time (before the setup, between the library's calls, before the first tick and inside the playback scene's tick), it moves to where ssbm-rs's clock has that code end (`audio::boot::BootTimes`, measured from its `AUDIO_TIMELINE` log of a replay's boot, which doesn't depend on the replay); the waits, disc reads, audio frames and interrupts in between run as the clock models them. The game's data that holds something before any code runs is set where the state's defaults are zero (the device command queue's first id, the driver's flags, the synth's ratio); ssbm-rs's console is in stereo. What the boot leaves compares byte for byte with ssbm-rs's boot state on every traced replay (`melee-oracle diff --boot-audio`, [the oracle](oracle.md)).

**DSP models** (`audio::dsp`). In the silent model the DSP's blocks change only through the frame's sync, so a voice plays until it is keyed off and faded, stolen or dropped for the DSP's budget, as in ssbm-rs's `AX=0` runs. In the sample-accurate model the DSP also runs each voice on the block list for its five milliseconds, as ssbm-rs's default runs (Dolphin's AX microcode) do:

- the resampler's position, the accelerator's address through ADPCM frames or PCM, looping, and stopping at the end of the samples;
- the volume envelope and the bus ramps.

What depends on the samples' values is the mix's, and the comparison leaves those words out in that model: the decoder's predictor and history, and the resampler's and buses' last samples. `vs_match::Settings::dsp` carries the model.

**The music stream** runs as in the original. The master clock follows the playing voice through the three boxes, moves the voices' end and loop, and refills the box after the playing one through the device command queue: a disc read into a relay buffer, then on to ARAM. Its samples are the mix's, but the boxes' headers it reads into memory are state. Only in the sample-accurate model do voices advance, so only there does the stream refill.

**The timeline** (`audio::clock`) is ssbm-rs's virtual hardware:

- video fields, the pad sampling alarm, the 5 ms audio DMA and the DSP's answer;
- disc reads, each finishing 20,250 ticks after its command (ssbm-rs's `DVD_LATENCY`, Slippi's fast disc speed), and at a drive's pace that plus its bytes' transfer at 3 MB/s (below);
- ARAM transfers, which finish at once and raise their interrupt;
- the interrupt handlers' costs, and the scene loop's waits and register reads.

Each disc read also sets the disc driver's 10 s timeout alarm, which the read's interrupt cancels. Any event can be taken back before its time (`Clock::cancel`), as on the console: a cancelled or re-set alarm (`set_pad_alarm`, `cancel_pad_alarm`) and a stopped audio DMA (`stop_audio_dma`) leave nothing behind. ssbm-rs before its `ab3cd01` left such events queued, where a read's dead timeout cut a wait short 10 s after every disc read and moved the audio frames after it.

That bug never reached the silent Final Destination and Battlefield timelines the checks use, which start at tick 1500. In the silent model a match makes no disc reads, and the dead events from the loads before tick 0 fell near tick 600. Re-recording them with the fixed ssbm-rs changed only ticks 580 to 602, and their start captures came out identical. It did reach the `AX=1` timeline, whose music refills read the disc every few seconds: its re-recording moved ticks 2855, 5107, 5214, 6608 and 8110.

**When an event runs.** ssbm-rs runs a hardware event at the first wait point at or after its time (`crates/sdk/src/lib.rs`, `service` and `next_due`), never inside an interrupt handler, and the audio DMA's event schedules the next block from when it ran (`crates/sdk/src/hw.rs`, `ai_schedule`: `sdk.after`, now plus the block's ticks). An idle jump lands on the event's time, so a frame picked up there keeps the period; a frame picked up late moves every later audio frame back by its lateness. `Clock::service` does the same (it schedules the next `AudioDma` from `now`), so the timeline must take each event at the same point ssbm-rs does. Its audio frames run 8 ticks after ssbm-rs's events (an event's time here is the frame's start, `__AXLocalProfile.axFrameStart`, which the handler reads after a register read), and its wait points line up with ssbm-rs's on that offset.

An ARAM load is one such place. In ssbm-rs its request (`lbArq_80014BD0`, 56 ticks) and each 4 KB chunk's ARAM interrupt handler (64 ticks, the last chunk's 8) run with interrupts off, and an event that comes due meanwhile runs when a handler returns: 56 ticks into the load and every 64 after. `Clock::aram_load` took the whole load as one step until 2026-10-14, so an audio frame due during a load of several chunks ran only at its end. On Roy's Yoshi's Story replay (`hf-roy-fox-ys-b0c1d064`), in tick 272 a frame due during a 0x2420-byte animation load ran 64 ticks later than ssbm-rs's (a probe on a scratch ssbm-rs branch logged it due at 195,760,702 and run at 195,760,733), and every frame after it with it; in tick 498 the late schedule put a frame 5 ticks after a video field, whose handler ran first and moved it 27 ticks more; and in tick 779 that tick's game code ended before a frame ssbm-rs ran inside it, so the audio state differed. The load now takes its chunks one at a time with interrupts taken between them (every `ARAM_CHUNK` from the load's start, which is ssbm-rs's 56 and 64 on the timeline's 8-tick offset), and every audio frame of the replay's first 820 ticks runs at ssbm-rs's time on that offset. Scheduling the next frame from the last one's due time instead also got past tick 779, but isn't what ssbm-rs does.

The last chunk's handler returns as the load ends, and ssbm-rs takes an event due by then there too (its `service` looks for due events after each interrupt it delivers), so an audio frame due by the load's end starts 8 ticks after it, after the audio handler's register read. On this timeline that is a frame due up to `REG_READ` (8) past the load's end; until 2026-10-15 `Clock::aram_load` left it to the tick's next register read. On Peach's Battlefield replay against Sheik (`hf-peach-sheik-bf-266c777a`), tick 6684 loads two animations as Peach raises her shield (0x5100 and 0x18A0 bytes); the second ends at 4,527,033,209 and the next frame was due at 4,527,033,210. ssbm-rs's `AUDIO_TIMELINE` probe (`tools/run`) logs that frame starting at 4,527,033,217, before the shield's sound starts (`HSD_AudioSFXStartParam`), so the sound waits for the frame after; melee-sim ran it at the tick's closing perf-timer read, after the sound start, and gave the sound a voice that frame freed. `aram_load` now takes such a frame at the load's end. It is rare because three things must line up. A frame comes due inside a tick only when the scene loop's last wait before the tick stops short of it (here at its 10,125-tick cap, 529 ticks before the frame); otherwise the wait runs to the frame and takes it between ticks. Then a load's last chunk must end in the 8 ticks before the frame, about one load in 25,000. And the state differs at once only if an audio call comes between the load and the tick's end; otherwise the frame runs a few ticks late and every later frame with it. A probe over the 231 replays that play to their end (2.5 million ticks: the author's Slippi replays, the benchmark matches and the traced ranked replays) finds the case four times: this one, the author's `Game_20260913T221846` in tick 1582 (which differed there the same way, [the oracle](oracle.md)), and the untraced `Game_20260605T213147` (tick 7280) and `Game_20260605T214312` (tick 6381).

**The game's spins.** A few of the game's loops spin on what interrupts change and pass no wait point. ssbm-rs's SDK hooks each to wait a quarter millisecond a spin until it would end (`crates/sdk/src/lib.rs`, `install`'s `spins`), and melee-sim's clock does the same (`Clock::wait_until`): room in the sound bank load queue (`HSD_SynthSFXLoad`), the boot's bank read, and, since Mushroom Kingdom's music speed-up (2026-10-22), a music start waiting for the stream's box read in flight (`HSD_SynthPStreamStart`, `clock::Wait::StreamIdle`). A song changed while the stream reads its next box reaches that wait; the CPU sweep's free-for-all matches on Mushroom Kingdom found it once in 12 (the speed-up 20 seconds from the end), where it stopped the match before. No oracle match reaches it yet: the stage's oracle match changes its song between reads.

**Decision: the disc's speed is a match setting, and the player reads at a drive's pace.** `vs_match::Settings::disc` (`audio::clock::DiscSpeed`) is plain data the match's audio state keeps, as `dsp` is. `Fast` finishes each read after the latency alone, as ssbm-rs's runs do unless told otherwise: the oracle's traces, ssbm-rs's audio recordings and every replay check were made that way, so `Settings::from_game_info` (and so a replay's match) takes it, and every existing check is unchanged. `Drive` adds each read's transfer at 3 MB/s, as ssbm-rs's window does since its `1fb4da3` (`Hw::set_disc_rate`; `DISC_RATE=3000000` does the same in any run), and `Settings::vs` and the player take it, for a match from its settings and for a replay alike. The reason is the music. HSD starts a song with `AXSetVoiceAddr`, whose parameter block carries the stream's loop flag, and sets the stream's addresses five reads later (the 0x20-byte box header, then the box's 0x4000-byte chunks). At the fast disc's 0.5 ms a read both often fall within one 5 ms audio frame, so `__AXSyncPBs` copies only the addresses to the DSP, the stale loop flag stops the voice at the end of its first box, and the song goes silent about 1.8 s in: on the Fox–Marth benchmark matches on Final Destination and Pokémon Stadium the stream stops moving after tick 109, in ssbm-rs's runs and in melee-sim's alike. At a drive's pace those reads take longer than a frame (any rate under about 13 MB/s does) and the song plays on. Sounds' voices come from the same pool, so the disc's speed reaches the handles game code keeps: a match keeps the speed it was played at, and a replay played at the other speed compares only with a trace made at that speed.

At a drive's pace the boot's unported code waits on its reads where at the fast speed nothing did, so its times there follow the reads instead of fixed times (`audio::boot::BootTimes`): the first scene starts its preload as the boot's bank loads end and ticks a fixed time after its first file's read (`FIRST_TICK_AFTER_PRELOAD`), and Slippi's playback scene waits for the next retrace and then for the preload cache's last file before its audio calls (`PLAYBACK_AFTER_PRELOADS`); at the fast speed those land where the old fixed times did. Two things only the drive's boot reaches are modeled from its run: an audio DMA block that ends while the disc interrupt's handler runs is taken 8 ticks after the handler (`clock::DI_TAIL`), and the pad library's queue, which keeps its five newest polls, holds five at the boot's end after the playback scene's long wait (`game::boot`). With them, ssbm-rs's `DISC_RATE=3000000` traces of the Fox–Marth matches on Final Destination and Battlefield (`local/player/audio-drive-fox-marth-{fd,bf}.trc`, 4,159 and 4,177 ticks) compare with no difference and no stale read from the boot state on (`melee-oracle diff ... --disc-speed drive`), and from melee-sim's own boot with `--boot-audio`, whose boot compares byte for byte, timeline included.

**A console's boot** (`game::session`, milestone 5). A session from power-on runs `main` and the memory card scene on the same timeline, against ssbm-rs's traces of recorded sessions ([the oracle](oracle.md#sessions)), which brought out what a replay's boot never reaches:

- *Where a disc read's time goes.* A read's command from the game's own code goes out 8 ticks into its request (`clock::DISC_ISSUE`), one from a handler's callback (the device command queue's next read) 24 (`DISC_ISSUE_HANDLER`), with 16 more of that handler's work after it (`DISC_ISSUED_HANDLER`); the game's code going on from a wait a read's interrupt ended takes 16 (`DISC_WAKE`). Chained reads come out where they did (the sessions' boot reads match ssbm-rs's to the tick, and the replay boots' compare as before), sequential loads too (8 after the wake's 16); what changed is a read issued from code that didn't wait (the trophies' data after a failed load, 16 sooner), an audio DMA block that ends during a chained read's handler (taken 16 later), and the replay boot's audio reset (`BootTimes::RESET`), whose old time had made up for the first two: the console's boot with no card turns out to reach it with Slippi's playback boot, and Slippi's playback scene's audio calls come 40 after the preload cache's last read (`PLAYBACK_AFTER_PRELOADS`).
- *The retrace handler's tail.* An event that comes due while the retrace interrupt's handler runs is taken `DI_TAIL` (8) after it, as after the disc's.
- *HSD's two frame buffers.* `Clock` keeps `HSD_VIStatus`'s two buffers (`xfb_pending`, `xfb_shown`): a render waits (`HSD_VIWaitXFBDrawEnable`) until one is free, a retrace shows the next copied frame and frees the one shown (`HSD_VIPostRetraceCB`), and a scene's end waits until every copied frame shows (`HSD_VIWaitXFBFlush`). At power-on neither buffer has been drawn, so the first scene's third round renders without waiting, which the replay boot's model (a frame showing, the last one copied waiting) never needed. A match's scene end keeps the replay boot's single retrace.
- *The boot's clock offsets.* A console's boot with a card in slot A reaches the audio setup 17 fields after Slippi's playback boot (the OS's probes of the card from field 2 to 19, `CONSOLE_BOOT_DELAY`) and the save data's reset 56 ticks later than that (`CONSOLE_RESET_EXTRA`); with no card it has no delay and reaches the reset with the playback boot. The random seed is the time base's low word at `main`'s `OSGetTick` (`BootTimes::SEED`, from the clock at power-on). The audio heap starts past the OS's four heap descriptors (`HEAP_START_CONSOLE`), where Slippi's bootloader adds its own.
- *The card.* The native save's task lists and the memory card scene's probes take ssbm-rs's card's steps and register reads ([saves](saves.md#the-native-save-on-the-timeline)).

**Game file loads.** Pokémon Stadium loads each transformation's file during the match.

- *The original's own load* is asynchronous and polled: `grpstadium.c`'s `startLoad` uses `lbFile_80016580` with a callback, and the stage waits for the callback. That is the case `docs/architecture.md` treats as an input. With a timeline, the request goes on the device command queue and its read ends in an interrupt, which runs the callback (`fn_801D4220`); the audio state notes it and the game clears the stage's loading mark before anything reads it (`gr::stadium::take_load_end`), and the cycle's next poll registers the file and marks its materials (`grStadium_801D42B8`). The benchmark matches, which record no ruleset, load this way. Without a timeline the load never ends, so the port stops there.
- *The replays ssbm-rs plays* (Slippi's codes) load it synchronously: the call returns into the codes' memory, as `lbFile_8001668C`, a request on the device command queue and then a loop that waits until the load's callback, taking interrupts as it waits.

`Audio::file_load` models the synchronous load on the timeline, inside the tick, and an audio frame that comes due during the wait runs there. A read into the game's heap moves no bytes here: the loader takes the file from its archives. A match's entry loads its files the same way where the original does: `LbRf.dat`, `PdPm.dat`, the fighters' files, `GmPause.usd`, `SdIntro.dat`, `IfCoGet.dat` and `LbBf.dat` (`Running::disc_load`, timed only when the boot left a timeline).

**The library's tick** (`lbAudioAx_80027DF8`) runs in the scene loop before the processes. It does three things:

- starts the crowd's two loops, follows their volumes, or stops them;
- hands the synth the channels' volumes and the music channels' aux send whenever the settings change;
- runs the queued sounds' timers, or plays the queued sounds all at once when the scene asks.

The VS scene's pause menu holds the music and the match's channels through `lbAudioAx_80024E84`, and its start and end reset the library's mix.

**The aux effects** (reverb and the like, set up by `HSD_AudioSFXSetupAux`) are presentation. Their state lives in a heap of their own, and only the aux callbacks read it. Those callbacks touch only the mix buffers, so the game reads nothing they write. The driver's aux flags are state. `melee-audio` mixes the voices and runs the effects from the mix log (`audio::mix`), presentation output that records what the DSP mixes each frame and every write into ARAM when the presentation turns it on (`docs/player.md`).

**Where game logic reads audio.** Almost every audio call game code makes is fire-and-forget: handles are stored only to stop, pan or bend their sounds later. Game code calls the driver directly in one place only, the reset path's `HSD_DevComIsBusy`. Three paths make the game depend on *when a sound ends*, which is what makes voice lifetimes, the clock and the DSP model simulation:

1. *The crowd* (`melee/sfx/crowdsfx.c`, set up for every match by `fn_8016E730`). Its per-frame state machine (`un_80321A00`) moves on only when the crowd's chant voice has stopped (`lbAudioAx_80023710`, so `HSD_AudioSFXCheck`). A start that fails, for example on a channel the pause menu or camera mode muted, counts as stopped. Whether a fighter's knockback then starts a gasp and awards bonus stat 0x5B (`un_80321EBC`, then `pl_8003FDA0`) depends on that, as does the focus fighter and which crowd sound plays next. A VS match reaches it. Ported (`game::sfx`): its GObj, process and entry points; the fighters' calls into it reach it through `code::call`.
2. *Corneria's and Venom's Star Fox calls* (`Ground_801C54DC`, `grCorneria_801E277C`, `Ground_UpdateStarFoxSequence`). A call's window closes only after its voice line ends, so the sequence lives as long as its lines play. While it lives:
   - the HUD's percents are hidden;
   - a Fox or Falco side taunt can't start a call: starting one draws `HSD_Randi(5)` from the game's RNG and sets the taunt's damage callback;
   - a taunt during a call earns bonus stat 0x8B at the match's end.

   A VS match reaches it. In attract mode, Corneria's intro banter can block a taunt's call. Not ported: it waits for Corneria's and Venom's stage ports, which own the call windows and the sequence; the taunt's side waits for Fox's and Falco's.
3. *The tournament bracket's music* (`gmtou_1.c`'s `fn_8019AF50`) waits for the music stream to stop (`AXDriverCheck`) before starting the winner's. This is menus only.

Other reads change nothing simulated:

- the sound options menu's stereo setting;
- the debug sound test's;
- Kirby's copied voices (`lbAudioAx_800233EC` reads whether `kirbytm.ssm` is loaded, which only picks the sample, and only single-player loads it);
- the stores and checks at fighter and item teardown, whose handles are cleared either way.

Sound objects (`lbAudioAx_800263E8`) end by frame count, not with their voice. Several sound paths draw from the game's RNG whatever audio does, so a port keeps those draws even with audio out:

- a sound object panned at 0 (`fn_80025FAC`'s `HSD_Randi(2)`; fighters' subaction sounds do this);
- `ft_PlaySFX`'s voice ids 332 to 370;
- `ft_800889F4`'s random voice;
- `ftcoll.c`'s hit sounds;
- stages' random music.

Sound objects (`lb::sound_obj`, `lbAudioAx_800263E8`) are GObjs of class 23 on p_link 62 whose user data (`SoundObj`, from `lbl_80433710`) follows one sound: each frame their process (`fn_800262A0`) sets its pan by the behavior the maker chose (the owner's place across the view, or a sweep between two pans over the object's frames) and its volume, until the object's last frame. The fighter script's positional sound command (`ftAction_80072320`) makes them; one made with a pan direction of 0 draws `HSD_Randi(2)` for it. The user data's first word is never written or read, so it isn't modeled.

A state imported from a single captured call has no timeline, and no audio frames run.

## Rulesets in the state

`Game::rules` holds the gameplay toggles, one per rule of the Slippi ruleset (`game::slippi`): `slippi` for the online determinism fixes, `ucf` (off, 0.8 or 0.84), `neutral_spawn`, `prevent_wobbling`, `offscreen_limits` and `freeze_glitch_fix`. Among the determinism fixes the ported code reaches, Final Destination's background cycle keeps the random seed to itself (`grLast_8021AAB0`) and stage objects' user data is zeroed when allocated. UCF's pad buffer, which the code keeps in its own words, is `Game::ucf`. A replay's code list decides the rules (`Rules::from_codes`); the capture importer reads them from the codes applied in the captured game (`Rules::from_memory`). `Rules::player` holds the codes players add themselves ([below](#players-codes)), and `Game::player_code_state` what they keep outside the game's structs.

`Settings::unlocks` (`gm::Unlocks`) is what the memory card's save data has unlocked and recorded, an input a match reads: the characters' and the stages' masks (the card data's `0x1868` and `0x186A`, behind `gmMainLib_804D3EE0`), the first word of the records (`0x1B4C`, which the Poké Ball's rare draws ask about), and whether the unlock-all codes run (Slippi Dolphin's, which patch `gm_80164ABC` and `gm_80164600` to answer 1, and the records' test to answer 1) and Slippi's Disable Special Messages (a `blr` at the records' test, which then answers with the index it is asked; [the player](player.md#items-toggle-whats-left), "The Pokémon"). The only thing a match writes into it is a rare Pokémon's record, its bit; the record's time (from the console's clock) and its other word aren't kept, as nothing in a match reads them. The stage's music choice (`Ground_801C24F8`, from `Stage_80225074`) draws `HSD_Randi(100)` for a stage whose alternate song needs every character unlocked (Final Destination, Battlefield, Yoshi's Story and Pokémon Stadium) or every stage only when the save says so, so the unlocks decide whether a match's start draws from the random seed. `Unlocks::slippi` is everything; the oracle reads them from the trace's boot memory (`Unlocks::from_memory`). The trophies' save-data flags that the stage load's trophy data load (`tyDisplay_8031C2CC`) reads aren't modeled: the load only times its disc read.

`Game::playback` is Slippi replay playback's state in a match a replay drives (`game::playback`): the replay frame it counted, the frame it read last, and while a tick runs, the Slippi device's answers the frontend supplied for it. The pad library's `playback` flag is the playback codes' patch to it.

## Players' codes

## Loaded data the game writes into

- The stage's parameters (`grGroundParam`): the game sets colors and the scale in them, so `game::gr::Globals::param` holds the struct and `stage_info.param` keeps pointing at the archive.
- `grDatFiles_801C6228` sets `rendermode` bit 26 in the materials a stage's `map_head` lists: `Objects::rendermode_patches` records the bits and `HSD_MObjLoadDesc` applies them. A captured state's marks are what memory holds: Pokémon Stadium's transformation file shows them gone while it's registered (its buffer is lbDvd's preload entry 0x7D5, which something writes again after the stage registers it), and its return to the default stage zeroes the first words of that file's header (it hands `grAnime_801C65B0` the file's buffer instead of its archive), so the importer finds such a file through the header copy in the stage's `HSD_Archive`.
- `Ground_801C0800` writes the stage's `ALDYakuAll` scripts into the random stage item's states in the items' data: `game::gr::Globals::yaku_scripts` records them for the items' port.
- `ftData_80085A14` writes each animation's ARAM address into the character's animation table when the animation file reaches ARAM; `Running::anim_aram` works the address out from the file's and the animation's offset instead.
- A fighter's two animation buffers (`x59C` for the action's animation, `x5A0` for a second one, such as the fall's lean) hold the archive last loaded into them, and the figatrees (`x590`, `x598`) point into them. When Nana's second animation is in Popo's main buffer, `ftData_80085E50` copies it from there into her main buffer, not her second, and `x598` points into her main buffer: her next action's animation overwrites it there, and `x598`, unchanged, then points at the same offset into that archive, or past its data. `ft::second::SecondTree` keeps which buffer the figatree is in, and loading either kind of animation into the main buffer moves the figatrees in it to the new archive at the same offsets (`Running::overwrite_main_buffer`), the action's too when a second animation is copied there; the comparer checks a figatree in the main buffer by its offset there. Nothing has read such a figatree yet (a second animation asked for again before another one loads would bind it).
- **Decision: a fighter's animation buffer holds every byte its loads left, modeled as the loads, not the bytes** (the coordinator's, 2026-10-15). In the original each buffer is a 0x8000-byte block of `fighter_x59C_alloc_data` (32-byte aligned, two per fighter from `ftData_80085B10`, freed with the fighter), and nothing but the loads writes it. `ftData_80085CD8` (into `x59C`) and `ftData_80085E50` (into `x5A0`) copy an animation from ARAM with `lbArq_80014BD0`, which moves `OSRoundUp32B` of its size from the animation's ARAM address (its character's animation file plus its offset) to the buffer's start, so up to 31 of the file's next bytes come along; `HSD_ArchiveParse` then adds the data's address (the buffer's plus 0x20) to every relocated word in place. When Nana takes an animation from Popo's main buffer, both functions `memcpy` exactly its size into her main buffer and `lbArchiveRelocate` adds the two buffers' distance to each relocated word, which leaves the archive relocated to her buffer just the same; a copy out of main memory (`memcpy` of its size) isn't ported. So the byte at offset i is the newest load longer than i: its file's byte (header, data with pointers relocated to this buffer, tables, the following bytes), or, past every load, what the block held before: a fresh heap's zeros under Slippi's playback (the traces' buffers read zero before their first load), an earlier scene's bytes after the menus. A load hides every older one no longer than it, so the loads that still show have lengths rising strictly going back. `ft::anim_buf::AnimBuf`, each buffer's slot in `fighter_anim_bufs`, keeps them as up to 16 (archive, length) layers over a fill (`Fill::Zero` where the allocator model's heap is fresh, `Heap::fresh`, else `Unknown`); a block the pool gives again keeps its layers, as the original's keeps its bytes. Each archive keeps its header and the file's bytes after its data block, and an animation's archive also the animation file's bytes up to the next 32-byte boundary (`Archive::parse_in`, `Archive::file_byte`), so `AnimBuf::byte` reads any byte of the buffer from disc data, relocating a word the layer's relocation table names by the buffer's address (the allocator model's; unknown without it). The bound is 16 because filling it takes that many loads in a row each shorter than every one kept: the ten replays of the survey's stop kept at most 12, the benchmark matches at most 14 (Fox against Marth on Battlefield). Past it the oldest, longest layer goes and the bytes past the next become unknown; reading an unknown byte stops the simulation rather than guess. An imported buffer is `Unknown` with no layers. A buffer costs 66 bytes of state.
- Who reads past an animation: `ftAnim_8006F7C8`, `ftAnim_8006F628` (a figatree made for another skeleton) and `ftAnim_80070A10` (the second animation) skip one node of the figatree per part before the part they bind from, without stopping at the node list's end (0xFF), so a part past the figatree's skeleton walks on past its data block. ## Hangs

`mpColl_80046904` repeats its walls, ceiling and floor checks until the squeezes they apply stop changing, which on some geometry never happens: the original hangs. Its body is a function of the collision data, mpcoll's statics and a few locals, so the port watches for an iteration that starts from a state an earlier one started from and halts there instead. A loop can also drift instead of repeating (an ECB squeezed inside out widens a little each time round); the port runs it as long as the original, and checks bound it with a watchdog (`CollStatics::watchdog`, off in play) and skip the original there.

## Checking against ssbm-rs

- `leaf_check::reference()` is ssbm-rs's runtime with the disc's `main.dol` loaded and every port registered; `leaf_check::hsd_reference()` adds an OS heap and HSD's allocators, so ports that build joints, display objects and animations run there.
- Real game states come from ssbm-rs's `STATE_TRACE` (fighters, items, player blocks, stage, camera, RNG and every fighter's joint tree, each engine tick) and, for single game functions, from ssbm-rs's lockstep captures (`CAPTURE=DIR CAPTURE_FUNCS=...`), which save memory and registers at a call.
- A captured state holds words its owner never set: a heap block keeps an earlier object's bytes until each field is written, and some fields are written only in some states. The importer follows what the original reads and represents the rest explicitly. A pointer to a freed object or into nothing (a freed joint, GObj, fighter, item, joint table, camera box or deferred spawn, or a word that was never a pointer) dangles: it gets a slot that stands for the address and compares by address (`Maps::dangling_*`), so the original handing that block to a new object later pairs the new one afresh. A word an object keeps before its owner writes it that points to a live joint (the yo-yo's variables hold its tip link's model, a joint of another GObj the walk meets later) imports as that joint. A joint counts as live only in the heap and starting with its class; a freed one starts with the allocator's link. Arrays filled up to a count (a fighter's costume textures and dynamic bone sets, an item's dynamic bones: `game::ft::counted`) are mirrored up to the count; a count past the array is one never set, and nothing reads such an array. A human player's CPU block (`CpuFighter`) is never filled, so its pointers dangle; an item's ECB box leaves the joint member's last two words as they were; items' links (user data kind 6 on a GObj of class 7, `ItemLink`) aren't modeled and import as raw user data.
