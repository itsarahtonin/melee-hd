# Architecture

melee-hd separates the game's simulation from everything that presents it. The simulation is a library; the player, netplay, tools and bots are frontends to it.

## Simulation and presentation

| Layer | Rule |
| --- | --- |
| Simulation: game state each tick, RNG, physics, action states | Bit-exact with ssbm-rs, checked by [the oracle](oracle.md) |
| Presentation: rendering, audio mixing, HUD drawing, the rendered camera | Free: modern pipelines, any aspect ratio, upscaling |
| Gameplay changes: UCF, Slippi's codes | Rulesets, recorded in replays |
| Cosmetic toggles: widescreen's fighters in the added sides | State only the display pass reads may change, gameplay never: tested |

`melee-sim` steps the game: roughly `step(&mut State, Inputs) -> Events`. Sounds, rumble and anything else that leaves the simulation are events it returns, never calls it makes. Its state is plain data in arenas with indexed handles, so a rollback snapshot is a clone.

Nothing implicit from the host reaches a tick: not the frame rate, the high refresh mode, tick timing, the window's size, the GPU, disc timing or audio. The state depends only on the state the match starts from, the controllers' inputs and explicit toggles, which are state too, so a snapshot carries them and a rollback replays with them. Rulesets and gameplay toggles (Vanilla, Slippi's gameplay codes: `Rules`) decide gameplay. Cosmetic toggles (`Cosmetic`), as Slippi's optional codes stand beside its gameplay codes, change what the display pass draws; drawing writes state (below), so they may change state that only the pass reads, but never gameplay. Each has a test that plays matches with it off and on and finds every tick's output and state the same outside a documented list of display-only fields (`crates/melee-player/src/cosmetic_tests.rs`). The one today draws the fighters the game camera marks off screen, for widescreen's added sides ([player](player.md#resolution-aspect-ratio-and-pipelines)).

In the original, rendering feeds some game state, and the simulation computes those values itself instead:

- **Off-screen damage.** The original tests visibility in the fighter's draw callback against the camera's scissor; the next tick deals 1% per 60 off-screen frames, up to 150%. melee-hd tests it against a fixed 4:3 gameplay camera, as Slippi's widescreen code does, so the rendered view can take any shape. The Slippi ruleset uses fixed stage limits, as Slippi's online play does.
- **Camera snapshots.** The game reads back a camera-mode snapshot's EFB copy to save it. The frontend renders that one image on request and hands it back as an input.
- **Disc timing.** Loads finish outside the simulation; where the original polls a read (Pokémon Stadium's transformations), its completion is an input.

The audio driver's bookkeeping is simulation too. Playing a sound returns a voice handle that game code stores (a fighter keeps its sounds' handles to stop them later): HAL's AX driver builds it from a running counter and the virtual voice it assigns, and which voices are free depends on the driver ending them as their command streams finish, on the audio interrupt's schedule. So melee-sim runs the driver's voice allocation, its counter and its per-audio-frame command processing on the schedule the original's audio interrupts keep relative to engine ticks, and hands what plays to the presentation layer as events; only mixing and output are presentation. That keeps handles bit-exact without treating audio hardware as an input, which rollback could not replay.

Which voices are free depends on more than the driver: an effect plays on one or two of the AX library's 64 voices, which the synth acquires by priority, steals from lower priorities when none is free, and loses when the DSP's cycle budget for a frame runs out, and each loss ends the driver's voice. So the synth's nodes and the AX library's voice allocation are simulation too (`melee_sim::audio`). The schedule is ssbm-rs's: it keeps virtual time that moves at wait points and by a few ticks per time base or register read, and takes interrupts there. In play every audio frame lands at a wait point between ticks, and which ticks it falls between follows from a few clocks (video fields, the 1/60 s pad sampling alarm, the 5 ms audio DMA, the DSP stand-in's answer) and the scene loop's waits, which melee-sim runs as plain data (`audio::clock`). That reproduces ssbm-rs's tick start times and audio frames exactly over whole matches. Three decisions settle what that schedule is:

1. **The clock is ssbm-rs's virtual hardware clock**, not the console's (whose audio interrupts land wherever real CPU time puts them): the same wait steps, register read costs, handler costs and disc latency, so the oracle can check it frame for frame. How fast the disc reads is a match setting a recording carries too: Slippi's fast disc speed, which ssbm-rs's traces of replays use, or a drive's pace, which ssbm-rs's window and the player use and the music needs ([the engine notes](engine.md)).
2. **Both of ssbm-rs's DSP models are a match setting a recording carries**, as ssbm-rs's recordings carry their sound flag: silent (a voice ends only when keyed off, stolen or dropped; ssbm-rs's `AX=0`) and sample-accurate (the DSP also walks each voice through its samples and ends it with them, as the console does; ssbm-rs's default). They end voices at different times, so they hand out different handles. Sample-accurate is the model, for play and for a match from a Slippi replay alike: Slippi Dolphin's DSP played the recording's samples, and ssbm-rs's runs mix by default. Silent stays available as an explicit setting. Its cost falls on the oracle: with voices advancing, audio memory changes every tick, so a state trace with memory is about twice the size of a silent one (about 525 MB for a whole match). Sample-accurate needs only the walk through each voice's samples (positions, loops, ends), not mixing.
3. **Without ssbm-rs's old cancelled-alarm bug.** On the console a cancelled or re-set alarm leaves the OS's queue and a stopped audio DMA raises no more interrupts. ssbm-rs used to leave their events queued, where a disc read's 10 s timeout cut a wait short and moved later audio frames. ssbm-rs fixed that in `ab3cd01`, and the clock takes such events back the same way.

A tick's fighter animation loads out of ARAM take time on it too: an audio frame that comes due during one runs between its 4 KB chunks or as its last one ends, where ssbm-rs's interrupt handlers return ([the engine notes](engine.md#audio), "When an event runs").

The original's display traversal (`HSD_GObjRender` over the GX links, down through joints, display objects and shapes) changes game state as it draws. A joint's particle list spawns its particles the first time it is displayed, the particle system draws from the game's RNG, and setup computes joint and envelope matrices. So the display pass is simulation. melee-sim runs it where the original does, after a frame's engine ticks, and where the original issues GX commands it appends draw commands to the frame's output. The presentation layer turns those commands into GPU work, at any resolution or aspect ratio, but never decides what the pass runs; only an explicit cosmetic toggle the frontend sets does (above). [The player](player.md) describes that layer.

## Frame pacing and high refresh rates

**Decision (2026-10-15): three modes for drawing faster than the game's 60 ticks a second, Off, Interpolate and Extrapolate; Off stays the default until Sarah decides at the player milestone.** The renderer draws a frame from two states and a fraction, (A, B, t): t is how far the frame's display time (when it reaches the screen, as the latency loop estimates it, not when drawing starts) lies between ticks, so any refresh rate works the same way, 240 Hz's four frames a tick, 144 Hz's uneven ones and variable refresh alike.

- **Off** draws tick N as it is, one frame per tick, as the player does today. At a rate that isn't a multiple of 60 its ticks show for uneven numbers of frames.
- **Interpolate** draws between tick N-1 and tick N, joint matrices and cameras blended: every frame lies between two states the game reached, at the cost of up to a tick of added latency.
- **Extrapolate** draws between tick N and a predicted tick N+1: the next tick run ahead of time on a copy of the state with the current inputs held, as rollback predicts, its sounds and other events thrown away. It adds no latency, and because the prediction is the simulation itself, what the game decides on its own (landing, ledges, walls, hitlag, knockback, stage objects) comes out right; it shows the old motion for one frame too many only when an input changes in that tick, and the real frame still arrives on time. Its cost is one more simulation tick and a state clone per tick, whatever the refresh rate; t is clamped to 1, so it never predicts past one tick.

Both blending modes skip true discontinuities (respawns, teleports, ledge snaps, camera cuts) rather than drawing an in-between. Per-frame work (the blend, building the GX stream, drawing) scales with the refresh rate; the simulation's doesn't.

So the base keeps what these modes, and any later temporal technique, need, which is easy to break by accident:

- **Stable draw identities.** The display pass's draws name the objects they draw by handle (`hsd::display::Draw`), so two frames can be matched object for object.
- **Previous transforms.** The presentation can keep the previous frame's joint matrices and cameras, which interpolation, extrapolation and per-pixel motion vectors all need; today melee-render reads them live as the pass left them and bakes them into the GX stream, so the blend goes before that stream is built.
- **A projection-jitter hook** in the renderer, for temporal anti-aliasing.
- **The 3D scene separable from the HUD**, so a temporal or upscaling pass leaves the HUD alone.

**Implemented (2026-10-16): Off and Interpolate, with Off the default.** `melee_render::blend` draws a frame from (A, B, t): B is the latest tick's display pass, drawn live as every frame is, and A is what the tick before's pass left, kept in a `Capture` keyed by the pass's handles (a joint by its handle and the descriptor it was loaded from, a shape by joint, display object and shape, a camera, an app-SRT or a shape by the how-manyth time the frame draws it, a particle by its slot and ID). What blends is transforms only, for what both passes drew: joints' world matrices, decomposed into a rotation (slerped), an upper triangular scale and shear and a translation (both lerped), so a limb turning fast keeps its length midway, which lerping the matrix doesn't (a 60 degree turn shrinks it by a seventh); world matrices rather than local SRTs, since composing those would rerun the hierarchy, which is simulation. Cameras blend their eye (lerped), view rotation (slerped) and projection (lerped); instance joints' views, app-SRT views, shadow cameras' projections onto the stage and particles' position, velocity, size and turn blend too. B's as it is: the HUD's and other 2D cameras (every camera that covers the screen but the game camera), colors, textures and their matrices, materials, lights, text, quads, afterimages, point particles, and what only one pass drew, drawn where B has it through the blended camera. Discontinuities snap: a joint or particle moving more than 40 units in a tick (`blend::JUMP`: Melee's fastest continuous motion, a strong launch or a sword's tip, stays well under it; a respawn or a reused handle doesn't), a joint whose handedness flipped, and a camera whose eye moved more than 60 units or that turned more than 45 degrees or changed its projection's kind. Every blend returns A exactly at t = 0 and B exactly at t = 1, so Off's frames are untouched and a frame at t = 1 is Off's command for command (`crates/melee-render/tests/blend.rs`). The player's pacer ([player](player.md#high-refresh-rates)) draws frames at the display's rate and takes t from each frame's estimated display time; ticks keep Melee's 60 Hz clock, each started just before the first frame that shows it ([just-in-time ticks](player.md#just-in-time-ticks)). The simulation doesn't change: nothing here reaches it.

**Implemented (2026-10-16): Extrapolate.** After each real tick N, `melee_render::predict::Predictor` restores a copy of the match from the real state (`clone_from`, reusing the copy's storage; the archives are shared, and fixed once the match has started), runs one tick on it, display pass included, with the controllers held (the ones the next tick will see when an added delay has read them already; a replay's next frame for a replay) and keeps that pass in a `Capture`: the predicted N+1 is B and the real tick N is A. Frames until the real N+1 draw tick N live, as every frame is drawn, with its transforms blended toward the prediction, the blend run from the capture back to the live pass (`Blend` at 1 - t). So only motion is predicted: the HUD, colors, materials, what exists and what only one pass drew are tick N's, a predicted hit shows neither its damage nor its flash early, and at t = 0 a frame is tick N's own, command for command, Off's frame. t comes from the frame's display time as in Interpolate, clamped to 1, so a late tick holds the prediction rather than running past it; when the real N+1 comes it replaces both, drawn live, with N+2 predicted from it. The blending, the snap rules (a snapped joint, particle or camera stays tick N's until N+1 comes) and the pacer are slice 1's. A tick without a display pass, or a prediction that stops (unported code, which the real tick would reach next), leaves no prediction, and frames draw the real tick as it is. A real tick without a display pass (Melee's render skip, about every 1001 ticks) presents nothing new in either mode, as Off and the console present nothing: its draws would be the tick before's on a state they no longer match ([player](player.md#high-refresh-rates)).

**Mispredictions.** The prediction holds the inputs, as rollback does. When an input changes in tick N+1, the frames before it moved toward the pose the held input gave, and the first frame after it (t near 0: the real N+1 itself) shows the real pose: a correction of at most one tick's motion, and only motion, never a state the game didn't reach. What the game decides on its own (landing, ledges, walls, hitlag, knockback, stage objects) comes out exact, and so does every prediction of a replay or with an added delay, whose next inputs are known.

**No side effects.** The real match is only read (`Predictor::predict` takes `&Match`). The copy's tick hands its sounds, rumble and other events to nobody (its frame goes back to the copy unread), its mix log is off (a clone starts without it and a restore keeps the copy's, `#[clone_from(keep)]` on `Audio::mix`), and the mixer reads only the real match's log. Outside the state the tick touches only the per-thread memo tables, caches that give the same bits for the same inputs, and the allocator model it borrows is the copy's own. `crates/melee-player/src/predict_tests.rs` proves it: it plays the Fox ditto's benchmark replay (1,800 ticks) and a match of the player's own with scripted controllers (900 ticks) twice, one with the player's prediction after every tick, and every tick's state (`StateEq`, as the sync test compares), output (sounds, rumble, draws) and mixed samples are the same, the state also right after each prediction; the replay's 1,799 checked predictions equal the ticks that followed them, bit for bit, and the scripted match's held controllers miss 267 of 899, where its inputs change. Its cost, about 0.5 ms a tick at 1440p, is in the [player](player.md#high-refresh-rates).

DLSS upscaling and frame generation belong to the follow-on repository if anyone wants them: Melee's scenes render natively at high resolutions in about a millisecond, so upscalers save little; frame generation adds latency and invents frames that Extrapolate computes exactly; and NVIDIA's SDK is a proprietary binary, awkward beside GPL-3.0, that wgpu doesn't integrate. An MIT temporal anti-aliaser (FSR's, say) could come to the base later.

## Exactness

The original's float behavior matters only where it differs from IEEE single and double precision: fused multiply-adds, `frsqrte` and `fres` estimates, and paired singles. Those go through `gekko-fp` (melee-hd builds a faster copy of ssbm-rs's, checked against the unchanged one; see [performance](performance.md)); plain arithmetic is native. The game's own `sqrtf`, sin, cos and atan replace platform math, which also makes the simulation agree across platforms. ssbm-rs's two float modes, Hardware (the console) and Slippi (Ishiiruka's x86-64 JIT, which recorded Slippi's replays), both remain available.

## Rulesets

Vanilla is NTSC 1.02 as the console runs it. Slippi adds the codes Slippi tags as affecting gameplay: UCF (0.84, or 0.8 in older replays), neutral spawns, fixed-limit off-screen damage, the camera-independent Pokémon Stadium transition, wobbling prevention, the Ice Climbers' freeze glitch fix, and the online determinism fixes. Lag-reduction codes are not gameplay, and the player's own loop replaces them.

A Slippi replay records the codes it ran, and its rules are the ones those codes make: melee-sim recognizes each code by where it injects and the instructions it runs, and refuses a replay with a gameplay code it doesn't know. Playing a replay back is not a ruleset: it is what Slippi's playback codes do to a match (`game::playback`), with the replay's settings and frames as inputs.

## Saves

The game's save lives outside the simulation in `melee-save`, which reads memory card images and `.gci` files, judges them as the game's load does and writes them byte for byte as the console's card layers do ([saves](saves.md)). The simulation sees a card only through the game's own card code and the native save that answers its tasks, inputs like any other; where the player keeps the file is still to decide ([milestone 5](milestone-5.md#design-calls)).

## Netplay and other features

**Decision (2026-10-14): netplay belongs to a follow-on repository.** Sarah's call: melee-hd is the base, exact, fast and complete, and features built on the game (netplay, training tools, mods) belong in a planned follow-on repository that depends on `melee-sim`. A real consumer decides the library's extension points; hooks designed here for imagined users would mostly go unused. Depending on the library rather than forking it keeps a project's accuracy fixes free.

melee-hd stays rollback-ready all the same, because a base can't be made so from outside: a snapshot is a `clone`, a restore and the ticks replayed after it reproduce the straight run bit for bit and allocate nothing, inputs come from outside the simulation, and state only the display pass sets is recomputed when ticks are replayed ([the engine notes](engine.md)). A sync test checks this every tick ([the oracle](oracle.md#sync-test), `melee-oracle sync-test`): it restores the state from up to 8 ticks before, replays the ticks since and fails on any difference from the straight run, every field of the state compared bit for bit.

The follow-on's netplay is planned as rollback over these snapshots behind two traits, a `Matchmaker` (own server, direct IP, LAN, and Slippi's if the Slippi team agrees) and a wire protocol, with the Slippi ruleset as the online default. Neither repository connects to Slippi's matchmaking servers until the Slippi team is asked.
