# The oracle

melee-hd's simulation is checked against ssbm-rs at the `melee-hd-base` tag, whose ports are verified function by function against the original machine code. The oracle comes before any porting: every ported system is checked by it from its first commit.

## Levels

| Level | Reference | Compares | Status |
| --- | --- | --- | --- |
| Replay events | Slippi replays, which ssbm-rs reproduces | Slippi's pre-frame, post-frame, item and frame-start events, field by field, through the timeline rollback settled on | `melee-oracle compare` |
| Full state | ssbm-rs playing the same replay | The whole state every tick, as the captured-state checks compare it, against ssbm-rs's memory | `melee-oracle diff`: runs from the match's start or a trace tick, stops at the first difference or unported function |
| Captured states | ssbm-rs's lockstep captures (memory at a real call) | A game function run from a real game state on both sides, then the whole state | `melee-capture`: imports a captured state into melee-sim (scheduler, joint trees and everything on them, fighters, the stage) and compares melee-sim's state with memory; round trips on real captures come back clean. leaf-check's `stage` tests run Final Destination's and Battlefield's setup and processes from captures, and its `camera` tests every camera function |
| Leaf functions | ssbm-rs's ports | Math, collision geometry and other code whose inputs and outputs map directly | `leaf-check`: the RNG, math, the SDK's and HAL's vectors, matrices and quaternions, collision geometry, stage and environment collision, controllers and rumble, and HSD's scheduler, animation, joints, references, display lists and shapes |

**Replay events.** ssbm-rs plays the 40-replay smoke set to the same recordings as the original code, with documented entry-frame and off-screen-flag differences in 12. A melee-hd recording is compared with the original replay through ssbm-rs's own comparison (`ssbm_slippi::compare`). This covers VS matches only, and only what Slippi records.

**Full state.** Replays leave out most of the game: menus, single-player modes, stage objects, the camera and most fighter fields. ssbm-rs's runner, with `STATE_TRACE=FILE`, writes the game's raw state at the end of every engine tick: the RNG seed, the player blocks, the stage, the camera, and every fighter, item and fighter joint. `melee-oracle trace-check TRACE REPLAY.slp` checks a trace against the replay it ran: each frame's post-frame fighter positions and percents must equal the trace's, bit for bit, one tick per frame. Two full smoke replays (Dream Land, 13,779 frames; Pokémon Stadium, 13,671) pass with no difference; a full match's trace is about 14 MB. Slippi's pre-frame data doesn't line up as exactly, because it is sampled partway through a tick. Function-level lockstep doesn't carry over, because melee-hd's data no longer has the original's layout.

With `STATE_TRACE_MEMORY=FROM..TO` (ticks, or `1` for all; branch `feat/state-trace-memory`, trace version 3), each tick also carries main memory: the 4 KiB pages that changed since the tick before, XORed with what they held, every nonzero page at the window's first tick. The main thread's stack and the GX FIFO are left out, as neither is game state. A whole match with memory is about 250 MB. The oracle's traces are made with Show Player Names off (`SLIPPI_PLAYER_NAMES=0`, a setting Slippi Dolphin has too): that optional playback code draws the players' names over the match and makes HUD objects for them, which melee-hd leaves to the presentation. The Fox vs Sheik Final Destination replay's is made so, from ssbm-rs's checkout:

```text
SLIPPI_PLAYER_NAMES=0 STATE_TRACE=local/traces/Game_20260129T133652.trc STATE_TRACE_MEMORY=1 \
  target/release/ssbm-run "$SSBM_DISC" --replay Game_20260129T133652.slp --fields 100000 \
  --port all --known local/replays/known/Game_20260129T133652.txt
```

`melee-oracle diff TRACE REPLAY.slp` plays the replay in melee-hd and compares its whole state with the trace's memory after every engine tick, through `melee-capture`'s comparer: the scheduler and everything its GObjs hold (joint trees with their animations, references, display objects and shapes, the fighters, the stage objects), the stage, the camera, HSD's ID table, the audio driver's voices, the player blocks, the pad library, the button maps, the scene loop and its clocks, the VS match's controller, Slippi playback's state, the ruleset and UCF's pad buffer. Objects pair afresh each tick by where they are reached from. It reports the first tick (and its replay frame) that differs with every field that does, or the first function no port covers (`code::unported`), named with its tick. Without options it starts the match from the replay's settings (`Settings::from_replay`), as Slippi's playback codes do, and runs from the trace tick that ran the match's first engine tick. With `--from TICK` it imports the trace's state at the end of that tick through `melee-capture`, compares the import back with the memory it came from, and plays on from there; `--against TICK` compares the import with a later tick's memory instead, which shows the comparison telling states apart. `trace-info`, `trace-dump` and `trace-world` inspect a trace with memory.

On the Fox vs Sheik Final Destination replay, the match's start stops before the first tick at the debug text's GObj (`un_802FF78C`, the HUD's). Taken up from any tick, the import compares back with no difference (ticks 1, 200, 2000 and 6000 checked), and the next tick stops at the first process no port covers: the HUD's (`if_802F73C4`) at tick 2, and `fn_800204C8` (a priority-0 process on p_link 22) from tick 201 on. The four-player Final Destination replay with two Foxes (`Game_20260531T174953`, traced the same way) imports and compares back clean at ticks 200 and 6000 and stops at `fn_800204C8` and at an effect's `efLib_ResumeAll`. The diff runs a full tick once the HUD and effects processes land.

A match that starts from the replay's settings can't hold what the boot left in the original's memory: which slots the GObj and heap pools reuse (objects pair by structure, so this doesn't show), the pad queue's read and write positions (the polls are all at rest in a replay run, and the codes read the queue relative to its read position, so play doesn't depend on them), and HSD's ID table entries from earlier scenes. The comparison will show the last two when a match first runs a tick from the start; whether to start a replay's match from the trace's boot state or to treat them as the platform's is an open question.

**Captured states.** Game code needs real states to run from: a fighter mid-action, with its joints, animations and stage. ssbm-rs's lockstep captures (`CAPTURE=DIR CAPTURE_FUNCS=NAME,...`) save main memory and registers at real calls. `melee-capture` finds which disc archives are loaded where (by header and contents; the game writes into some, such as fighters' action tables), then imports the state into a `Game`: the GObj scheduler with its processes, every joint tree with its animations, references, display lists and shapes, the fighters through their generated mirrors, and the stage (`stage_info`, the stage objects' user data with their variables typed for the stage, the stage parameters the game writes into, the collision geometry and islands, fog, lights, the game camera with its camera boxes, the player slots, game mode and controllers the camera reads, the random seed and HSD's ID table). Afterwards it compares a `Game` with memory, pairing objects by where they're reached from, so objects either side created since pair too. A port runs from the imported state while ssbm-rs runs the call from the same memory, and the two states are compared. Pointers the importer doesn't model yet (static data in the executable, item user data) are listed rather than guessed.

Besides single calls, a captured state can drive longer runs: leaf-check's `last_stage_ticks` runs Final Destination's stage processes alone for 6,400 ticks on both sides from one capture (phases 1 through 8 of its background cycle), `battle_stage_ticks` runs Battlefield's for 9,000, and the `on_state` tests call functions no capture reached on a real stage. The camera's tests also run perturbed copies of captured states (both sides start from the same changed memory) to reach values and branches the replays don't, and enter its special modes from VS states with random controllers. Where objects are freed and new ones made, both sides are paired afresh by where objects are reached from, since the heap reuses blocks by address and pools by last freed.

The audio driver is too (`leaf-check`'s `audio` tests): the importer brings in the driver's virtual voices and globals, the synth's nodes, loaded effects and globals, the AX library's voices, parameter blocks and stacks, and the sound bank (from its loaded copy), and the comparison checks them byte for byte. Their calls are saved with the runner's `CAPTURE_INTERACTED=1`, since every audio function masks interrupts. Their schedule has a check of its own: ssbm-rs's runner records every audio call game code makes, the audio frames and the audio state at every tick's end (`AUDIO_TIMELINE`), and the check replays the calls from a captured tick with melee-sim's timeline placing the frames, comparing tick start and end times and the whole audio state every tick over whole matches (a Final Destination singles and a four-player Battlefield teams replay, about 10,000 ticks each, clean).

The VS match is checked the same way (`leaf-check`'s `vs` and `player` tests): the importer also brings in the player blocks, the pad library (queue, rumble and statuses), the button maps, the scene loop's state and frame clocks, the VS controller, the live standings, the pause screen and the player library's counters, and compares them back. Its captures come from the debug VS mode's random matches (`--mode e --matches`), whose code Slippi's playback codes don't patch (in replay runs they patch the VS scene's frame, setup and entry, and the pad library). Calls the runner never saves (those that load files or reach the audio driver) run from other functions' captured states; the player blocks' and the match's accessors run as random sequences from captured states, comparing every value read and the blocks after each step.

The fighter mirrors come from `tools/structgen`, which generates each game struct with an importer and a field-by-field comparer. `melee-oracle mirror-check TRACE` round-trips every fighter of a state trace through them.

**Replay playback and the Slippi ruleset.** A replay drives a melee-hd match through a port of Slippi's playback codes (`game::playback`): the replay's game start becomes the match's settings, its seed and each frame's recorded inputs and seed are inputs the frontend supplies (`Match::step_replay`, answering what Slippi's EXI device answers), the fighters get the recorded inputs in `Fighter_procInput`, the pad library renews from the newest poll each tick, team stock steals follow the replay, the match ends with the replay, and the playback and recording GObjs exist as in a replay run. The codes that don't change the simulation in a replay played forward are listed in `game::playback`'s documentation. The replay's code list makes the rules (`game::slippi`), and the codes the ported code reaches are ported natively.

Playback's own set also patches fighter code no port covers yet: in `ftCo_8009DD94` (`+0x2FC`, the bone dynamics' end) it sets up every dirty matrix of the fighter's model (each joint with `0x40` and not `0x800000` in its flags, children before siblings, instances included), and in `ftCo_800DEBD0` it reads the debug level as 0, which a retail disc's is anyway. At the match's end the recording codes copy the results into the VS scene's exit data (`gmVsMelee_VsExitInfo`) and rank them with `gm_80166378`, which matters once the exit data is ported.

These ports are checked in leaf-check's `replay` tests against ssbm-rs's ports made with the codes (`ssbm_game::playback`), from captures of replay runs (their header shows how to make them): the recorded inputs with their raw sticks at UCF's thresholds, the first frame's settling, UCF's stick history and SDI, the off-screen limits, the frame reads and the replay's end, stock steals, the seed restored each frame, the general codes' costume rules and the settings themselves. leaf-check's reference runs the patched port of every function whose codes a capture's memory holds (`register_patched`), so the fighter and VS checks on replay captures check the patched behavior too; the VS checks' `place_players` covers neutral spawns, and `input`'s pad library sequences run with the playback patch on a quarter of the time.

**Leaf functions.** `leaf-check` loads the disc's `main.dol` into ssbm-rs's runtime, registers every port, and calls them one at a time, so melee-sim's functions are compared with ssbm-rs's input by input, in both float modes. Inputs are special values, random bit patterns and values spread over each function's useful range. Changing one bit of a constant makes the checks fail.

## Rules

- Floats compare by bit pattern. One ULP is a divergence.
- External events (a disc read completing, a camera snapshot) are inputs, recorded and replayed like controllers, never compared as state.
- A known difference must be explained and listed per replay, as ssbm-rs's known-divergence files are; a blanket exception is never accepted.
